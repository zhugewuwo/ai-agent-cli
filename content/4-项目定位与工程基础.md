# 第 4 章 项目定位与工程基础

前三章从「最小 demo」「三层工程」「失败模式」三个角度给全书建立了坐标系。从本章开始进入具体的工程实现。在讨论 Agent Loop、工具系统、终端 UI 等核心模块之前，需要先交代一组前置决策：X-Code CLI 在赛道中处于什么位置、对接模型用的是什么接口、代码仓库为什么拆成两个包、每个包的内部结构是怎样的。这些决策看似是一次性的基础设施工作，但它们直接决定了后续章节的代码组织方式——例如工具实现放在哪个目录、权限检查在哪一层拦截、UI 回调如何传入 Agent 引擎。

本章不论证「为什么选 TypeScript 而不选 Go / Rust」这类语言选型问题。作者的技术背景是前端与 Node.js 全栈，TypeScript 是日常语言，终端 UI 框架 Ink 基于 React——这些选择是技术栈延续的自然结果，不是逐项权衡评估出来的。工业界的实践也表明语言不是决定 Agent 质量的关键因素。本章将分为如下几个部分进行介绍。

- 4.1 节交代 AI Agent CLI 在当前赛道中的位置，以及选择 CLI 形态的工程约束。
- 4.2 节介绍 LLM 接入层 Vercel AI SDK，说明 X-Code CLI 用到了哪些接口、多供应商如何接入、供应商专有字段如何处理。
- 4.3 节讲解 monorepo 分包策略：为什么拆成 core 和 cli 两个包、单向依赖如何强制执行。
- 4.4 节给出 core 包的内部模块地图，帮助读者在后续章节中快速定位源码位置。
- 4.5 节简要交代 monorepo 配置与构建工具。
- 4.6 节给出本章小结。

## 4.1 AI Agent CLI 的赛道定位

当前主流的 AI 编程助手按产品形态可以分为两类。第一类是编辑器内嵌形态，代表产品包括 Cursor（基于 VS Code 的独立 IDE，内置 AI 能力）、GitHub Copilot Chat、Cline、Continue 等，它们以 IDE 插件或内置功能的方式运行，与编辑器的文件树、终端、调试器深度集成。第二类是独立 CLI 形态，代表产品包括 Claude Code、Codex、Gemini CLI 等，它们脱离 IDE 独立运行在终端中，通过命令行与用户交互。少数产品同时提供两种形态。

X-Code CLI 属于独立 CLI 形态。选择这种形态有几个工程上的考量。（1）脱离 IDE 限制，可在任何终端环境运行，包括 SSH 远程连接到服务器的场景——在远端服务器上运行 `xc`，本地终端就是交互界面。（2）易于嵌入脚本和 CI 流水线，通过管道输入或 `--print` 非交互模式即可在自动化环境中使用。（3）跨编辑器复用——使用 Vim、Emacs、VS Code 或其他编辑器的开发者都可以使用同一个工具，不受编辑器绑定。

## 4.2 LLM 接入层：Vercel AI SDK

X-Code CLI 通过 [Vercel AI SDK](https://ai-sdk.dev/)（npm 包名 `ai`）对接大语言模型。本节交代它在项目中承担什么角色、用到哪些接口；具体的 Agent Loop 实现和供应商适配细节分别在 Ch.08 和 Ch.09 展开。

### 4.2.1 用到的核心接口

X-Code CLI 用到的 AI SDK 核心接口如表 4-1 所示。

| 接口 | 用途 | 调用位置 |
|---|---|---|
| `streamText` | 主 Agent Loop——把对话历史与工具集发给模型，流式返回文本与工具调用 | `agent/loop.ts` |
| `generateText` | 一次性非流式调用——用于会话摘要、上下文压缩、视觉降级、记忆提炼等后台任务 | `compression.ts` / `vision-fallback.ts` / `memory-extractor.ts` 等 |
| `tool({...})` | 定义工具——`description` + `inputSchema`（Zod）+ `execute` | `tools/*.ts` |
| `createProviderRegistry` | 把多个供应商装进一个注册表，按 `'<provider>:<model>'` 字符串路由到对应供应商 | `providers/registry.ts` |

> 表 4-1 X-Code CLI 用到的 AI SDK 核心接口

除表中四个接口外，记忆提炼模块还使用了 `Output` 来约束模型的结构化输出（Ch.36），MCP 工具桥接使用了 `jsonSchema` 来包装外部工具的参数模式（Ch.37）。类型层面只用到 `LanguageModel`、`ModelMessage`、`UserContent`、`FilePart` / `ImagePart` / `TextPart` 等少数几个。一个典型的调用如下所示：

<!-- check:ignore=punctuation -->
```ts
import { streamText } from 'ai'

const result = streamText({
  model,       // registry.languageModel('anthropic:claude-sonnet-4-6') 取出的实例
  system,
  messages,
  tools,
  abortSignal, // 一路传递到 fetch 与 shell 子进程，Esc 一键打断
  providerOptions, // 各家专有字段从这里透传
})
```

### 4.2.2 多供应商接入

多数供应商有对应的 `@ai-sdk/<vendor>` 适配包（如 `@ai-sdk/anthropic`、`@ai-sdk/openai`、`@ai-sdk/google`、`@ai-sdk/deepseek` 等）。所有适配包对外都统一暴露为 `LanguageModel` 接口，下游代码不需要区分当前使用的是哪家供应商。`createProviderRegistry` 将所有已配置 API Key 的供应商聚合成一个查询入口，通过 `registry.languageModel('anthropic:claude-sonnet-4-6')` 这种字符串即可取出对应的模型实例。X-Code CLI 目前支持 8 家主流供应商（Anthropic、OpenAI、Google、xAI、DeepSeek、阿里云、智谱、Moonshot），另外还支持一个 OpenAI 兼容的自定义端点，用于接入没有官方适配包的供应商。所有供应商的 API Key 均从环境变量读取，不需要在代码中显式传入。

### 4.2.3 供应商专有字段

不同供应商各有各的专有参数：Anthropic 有 `cache_control`（缓存控制）、OpenAI 有 `reasoning_effort`（推理力度）、Google 有 `thinkingConfig`（思考配置）。AI SDK 的处理方式是不强行抹平差异，而是提供一个 `providerOptions` 字段，按供应商名分组后直接透传：

```ts
streamText({
  model,
  messages,
  providerOptions: {
    anthropic: { cacheControl: { type: 'ephemeral' } },
    openai: { reasoningEffort: 'high' },
  },
})
```

X-Code CLI 在 `providers/cache-control.ts` 和 `providers/thinking.ts` 中维护了「按当前供应商拼出对应 `providerOptions`」的映射逻辑。对外只暴露 `/thinking on|off` 这类统一开关，将各家差异封装在适配层内部。详见 Ch.09 多供应商支持。

### 4.2.4 依赖 SDK 的代价

跟随 SDK 主版本升级时，类型定义和字段名可能发生变化（如 Chunk 类型枚举、usage 对象结构），需要按发布说明逐个调整调用点。这是选择「用 SDK」这条路径本来就需要承担的固定成本。换成自研 HTTP 调用层同样需要随各家供应商的协议变化做调整，只是把变化点从 SDK 层移到了 HTTP 层。

## 4.3 拆 core / cli 两个包

X-Code CLI 的代码仓库拆成了 `@x-code-cli/core` 和 `@x-code-cli/cli` 两个包。这种拆分不只是形式上的工程化——它直接决定了未来能否把 Agent 逻辑复用到 VS Code 插件、Web 版、SDK 等其他端。两个包的职责划分与依赖关系如图 4-1 所示。


![image.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/073a294a71b7402b9023fa31e14422bc~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=291&h=370&s=16413&e=png&b=ffffff)

> 图 4-1 双包结构与单向依赖关系

`@x-code-cli/core`（路径 `packages/core/`）是 Agent 逻辑层，包含 AI SDK 调用、工具实现、供应商注册、知识系统、权限模型等。它有一条关键约束：不引入任何 UI 依赖——`package.json` 中没有 React、Ink、yargs 或其他终端 UI 库。

`@x-code-cli/cli`（路径 `packages/cli/`）是终端界面层，包含 Ink/React 组件、yargs 参数解析、用户输入处理、流式渲染等。它依赖 core，但 core 不能反向依赖 cli。

这种单向依赖通过三层机制强制执行。（1）TypeScript 的 Project References 在编译期拦截：cli 的 `tsconfig.json` 声明了对 core 的引用，如果反过来给 core 加 cli 引用会形成循环，TypeScript 编译器直接报错。（2）core 的 `package.json` 没有声明对 cli 的依赖，也没有 React、Ink、yargs 这些终端界面层的包，即使误写了反向 `import`，模块解析也会直接失败。（3）`AgentCallbacks` 接口统一承接 UI 交互：core 不知道 UI 是 Ink 还是 Webview，所有「询问用户」「汇报进度」的操作都通过这个回调接口由 cli 在运行时注入具体实现。

这种分层为未来的扩展方向提供了基础。如果要开发 VS Code 插件，只需复用 core 的 Agent 逻辑，将 cli 那套 Ink 渲染替换为 Webview 中的 React，core 的代码无需改动。如果要提供 Web 版，将 core 包装到一个 HTTP server 后面即可。如果要以 SDK 形式发布，将 core 的 `index.ts` 补全导出即可——架构上已经就绪。

## 4.4 core 内部模块地图

`@x-code-cli/core` 内部按职责分目录。读者完全不必现在就读完每个文件——这张地图的作用是让后续章节出现「打开 `agent/loop.ts` 看一下」这类指引时，读者能立刻知道它在项目中属于哪一层。

├── agent/          Agent 引擎主体
│   ├── loop.ts            Agent Loop 主循环               → Ch.08
│   ├── loop-state.ts      LoopState 状态容器              → Ch.08
│   ├── loop-guard.ts      死循环检测与阻断                → Ch.32

│   ├── plan-tools.ts      todoWrite / Plan Mode 分发      → Ch.20 / Ch.21

├── tools/          工具实现（13 个内置 + task 动态注入）
│   ├── read-file / edit / write-file                      → Ch.13
│   ├── shell / shell-provider / shell-utils               → Ch.14

几条值得现在就记住的结构关系：`agent/` 是引擎，`tools/` 是工具集——引擎知道「什么时候该调工具」，工具自己只管「被调时做什么」，两者通过 `tool-execution.ts` 这个分发层连接。`providers/` 是适配层，将 8 家模型供应商的协议差异封装在一处，让 Agent Loop 能用一份代码对接所有供应商。`permissions/` 和 `knowledge/` 是横切关注点——每次工具调用前过权限层检查，每次启动从知识层读取项目配置。`mcp/`、`plugins/`、`skills/`、`hooks/` 是扩展生态相关的模块，将产品从工具变成平台。`index.ts` 是公开 API 边界——cli 只从这个文件 import，core 内部各文件之间的互相引用不受此约束。

## 4.5 工程配置

monorepo 配置、构建工具、依赖方向这些细节对理解产品行为不是必需的，主要是给想阅读或贡献源码的读者一个交代。更深入的配置细节见附录一（构建工具链内部）。

monorepo 使用 pnpm workspace 管理。根目录的 `pnpm-workspace.yaml` 声明 `packages/*` 为 workspace 成员，cli 引用 core 写 `"@x-code-cli/core": "workspace:*"`。`pnpm -r run build` 递归触发各包的 build 脚本，按依赖顺序先 core 后 cli。

TypeScript 使用 Project References 与增量构建。根 `tsconfig.json` 的 `references` 串联两个包，每个包声明 `composite: true`。`tsc -b` 按依赖顺序构建，只编译发生变化的部分。共享编译选项放在 `tsconfig.base.json` 中（`target: ES2022`、`module: NodeNext`、`strict: true` 等）。

两个包都是 ESM-only（`"type": "module"`），相对 import 必须带 `.js` 后缀（即使源文件是 `.ts`）。这条要求源自 Node.js 原生 ESM 解析规则本身，TypeScript 的 `NodeNext` 模块解析只是把检查提前到编译期，避免运行时才报 `ERR_MODULE_NOT_FOUND`。

## 4.6 小结

本章交代了后续章节默认需要了解的工程基础。X-Code CLI 是一个独立 CLI 形态的 AI 编程助手，脱离 IDE 独立运行，能进 SSH、CI、任意终端环境。LLM 接入层使用 Vercel AI SDK，实际用到的接口只有 `streamText`、`generateText`、`tool`、`createProviderRegistry` 四个，供应商专有字段通过 `providerOptions` 透传。代码仓库拆成 core（Agent 逻辑层）和 cli（终端界面层）两个包，单向依赖通过 TypeScript Project References、包依赖隔离、`AgentCallbacks` 回调接口三层机制强制执行。core 内部按职责分为 `agent/`（引擎）、`tools/`（工具集）、`providers/`（供应商适配）、`permissions/`（权限）、`knowledge/`（知识）等目录，后续章节的每段代码都可以在这张地图中找到对应位置。
