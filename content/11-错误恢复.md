# 第 11 章 错误恢复：从 SDK 异常到人类可读提示

上一章讨论了流式 chunk 的处理过程，其中错误 chunk 的主动抛出和结果 Promise 的排空是异常处理链条的起点。本章接手这条链条的下半段：当异常从流消费层到达外层异常捕获块之后，如何对错误分类、决定重试还是终止，并将技术性的 SDK 异常转化为用户可以理解并采取行动的提示信息。本章分为如下几个部分进行介绍。

- 11.1 节讨论错误分类器如何把 14 种异构错误归为一张判定表。
- 11.2 节讲解如何解包嵌套错误，从 SDK 包装层下提取真实信息。
- 11.3 节介绍上下文超限和 orphan tool_call 这两类需要在流之前预处理的错误。
- 11.4 节讨论 HTTP 层拦截如何识别永久错误并将其短路掉。
- 11.5 节讲解 SDK 内部重试与用户中止信号的处理路径。
- 11.6 节讨论输出截断的自动续写与内容审核拦截。
- 11.7 节介绍从内部异常到用户提示的转化过程。
- 11.8 节给出本章小结。

> AI 知识背景：LLM 的结构性失败模式
>
> 在讨论 API 层的错误恢复之前，有必要先区分两类不同性质的失败。LLM 本身存在一组结构性失败模式（Structural Failure Modes），它们不是网络层能解决的。幻觉（Hallucination）是指模型自信地输出错误事实，原因在于训练目标是预测概率最高的下一个 token，而非保证事实正确；Agent 场景中的典型表现包括编造不存在的 API、引用错误的函数签名、声称「已经执行了 X」但实际并未调用工具。指令偏移（Instruction Drift）在长对话中尤为明显，模型会逐渐忽略早期的系统指令，多轮工具调用加上下文压缩后问题更加突出。过度自信（Overconfidence）使模型倾向于给出一个答案而非承认不确定性，导致 Agent 不知道何时该停下来询问用户。输出截断发生在撞到 max_tokens 上限时（详见本章 11.6 节自动续写）。格式错误则表现为工具调用参数不符合 schema 或 JSON 结构不完整。此外还有 doom-loop（详见 Ch.32），即模型对相同错误反复重试却不做任何实质性改变。这些失败由提示词工程、工具描述精细化和循环护栏（Loop Guard）等机制应对，不在本章范围内。本章讨论的「错误恢复」专指 API、网络和协议层面的错误。

## 11.1 为什么要把 14 种异构错误归为一张判定表

> 源码：`packages/core/src/agent/api-errors.ts::classifyApiError`

错误分类器（Error Classifier）的职责是把来源各异、格式不统一的 SDK 错误映射成统一的人类可读消息，并标记该错误是否可重试。当前版本一共识别 14 种错误形态，按优先级从高到低依次判定。优先级顺序很重要，因为同一个错误消息可能同时命中多条规则，排在前面的规则先匹配就先返回。以下是分类器的判定链结构（伪代码省略了返回值的完整字段，只保留语义）。

<!-- check:ignore=punctuation -->
```ts
export function classifyApiError(err: unknown): ClassifiedError {
  const msg = extractErrorMessage(err)        // 见下文：要先提取真实错误
  const status = extractHttpStatus(msg)

  if (isContextTooLongError(err))           return { 提示压缩或 /clear, retryable: false }
  if (isReasoningContentError(msg))         return { 提示 SDK 兼容问题, retryable: false }
  if (isMissingApiKeyError(msg))            return { 提示设置环境变量, retryable: false }
  if (isUnauthorizedError(msg, status))     return { '401 鉴权失败', retryable: false }
  if (isInsufficientBalanceError(msg, st))  return { '402 余额不足', retryable: false }
  if (isForbiddenError(msg, status))        return { '403 禁止访问', retryable: false }
  if (isModelNotFoundError(msg, status))    return { '404 模型不存在', retryable: false }
  if (isContentPolicyError(msg, status))    return { '422 内容审核拦截', retryable: false }
  if (isMaxTokensError(msg))                return { 'max_tokens 超模型限', retryable: false }
  if (isServiceUnavailableError(msg, st))   return { '503 服务不可用', retryable: false }
  if (isRateLimitedError(msg, status))      return { '429 限流', retryable: true }
  if (isNetworkError(msg))                  return { '网络错误', retryable: true }
  if (isTypeValidationError(err, msg))      return { '供应商返回非法响应', retryable: false }
  if (isMalformedToolHistoryError(msg))     return { 'orphan tool_call 历史', retryable: false }

  return { message: msg, retryable: false }
}
```

14 条规则中，多数按 HTTP 状态码或错误消息关键词直接归类（401 鉴权失败、403 禁止访问、429 限流、503 服务不可用、网络错误），逻辑直接。以下几条需要单独解释为什么必须作为独立规则存在，而不能只靠状态码一刀切。

| 规则 | 为什么需要单独识别 |
| --- | --- |
| `isContextTooLongError` | 不能走普通错误退出路径，必须触发响应式压缩（Reactive Compression）并重试当前轮（详见 11.3 节和 Ch.31） |
| `isReasoningContentError` | DeepSeek Reasoner 在 tool-call 链中要求每条 assistant 消息携带 `reasoning_content` 字段，这是 SDK 兼容问题而非用户错误，需给出清晰提示 |
| `isMissingApiKeyError` | 从错误消息中提取出供应商名称（如 "Anthropic API key is missing" → "Anthropic"），告诉用户具体需要设置哪个环境变量 |
| `isInsufficientBalanceError`（402） | 与 401 鉴权失败不同，402 表示余额耗尽。匹配时使用小写比较以兼容不同供应商的措辞差异（Moonshot 用 `please recharge`，DeepSeek 用 `Insufficient Balance`） |
| `isModelNotFoundError`（404） | 模型 ID 写错、被弃用或当前账号未开通。OpenAI 的错误体在 "model" 和 "does not exist" 之间插入模型名，因此匹配条件是两个关键词同时出现即命中 |
| `isContentPolicyError`（422） | 供应商安全过滤拦截，重试相同内容必定再次被拦截，因此标记为不可重试，提示用户改写或切换模型 |
| `isMaxTokensError` | 不同模型的输出上限不同，用户或配置传入了超过模型限制的值会被拒绝，需要提示调整 |
| `isTypeValidationError` | AI SDK 用 Zod 校验响应结构，部分供应商（如阿里 dashscope）出错时返回 JSON 错误体而非 SSE 流，触发类型校验错误。真实的供应商错误信息嵌套在包装层内部（详见 11.2 节） |
| `isMalformedToolHistoryError` | tool_call 与 tool_result 配对错乱时多数供应商会拒绝整个请求，需要触发修复机制（详见 11.3 节） |

其余几条（401、403、429、503、网络错误）按 HTTP 状态码直接归类。404 和 422 这两条实际上也可以按状态码归类——后文 11.4 节的 HTTP 层拦截已经把对应的响应体重写到了这两个状态码上，分类器只需检查状态码即可命中；表中列出的消息关键词是为绕过 HTTP 拦截直接抛出的路径提供降级匹配。

## 11.2 解包嵌套错误：SDK 包装层下的真实信息

> 源码：`packages/core/src/agent/api-errors.ts::extractErrorMessage`

分类器在做模式匹配之前，首先要解决一个前置问题：SDK 抛出的异常对象的 `message` 字段未必包含供应商返回的真实错误信息。AI SDK 在校验响应结构时使用 Zod，当供应商返回的不是预期的 SSE 流而是一个 JSON 错误体时，Zod 校验失败会抛出类型校验异常，原始的供应商错误（如「账户余额不足」或「模型不存在」）被嵌套在异常对象的深层属性中。如果不做解包直接读取异常的 `message` 字段，看到的只是 Zod 的结构转储信息，后续的关键词匹配全部失败，最终用户看到的是一段无法理解的技术信息。

<!-- check:ignore=punctuation -->
```ts
function extractErrorMessage(err: unknown): string {
  if (!(err instanceof Error)) return String(err)
  const msg = err.message
  // AI SDK TypeValidationError 把真实供应商错误嵌套在 `.value` 里
  const val = (err as Record<string, unknown>).value
  if (val && typeof val === 'object') {
    const inner = (val as Record<string, unknown>).error
    if (inner && typeof inner === 'object') {
      const innerMsg = (inner as Record<string, string>).message
      if (typeof innerMsg === 'string') return innerMsg
    }
  }
  return msg
}
```

解包逻辑的层次结构反映了 SDK 的异常包装方式：异常对象上的 `.value` 属性是 Zod 校验的原始输入（即供应商返回的 JSON 体），其中 `.error.message` 才是供应商的错误描述。以阿里 dashscope 为例，当请求出错时它返回的不是 SSE 流而是一个标准的 JSON 错误体，AI SDK 的 Zod 校验失败后抛出类型校验异常，原始的「余额不足」或「模型不存在」信息就嵌套在这个层次结构中。解包函数先尝试沿这条路径提取，提取失败则回退到异常本身的 `message` 字段。这条路径在接入新的、会返回非 SSE 错误体的供应商时尤其关键——如果解包逻辑未能覆盖该供应商的错误结构，用户将只看到 Zod 转储而非可操作的错误提示。

## 11.3 两类需要预处理的错误

14 种错误形态中，有两类不能等到分类器判定后再处理，而是需要在错误到达分类器之前（甚至在流开始之前）就完成预处理。

第一类是上下文超限（Context Too Long）。这类错误的处理路径与普通错误完全不同：命中后不是退出循环，而是触发响应式压缩并重试当前轮（详见 Ch.31），因此它在分类器中排在最高优先级位置。识别的难点在于各家供应商返回超限错误的措辞各不相同——OpenAI 返回 `context_length_exceeded`，Anthropic 返回 `prompt is too long`，其他供应商又各有表述。识别函数维护了一个字符串模式列表（当前 7 条），对错误消息逐条做子串匹配；同时还检查 HTTP 413 状态码，这是 11.4 节的 HTTP 层拦截为上下文超限错误重写的目标码值。新增供应商时只需往列表中添加一条匹配模式，不需要修改判定逻辑。

第二类是 orphan tool_call。当消息历史中出现没有配对 tool_result 的 tool_call 时（最常见的触发场景是模型给出的工具入参未通过 Zod 校验，SDK 拒绝执行），下一轮请求携带这段残缺历史发送给供应商，供应商会直接返回 400 拒绝。三家主要供应商的拒绝措辞如下。

```text
OpenAI:    "Messages with role 'tool' must be a response to a preceding message with 'tool_calls'."
DeepSeek:  "tool_calls and tool_call_ids ..."
Anthropic: "tool_use without tool_result"
```

修复函数在每轮流开始之前对消息历史做一次预防性扫描，为没有配对的 tool_call 补充一条合成的错误 tool_result。扫描是幂等的，每轮执行的开销极低。修复机制的详细设计见 Ch.17。

## 11.4 永久错误的 HTTP 层短路

> 源码：`packages/core/src/providers/registry.ts::permanentErrorFetch`

供应商返回的 HTTP 状态码并不总是准确反映「重试能否解决问题」，有时一个不可恢复的永久错误会伪装成可重试的状态码——我们称之为「假可重试」。最典型的反例是 Moonshot——账户余额耗尽时它返回 HTTP 429，响应体是 `"... is suspended due to insufficient balance, please recharge ..."`。AI SDK 按状态码判断可重试性，将 429 视为限流可重试，于是启动 3 次指数退避重试，每次都打在同一个余额不足的错误上。约 30 秒后用户才看到一个被多层包装的错误对象，原始的「余额不足」信息深藏在最内层。这 30 秒完全是浪费。

X-Code CLI 的解决方案是在所有供应商的 HTTP 请求上挂载一层 fetch 拦截器。拦截器在收到错误响应（状态码 ≥ 400）后，先读取响应体并按关键词扫描是否属于永久错误，命中后将 HTTP 状态码重写为 SDK 视为不可重试的码值，使 SDK 在第一次尝试就跳出重试循环，错误直接到达分类器。图 11-1 以 Moonshot 余额不足为例展示了拦截器的工作时序。


![image.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/6b8dfb0465764595a7b8d2170c535e55~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1041&h=497&s=50659&e=png&b=ffffff)

> 图 11-1 永久错误拦截时序——步骤 2 在 SDK 看到响应之前完成状态码重写，避免 3 次无效的指数退避

5 类永久错误对应的目标状态码如下。

| 类别 | 目标状态码 | 命中关键词举例 |
| --- | --- | --- |
| 余额不足 / 配额耗尽 | 402 | `insufficient balance` / `exceeded_current_quota` / `please recharge` |
| 上下文超限 | 413 | `context_length_exceeded` / `prompt is too long` / `maximum context length` |
| 内容安全策略拦截 | 422 | `content_policy_violation` / `content_filter_triggered` |
| API key 失效 | 401 | `invalid api key` / `expired api key` |
| 模型 ID 不存在 / 未开通 | 404 | `model_not_found` / `model … does not exist` |

匹配依据是响应体关键词而非 HTTP 状态码本身，因此任何 4xx/5xx 错误响应都会经过这一层扫描。成功响应（状态码 < 400）直接放行，不读取响应体，避免把 SSE 流提前消费掉。

<!-- check:ignore=punctuation -->
```ts
const permanentErrorFetch: typeof fetch = async (input, init) => {
  const response = await fetch(input, init)
  if (response.status < 400) return response

  const text = await response.clone().text().catch(() => '')
  if (!text) return response

  const lower = text.toLowerCase()
  for (const category of PERMANENT_ERROR_CATEGORIES) {
    const hit = category.patterns.some((p) =>
      typeof p === 'string' ? lower.includes(p) : p.test(lower),
    )
    if (!hit) continue
    if (response.status === category.status) return response
    return new Response(text, {
      status: category.status,
      statusText: category.statusText,
      headers: response.headers,
    })
  }
  return response
}
```

拦截器只修改状态码，响应体原样传递——分类器仍然需要从响应体中提取供应商的错误消息做关键词匹配，状态码重写不能影响响应体内容。注册供应商时将这个拦截器作为自定义 fetch 传入即可。

<!-- check:ignore=punctuation -->
```ts
providers.anthropic = createAnthropic({ fetch: permanentErrorFetch })
providers.openai = createOpenAI({ fetch: permanentErrorFetch })
// Google、xAI、Alibaba、Moonshot、自定义端点同样使用 permanentErrorFetch
providers.deepseek = createDeepSeek({ fetch: deepseekReasoningFetch })
```

DeepSeek 使用的是另一个专用的 fetch 包装器，它先为 v4 系列模型回填 `reasoning_content` 字段（详见 Ch.34 thinking 模式），最后再调用永久错误拦截器，两层效果叠加。

## 11.5 SDK 内部重试与中止信号

> 源码：`packages/core/src/agent/loop.ts`

经过 HTTP 层拦截后，进入 SDK 重试层的只剩下真正可重试的错误——429 限流、5xx 服务端临时故障、网络连接中断等。AI SDK 的 `streamText` 调用通过 `maxRetries: 3` 启用自动指数退避重试。

<!-- check:ignore=punctuation -->
```ts
streamText({
  model,
  system,
  messages,
  tools,
  maxRetries: 3,
  abortSignal: options.abortSignal,
  onError: ({ error }) => {
    // 抑制 SDK 默认的 console.error 转储；真错误统一走 classifyApiError
    if (process.env.DEBUG_STDOUT) debugLog('stream.onError', String(error))
  },
})
```

重试期间对用户完全透明，SDK 在内部处理失败并重新发起请求，流仍按正常流程产出 chunk。永久错误已经被上一节的 HTTP 层拦截重写为不可重试的状态码，不会消耗这 3 次重试预算。3 次重试全部用完后仍然失败，SDK 将最后一次的错误抛出，由分类器处理。调试模式下（`DEBUG_STDOUT=1`），SDK 的重试日志会写入 `~/.x-code/logs/debug.log`，方便排查间歇性失败。

`onError` 回调必须显式覆盖，这一点容易被忽略。SDK 的默认实现是调用 `console.error(error)`，会把整个重试错误对象（含嵌套的 API 调用错误数组和供应商响应体）用 `util.inspect` 完整转储到 stderr，内容冗长且对用户没有参考价值。X-Code CLI 将其替换为仅在调试模式下记录一条简短日志，UI 用户只看到分类器输出的简洁提示。

中止信号（Abort Signal）是用户按 Esc 或 Ctrl+C 时的传导通道。信号触发后，进行中的 fetch 请求立即取消，流式迭代器抛出中止异常。

```
用户 Esc → AbortController.abort() → fetch 立即取消 + 流式抛 AbortError
                                  ↓
runTurn try/catch 捕获 → isAbortError(err, signal) → 返回 { kind: 'aborted' }
                                  ↓
agentLoop 看到 'aborted' → 跳出，不调 onError（Ch.08 已述）
```

中止是不可重试的中断信号，Agent Loop 捕获后直接退出当前轮，不触发错误回调，不向用户显示错误信息——UI 只显示一条「请求已被用户中断」的状态提示。

## 11.6 输出截断与内容审核

> 源码：`packages/core/src/agent/loop.ts`

当模型的输出被 max_tokens 截断时，结束原因（Finish Reason）为 `length`。这不是一个错误，但用户看到的是一段被截断到一半的回复，体验很差。X-Code CLI 的策略是自动追加一条续写提示，让模型从断点继续输出。

<!-- check:ignore=punctuation -->
```ts
const MAX_CONTINUATIONS = 3
let continuationAttempts = 0

if (outcome.finishReason === 'length') {
  if (continuationAttempts < MAX_CONTINUATIONS) {
    continuationAttempts++
    state.messages.push({
      role: 'user',
      content:
        'Output token limit hit. Resume directly — no apology, no recap. Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces.',
    })
    continue
  }
  callbacks.onError(
    new Error(`Response still truncated after ${MAX_CONTINUATIONS} continuation attempts — ask a narrower question.`),
  )
  break
}
```

续写提示只进入内部消息历史，不显示在 UI 的对话流中，用户只看到一段完整的回复，不会意识到中间发生了截断和续写。续写次数上限为 3 次，超过后提示用户缩小问题范围。计数器在任何成功的工具执行轮次后重置为零，避免连续的 `length` 截断累计触发上限。续写提示的文案经过精心设计——要求模型「直接续写、不致歉、不重述上文、必要时把剩余工作拆成更小的段落」，目的是避免模型在续写时浪费 token 做总结和重复。

结束原因为 `content-filter` 时，表示供应商的内容审核系统拦截了模型输出。

<!-- check:ignore=punctuation -->
```ts
if (outcome.finishReason === 'content-filter') {
  callbacks.onError(new Error('Response stopped by the provider content filter.'))
}
break
```

与截断不同，内容审核拦截是确定性的——用相同的输入重试必定再次被拦截，因此不做重试，直接通知用户这是审核问题而非网络或模型故障，让用户能针对性地调整提问或通过 `/model` 切换到其他模型。

## 11.7 从内部异常到用户提示

错误分类器的最终产物是一条人类可读的提示信息。设计原则是不暴露内部调用栈，而是给出简洁的错误描述加上用户可以采取的操作建议。以下是几种典型错误从 SDK 异常到用户看到的提示的映射关系。

| 内部错误 | 用户看到的消息 |
| --- | --- |
| `Error: 401 Unauthorized` | API authentication failed (401). Please check your API key... |
| `Error: 402 Insufficient Balance` | API account balance insufficient (402). Top up... or /model |
| `Error: 404 model_not_found` | Model not found (404). ... Switch with /model |
| `Error: 422 content_policy_violation` | Content blocked by the provider's safety filter (422). Rephrase... or /model |
| `Error: 429 Too Many Requests` | Rate limited (429). Waiting for retry... |
| `Error: ECONNRESET` | Network error: ECONNRESET. Retrying... |
| `Error: prompt is too long: 250000 > 200000` | Context too long — try /compact or /clear |
| `AI_TypeValidationError: ...` | Provider returned an error: <真实错误>. Try /model |
| `AbortError: The operation was aborted` | （UI 显示 [Request interrupted by user]，不触发错误回调） |

每条提示都包含两个要素：错误的性质描述和用户可以采取的下一步操作（充值、切换模型、压缩上下文、改写提问等）。调试所需的完整错误信息保留在日志中供排查，UI 层只展示这条精简后的提示。

错误处理分布在循环的三个阶段：（1）发起流式请求阶段——鉴权失败、配置错误、orphan tool_call 历史等错误在请求发出时就会抛出，异常捕获块直接交给分类器处理；（2）流消费阶段——网络中断、上下文超限等错误在迭代过程中抛出，捕获后先执行排空操作（Ch.10 已述）再判断是否属于上下文超限以决定重试还是分类；（3）响应收集阶段——流结束后的解析错误同样经过排空和分类。三个阶段的异常处理结构相同：先排空结果 Promise 防止未处理 reject 导致进程崩溃，再交给分类器统一处理。

## 11.8 小结

本章从错误的产生到最终呈现给用户，完整地走过了 X-Code CLI 的错误恢复链路。分类器识别 14 种典型错误形态，每种都映射为人类可读消息并标记是否可重试。在分类之前，解包函数从 SDK 的类型校验异常中提取出真实的供应商错误信息，否则后续的关键词匹配全部失效。上下文超限和 orphan tool_call 这两类错误需要在流开始之前预处理——前者触发响应式压缩并重试当前轮，后者为残缺的工具调用历史补上合成的错误结果。HTTP 层拦截器把 5 类永久错误的状态码重写为不可重试的码值，防止 SDK 对余额不足、模型不存在等不可能通过重试解决的问题做无谓的指数退避。SDK 的 3 次自动重试只对真正的临时故障生效，中止信号提供了用户随时终止请求的通道。输出截断时自动追加续写提示（上限 3 次），内容审核拦截则直接退出并告知用户原因。所有错误最终都汇入统一的分类器，转化为简洁的提示信息加上可操作的下一步建议。
