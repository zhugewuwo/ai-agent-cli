# 第 22 章 Plan Mode、todoWrite、task：三种「让模型自己规划」的形态对比

读完 Ch.19 至 Ch.21，读者手里已经有了三个看起来都和「任务规划」有关的机制：Plan Mode（计划模式）是一种会话状态，把模型的行为锁定在只读探索与写计划文件上；todoWrite 是一个工具，在内存中维护一份带状态的实时清单；task 同样是一个工具，将一段子任务连同独立的消息历史委派给全新的 agent 循环。三者名字里都带「规划」的意味，新手很容易产生几个典型误解——「Plan Mode 是不是就是带审批的 todoWrite？」「task 是不是 todoWrite 的进阶版？」「大型重构任务到底选哪个工具？」本章不再重复三者各自的内部机制（前面三章已经详细讲过），只回答一件事：在同一个真实任务里，它们各自负责哪个维度，以及如何接力协作。本章分为如下几个部分进行介绍。

- 22.1 节用一张对比表说明三者是三个维度而非三个替代品。
- 22.2 节用一个迁移任务展示三阶段接力的完整过程。
- 22.3 节讨论跳过 Plan Mode 直接建清单的代价。
- 22.4 节解释 task 不是 todoWrite 的进阶版。
- 22.5 节说明 Plan Mode 和 todoWrite 是前后接力而非上下替代。
- 22.6 节总结按场景而非按「高级程度」选工具的原则。
- 22.7 节给出本章小结。

## 22.1 三个维度而非三个替代品

将三者放在一张表里对比，差异立刻可见：

| 维度 | Plan Mode | todoWrite | task |
| --- | --- | --- | --- |
| 形态 | 会话状态（约束模型可用行为） | 工具：维护内存清单 | 工具：委派子任务 |
| 触发 | 用户 `/plan` 或模型调 `enterPlanMode` | 模型调 `todoWrite` | 模型调 `task` |
| 运行容器 | 当前 agent 循环，靠系统提示词覆盖段软约束 | 当前 agent 循环 | 新开独立的 agent 循环 |
| 持久化 | plan 文件写入磁盘（`.x-code/plans/`） | 内存 `LoopState.todos`（不写入磁盘） | 子任务执行完毕后丢弃，只返回最终消息 |
| 用户审批 | 必须（`exitPlanMode` 时停下等用户确认） | 不需要 | 不需要 |
| 解决的问题 | 大事之前先停下让用户看计划 | 拆步 + 实时反馈进度 | 把一段独立工作外包，不污染主对话 |

从表中可以看出，三者管理的维度完全不同。Plan Mode 控制模型当下能做什么，它是一种状态；todoWrite 反映模型当下做到哪了，它是一个进度仪表盘；task 把一段工作整段外包出去，它是一个调度器。三者不存在互相替代的关系——它们在同一个大型任务中可以依次登场，各自负责自己擅长的维度。接下来用一个具体场景把它们放在同一条时间线上观察。

## 22.2 一个迁移任务里的三阶段接力

假设用户输入：「把项目从 Express 迁到 Fastify，所有路由、中间件、测试都要适配。」这是一个典型的大型重构任务——影响多个文件、需要分步协作、中间还有一段独立的调研工作。在处理这个任务的过程中，Plan Mode、todoWrite、task 会以接力的方式依次登场，每个机制在自己擅长的阶段发挥作用。

### 第一阶段：在 Plan Mode 下探索并写计划

用户用 `/plan` 进入计划模式。模型在覆盖段的约束下只读探索代码、边探索边写 plan 文件、通过 `askUser` 与用户确认关键决策（如 rate-limit 用 `@fastify/rate-limit` 还是自实现、测试框架是否迁移）。几轮迭代后 plan 文件完成，模型调 `exitPlanMode` 提交审批，用户通过。

### 第二阶段：计划翻译成 todoWrite 清单

`exitPlanMode` 审批通过的瞬间，会话状态从 `'plan'` 切到 `'acceptEdits'`，系统提示词的计划模式覆盖段不再追加。模型在状态切换后的第一轮里，把 plan 文件中列出的步骤翻译成一份 todoWrite 清单：

```jsonc
{
  "todos": [
    { "content": "替换 server 启动代码到 fastify", "status": "in_progress" },
    { "content": "迁移路由（共 18 个 endpoint）", "status": "pending" },
    { "content": "调研 @fastify/rate-limit 配置等价物", "status": "pending" },
    { "content": "迁移中间件（auth / log / cors）", "status": "pending" },
    { "content": "把 supertest 测试改成 fastify.inject", "status": "pending" },
    { "content": "运行全量测试 + 类型检查", "status": "pending" }
  ]
}
```

每完成一项，模型调一次 `todoWrite` 更新整份清单。用户在终端面板上看到 `◼` 标记不断前移、`✓` 逐项累积，对于当前的状态做到哪一步一目了然。清单驻留在内存（`LoopState.todos`）中，每次调用都是全量覆写，不做增量修改。

### 第三阶段：遇到独立调研，派 task 出去

走到第三条「调研 @fastify/rate-limit 配置等价物」时，模型面临一个选择。这件事有三个特征：不需要修改主仓库代码（纯调研）；需要的上下文（fastify 文档、rate-limit 库 API）和主对话无关——通过 webFetch 取回的大段 HTML 留在主对话历史里只会浪费 token；输出形态是一份「建议这样配置 + 关键差异」的小报告。这正是 task 委派的理想场景。模型调用 task 工具：

```jsonc
{
  "description": "调研 rate-limit 等价物",
  "subagent_type": "general-purpose",
  "prompt": "我们正在把项目从 Express 迁到 Fastify。原项目用 express-rate-limit，配置如下：windowMs=60000、max=100、message='Too many requests'。请调研 @fastify/rate-limit 的等价配置写法，重点确认：1) windowMs/max 在 fastify 插件里的字段名；2) 自定义返回 message 的 hook 写法；3) 和 fastify 的 reply.code() 怎么配合。给出一段可直接复用的配置代码 + 三处与 express 版本的差异。"
}
```

子 agent 在一个全新的独立 agent 循环中运行：调 webSearch / webFetch 查阅文档，读项目中已安装的类型定义文件，最终写出一份约 250 字的结论和配置代码。子 agent 执行完毕后只把这份结论返回给主 agent——中间过程中 webFetch 取回的大段 HTML、读到的源码片段，全部留在子 agent 自己的消息历史中，不进入主对话。主对话因此保持精简。主 agent 拿到结论后继续推进：把清单第三项标为 completed，第四项切到 in_progress，开始迁移中间件。

Plan Mode 在大动作之前固化一份计划并交给用户审批，它是锚点；todoWrite 在执行阶段让用户随时看到 agent 处于哪一步，它是进度仪表盘；task 把一段上下文密集但与主对话无关的调研工作外包出去，它是资源调度器。一个真正大型的任务可能三者都用上，但小到一两步就能完成的任务三者都不需要，直接执行最快。三者的接力顺序也不是固定的——上面的示例是 Plan Mode → todoWrite → task，但如果任务一开始就有明确的步骤且不需要用户审批，完全可以跳过 Plan Mode 直接从 todoWrite 开始。关键是理解每个机制擅长什么，按场景选用。

## 22.3 跳过 Plan Mode 直接建清单的代价

新手常有这样的想法：让模型直接调 todoWrite 列出所有步骤再按步骤执行即可，何必先走一遍 Plan Mode。问题在于 todoWrite 没有用户审批的关卡。模型可能在拆分阶段就犯错——例如把「迁移路由」拆成「改 routes.ts」一项，但实际上路由分散在五个文件，需要修改的远不止一处。模型按这份有误的拆分继续推进，等用户发现时已经修改了大量文件，回退成本很高。Plan Mode 强制「先停下来等审批」，让用户在大动作之前确认模型对任务的理解是否正确、拆分是否合理。因此，对于影响范围小的任务（改一个函数、加一段配置），直接用 todoWrite 是合理的选择；而对于跨多文件、影响范围大的重构任务，先走 Plan Mode 写计划、通过审批后再翻译成 todoWrite 清单更稳妥。

## 22.4 task 不是 todoWrite 的进阶版

新手看到 task 能「把任务拆出去」，觉得它比 todoWrite 更强大，倾向于把所有任务都用 task 处理。然而 Ch.19 已经详细讨论过，子 agent 的隔离性既是优势也是限制——独立的消息历史意味着看不到主对话的上下文，只返回最终消息意味着中途无法向用户同步进度，禁止递归委派意味着无法继续拆分子任务。当一段工作需要频繁参照主对话里的上下文，或者需要中途向用户汇报进度时，这些限制就变成了障碍。

因此 task 适合边界清晰、与主对话无强耦合的工作——调研、审查、探索、独立的局部实现——而不适合需要边做边和主对话同步的执行类任务。执行类任务应该用 todoWrite 在主循环里跟踪，每完成一步就更新清单，用户可以随时看到进度。选择的判断标准可以归结为一个问题：中间过程是否需要进入主对话历史？如果需要（每一步的修改都应被记录在主对话中以便用户审阅），使用 todoWrite；如果不需要（过程中产生的大量中间数据对主对话来说只是噪音），使用 task 将其外包给子 agent。

## 22.5 Plan Mode 和 todoWrite 是前后接力而非上下替代

另一个常见误解是把 Plan Mode 想象成「带审批的 todoWrite」——两者都涉及步骤拆分，看起来只是有没有审批的区别。但 22.1 的对比表已经显示，两者管理的维度完全不同：一个约束行为，一个跟踪进度。更直接的证据是——在 Plan Mode 下，模型实际上不会调 todoWrite。原因不是技术上禁止（todoWrite 并未被从工具集中移除），而是覆盖段把每轮的合法收尾方式锁定为 `askUser` 和 `exitPlanMode` 两种，todoWrite 在这种约束下没有用武之地。规划阶段的步骤拆分写在 plan 文件中——持久化到磁盘、可供用户审批——而不是存放在内存清单里。`exitPlanMode` 审批通过、覆盖段不再生效后，模型才开始用 todoWrite 跟踪执行进度。两者在工作流中是前后接力的关系，时间上不重叠。

## 22.6 按场景而非按「高级程度」选工具

实际面对一个任务时，决策不是「哪个更高级就用哪个」，而是按任务的具体特征选择合适的机制。前面三节分别讨论了跳过 Plan Mode、滥用 task、混淆 Plan Mode 与 todoWrite 的代价，本节将分析汇总为一张决策表。关键的考量维度有三个：任务规模是否需要用户审批（决定是否走 Plan Mode）、执行过程是否需要给用户可见的进度反馈（决定是否用 todoWrite）、是否存在与主对话无关的独立调研段落（决定是否派 task 子 agent）。

| 情况 | 合适的机制 |
| --- | --- |
| 任务规模大、跨多文件、用户希望先审阅计划 | Plan Mode |
| 任务有明显的多步骤、需要给用户实时进度 | todoWrite |
| 任务里有一段独立的调研或审查可以外包 | task |
| 大型任务（影响多文件、有调研段落、需要审批） | 三者结合：Plan Mode → todoWrite → 中间穿插 task |
| 一两步就能完成的小任务 | 三个都不需要，直接执行 |

最常见的失误是对所有任务都用同一个机制——要么全部 todoWrite 不走 Plan Mode（失去了审批关卡），要么全部 task 不用 todoWrite（失去了主对话里的进度可见性）。三者各有擅长的维度，按场景的特征来选择比按「哪个更高级」来选择稳妥得多。前面反复提到的判断标准——「中间过程是否需要进入主对话历史」——是最实用的选择依据：需要的用 todoWrite，不需要的用 task，而复杂的任务让用户先审批再执行的场景用 Plan Mode。

## 22.7 小结

三者管理的维度不同——Plan Mode 约束行为、todoWrite 跟踪进度、task 隔离上下文——因此不存在互相替代的关系。选择时的核心判断标准是「中间过程是否需要进入主对话历史」：需要的用 todoWrite，不需要的用 task，而执行任务之前需要先停下来让用户审批的场景用 Plan Mode。
