# 第 9 章 多供应商支持：一个注册表管八家模型

上一章实现了 Agent Loop 的生产级循环——模型调用工具、客户端执行、结果回传、再发下一轮。但那里始终只用了一家供应商的模型。现实中，不同供应商在代码生成、长上下文、推理能力和价格上差异显著，开发者往往需要在不同任务之间切换模型。支持多家供应商不只是「多配几个 API Key」这么简单——还涉及模型标识符（Model ID）的统一格式、供应商注册表（Provider Registry）的抽象设计、启动时的自动探测与默认选择、运行时的实时切换与配置持久化，以及不同供应商之间的能力差异屏蔽。本章将分为如下几个部分进行介绍。

- 9.1 节列出 X-Code CLI 内置的 8 家供应商及其各自的定位。
- 9.2 节讲供应商注册表模式——为什么用一个统一的注册表而不是为每家写适配器。
- 9.3 节讨论启动时的供应商探测——可用性扫描和默认模型选择是两件不同的事。
- 9.4 节介绍 `/model` 命令的运行时切换机制。
- 9.5 节讲 OpenAI 兼容自定义端点——如何接入内置 8 家以外的供应商。
- 9.6 节说明供应商级别的能力差异表及其设计取舍。
- 9.7 节给出本章小结。

## 9.1 八家内置供应商

X-Code CLI 内置 8 家主流模型供应商，如表 9-1 所示。

| 供应商    | 默认模型          | 环境变量                       |
| --------- | ----------------- | ------------------------------ |
| Anthropic | claude-sonnet-4-6 | `ANTHROPIC_API_KEY`            |
| OpenAI    | gpt-4.1           | `OPENAI_API_KEY`               |
| Google    | gemini-2.5-pro    | `GOOGLE_GENERATIVE_AI_API_KEY` |
| xAI       | grok-3            | `XAI_API_KEY`                  |
| DeepSeek  | deepseek-v4-flash | `DEEPSEEK_API_KEY`             |
| Alibaba   | qwen-max          | `ALIBABA_API_KEY`              |
| Zhipu     | glm-4-plus        | `ZHIPU_API_KEY`                |
| Moonshot  | kimi-k2.5         | `MOONSHOT_API_KEY`             |

> 表 9-1 X-Code CLI 内置的 8 家供应商

每家供应商通过对应的 AI SDK 适配包（`@ai-sdk/anthropic`、`@ai-sdk/openai` 等）接入，唯一的例外是智谱——官方未发布 AI SDK 适配包，因此使用社区维护的 `zhipu-ai-provider` 包。所有供应商的 API Key 均通过环境变量传入，CLI 不会将 Key 写入任何配置文件。这是一个有意的设计决定：密钥仅存在于进程的环境变量中，避免了密钥明文写入磁盘带来的泄露风险。代价是每次新开终端都需要确保环境变量已经配置好——Ch.06 第 6.3 节已经讨论过环境变量和 `.env` 文件两种配置方式的适用场景。


## 9.2 供应商注册表模式

> 源码：`packages/core/src/providers/registry.ts`

如果为 8 家供应商各写一个适配器类，各自实现创建模型、发送请求、解析响应的逻辑。这看起来不错，不过有个问题——8 家供应商的请求流程本质上是相同的（都是调用 `streamText`），差异仅在于模型标识符和少量供应商特有参数。AI SDK 提供的供应商注册表（Provider Registry）正是为了消除这种重复而设计的：把所有供应商注册到同一个对象上，通过统一的 `provider:model` 格式的标识符来获取模型实例。以下是注册代码的核心结构。

<!-- check:ignore=punctuation -->
```ts
import { createProviderRegistry } from 'ai'
import { createAnthropic } from '@ai-sdk/anthropic'
import { createOpenAI } from '@ai-sdk/openai'
// ...

export function createModelRegistry() {
  const opts = getProviderOptions()
  const providers: Record<string, any> = {}

  if (opts.anthropic) providers.anthropic = createAnthropic({ fetch: permanentErrorFetch })
  if (opts.openai) providers.openai = createOpenAI({ fetch: permanentErrorFetch })
  if (opts.deepseek) providers.deepseek = createDeepSeek({ fetch: deepseekReasoningFetch })
  // ... 其余供应商同理

  return createProviderRegistry(providers)
}

// 使用：统一的 model id 格式 `provider:model`
const model = registry.languageModel('anthropic:claude-sonnet-4-6')
```

注册完成后，上层代码只需要一个字符串就能获取任意供应商的模型实例。切换供应商从「重建适配器对象」变成了「替换一个字符串」——Agent Loop 完全不需要知道当前用的是哪家供应商，它只看到一个统一的模型接口。这种设计还带来了一个附带好处：供应商特有的参数（如 Anthropic 的 `cache_control`、支持推理的模型的 `thinking` 配置）通过 `providerOptions` 透传，不需要在注册表的抽象层上添加特殊入口。每家供应商的特殊能力在调用 `streamText` 时按需拼装，注册表本身保持简洁。

## 9.3 启动时的供应商探测

> 源码：`packages/core/src/config/index.ts`

假设读者同时配置了 DeepSeek 和 Anthropic 两个 API Key。CLI 启动时需要做两件事：列出这两家供应商供 `/model` 命令的选择列表使用，以及从中挑一个作为默认模型。

### 9.3.1 可用性扫描

启动时的第一步是扫描环境变量，找出哪些供应商已经配置了 API Key。

```ts
const ENV_MAP: Record<string, string> = {
  anthropic: 'ANTHROPIC_API_KEY',
  openai: 'OPENAI_API_KEY',
  google: 'GOOGLE_GENERATIVE_AI_API_KEY',
  xai: 'XAI_API_KEY',
  deepseek: 'DEEPSEEK_API_KEY',
  alibaba: 'ALIBABA_API_KEY',
  zhipu: 'ZHIPU_API_KEY',
  moonshotai: 'MOONSHOT_API_KEY',
}

export function getAvailableProviders(): string[] {
  const providers = Object.keys(ENV_MAP).filter((p) => getApiKey(p))
  if (process.env.OPENAI_COMPATIBLE_API_KEY && process.env.OPENAI_COMPATIBLE_BASE_URL) {
    providers.push('custom')
  }
  return providers
}
```

返回的列表按映射表的插入顺序排列（anthropic → openai → google → …）。如果同时配置了 OpenAI 兼容自定义端点所需的两个环境变量（API Key 和 Base URL），则额外追加一个 `'custom'` 条目。

### 9.3.2 默认模型选择

有了可用供应商列表之后，下一步是确定默认使用哪个模型。如果用户没有通过任何方式显式指定模型，CLI 按以下四级优先级依次查找。

（1）命令行参数 `--model` 的显式指定。
（2）配置文件 `~/.x-code/config.json` 中通过 `/model` 命令写入的历史选择。
（3）环境变量 `X_CODE_MODEL` 的值。
（4）按供应商探测顺序表，选取第一个环境中存在 API Key 的供应商的默认模型。

```ts
export const PROVIDER_DETECTION_ORDER = [
  { envKey: 'DEEPSEEK_API_KEY', defaultModel: 'deepseek:deepseek-v4-flash' },
  { envKey: 'ANTHROPIC_API_KEY', defaultModel: 'anthropic:claude-sonnet-4-6' },
  { envKey: 'OPENAI_API_KEY', defaultModel: 'openai:gpt-4.1' },
  { envKey: 'ALIBABA_API_KEY', defaultModel: 'alibaba:qwen-max' },
  { envKey: 'GOOGLE_GENERATIVE_AI_API_KEY', defaultModel: 'google:gemini-2.5-pro' },
  { envKey: 'XAI_API_KEY', defaultModel: 'xai:grok-3' },
  { envKey: 'ZHIPU_API_KEY', defaultModel: 'zhipu:glm-4-plus' },
  { envKey: 'MOONSHOT_API_KEY', defaultModel: 'moonshotai:kimi-k2.5' },
] as const
```



### 9.3.3 未配置任何供应商时的引导

如果启动时扫描发现没有任何供应商的 API Key，CLI 不会只输出一行错误信息让开发者自己查文档，而是根据当前操作系统和 Shell 类型给出具体的配置命令。

```text
Error: No API key found.

Set at least one provider API key via environment variable:

  DEEPSEEK_API_KEY                 https://platform.deepseek.com
  ANTHROPIC_API_KEY                https://console.anthropic.com
  OPENAI_API_KEY                   https://platform.openai.com
  ...
  OPENAI_COMPATIBLE_API_KEY        (custom OpenAI-compatible endpoint)

Detected shell: bash
Persist it so you do not need to set it every session:

  echo 'export ANTHROPIC_API_KEY=sk-ant-...' >> ~/.bashrc && source ~/.bashrc
```

输出分为三段：第一段按 `PROVIDER_DETECTION_ORDER` 逐行列出每家供应商的环境变量名和密钥注册地址；第二段检测当前 Shell 类型（复用 Ch.06 第 6.4 节介绍过的 Shell 侦测逻辑，覆盖 PowerShell、cmd、bash、zsh、fish、sh 六种类型），给出一条与当前 Shell 匹配的持久化命令示例；最后提示也可以使用项目本地的 `.env` 文件。这样开发者无需翻阅文档，直接复制粘贴终端输出即可完成配置。

## 9.4 运行时切换：`/model` 命令

> 源码：`packages/cli/src/ui/components/App.tsx`

供应商探测解决的是启动时的默认选择问题。在会话进行过程中，开发者可能发现当前模型在某类任务上表现不佳，需要临时切换到另一家供应商。`/model` 命令提供了两种使用方式：不带参数时弹出交互式选择器，列出所有已配置 API Key 的供应商及其可用模型；带参数时直接切换，例如 `/model sonnet` 会匹配到 `anthropic:claude-sonnet-4-6`。以下是选择器的界面示例。

```text
? Select a model:
> anthropic:claude-sonnet-4-6 (current)
  anthropic:claude-opus-4-7
  openai:gpt-4.1
  deepseek:deepseek-v4-flash
  ...
```

切换模型时会触发两个副作用。第一，新的模型选择会写入配置文件 `~/.x-code/config.json`，确保下次启动时仍然使用该模型——这对应 9.3.2 节中默认模型选择的第二级优先级。第二，切换立即生效，下一条用户消息发出时就会使用新模型，不需要重启 CLI。实现这一点的关键是模型实例通过引用持有，切换时只需要更新引用指向的对象，而不需要重建整个组件树。这种设计使得模型切换对用户来说是零感知的——除了模型名称变了之外，整个交互界面和会话状态保持不变。

## 9.5 OpenAI 兼容自定义端点

> 源码：`packages/core/src/providers/registry.ts`

内置的 8 家供应商覆盖了主流选择，但开发者可能还需要接入其他供应商——豆包、文心一言、通过 Ollama 运行的本地模型，或者通过 vLLM 部署的自有模型。这些供应商大多兼容 OpenAI 的 API 格式，因此 X-Code CLI 通过 AI SDK 的 `@ai-sdk/openai-compatible` 包提供了一个通用的接入通道。开发者只需要配置两个环境变量——API Key 和 Base URL——就能将任意兼容端点注册为 `custom` 供应商。

```bash
export OPENAI_COMPATIBLE_API_KEY=...
export OPENAI_COMPATIBLE_BASE_URL=https://my-endpoint.com/v1
xc -m custom:my-model
```

注册逻辑在 9.2 节展示的 `createModelRegistry` 函数中执行：如果这两个环境变量同时存在，就创建一个 OpenAI 兼容的供应商实例并注册到 `custom` 名下。

```ts
if (opts.custom.apiKey && opts.custom.baseURL) {
  providers.custom = createOpenAICompatible({
    name: 'custom',
    apiKey: opts.custom.apiKey,
    baseURL: opts.custom.baseURL,
    fetch: permanentErrorFetch,
  })
}
```



## 9.6 供应商能力差异表

> 源码：`packages/core/src/providers/capabilities.ts`

不同供应商对视觉（Image）、PDF 和文件 API（Files API）的支持各不相同。X-Code CLI 在源码中维护了一份静态的能力差异表，运行时的附件处理管线根据当前供应商的能力声明来决定走原生通道还是降级方案（详见 Ch.35）。

```ts
const CAPS: Record<string, ProviderCapabilities> = {
  anthropic: { image: true, pdf: true, filesApi: true },
  google: { image: true, pdf: true, filesApi: true },
  deepseek: { image: false, pdf: false, filesApi: false },
  custom: { image: false, pdf: false, filesApi: false }, // 自定义端点保守默认
  // ...
}
```

这份能力表是供应商级别的粗粒度声明，而非模型级别的精确映射。选择供应商级别的原因是维护成本：每家供应商的模型列表经常更新，逐模型维护能力声明会带来持续的同步负担。供应商级别的粒度在绝大多数场景下足够准确——不支持视觉的 DeepSeek 和自定义端点采用保守的全部标记为不支持的策略，不会误发图片请求；支持视觉的供应商即使偶尔覆盖了一个不支持图片的模型变体，API 也会返回明确的错误信息，不会产生静默的错误行为。这种保守标记、避免误发请求的策略，与 9.5 节中自定义端点的保守默认值是同一种设计思路。

## 9.7 小结

本章讨论了 X-Code CLI 如何在一个统一的架构下支持 8 家内置供应商和 1 个 OpenAI 兼容自定义端点。核心设计是 AI SDK 的供应商注册表模式——所有供应商注册到同一个对象上，通过 `provider:model` 格式的标识符获取模型实例，切换供应商只需要替换一个字符串，Agent Loop 完全不需要感知当前使用的是哪家。启动时的供应商探测分为两个独立步骤：可用性扫描按映射表顺序返回已配置的供应商列表，供 `/model` 命令的界面渲染使用；默认模型选择按另一份优先级顺序查找，两份顺序分开维护避免了显示逻辑和选择逻辑的耦合。运行时的模型切换通过 `/model` 命令实现，切换立即生效且会持久化到配置文件。自定义端点通过 `@ai-sdk/openai-compatible` 包接入，采用保守的能力默认值。供应商之间的能力差异通过一份静态的供应商级能力表管理，粒度选择供应商级而非模型级是在维护成本和精确度之间的权衡。下一章将讨论流式 chunk 处理——模型的响应不是一次性返回的完整文本，而是以流（Stream）的形式逐片段（Chunk）到达，Agent Loop 需要实时解析这些片段并驱动终端界面的增量渲染。
