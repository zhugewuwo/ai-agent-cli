B.2 架构概览

两个核心包 cli → core 构成单向依赖，详见 Ch.04。

渲染层面，Ink 动态区始终为空，App 组件只返回单个 <ChatInput />，没有 Ink 子树。所有 UI 元素（输入框、进度指示器、对话框、终端历史区提交）都由 <ChatInput> 自己通过 cell 级别 diff + process.stdout.write 渲染。Yoga 抖动溯源与 cell buffer 实现详见 Ch.23 和 Ch.24。

B.4 具体示例

用户输入：「帮忙分析一下项目产品功能以及优化点」

完整执行流程


1. 用户在终端输入 "帮忙分析一下项目产品功能以及优化点"，按 Enter

2. ChatInput 组件
   └─ onSubmit("帮忙分析一下项目产品功能以及优化点")

3. App.handleSubmit()
   └─ 非 / 开头，走普通提交路径
   └─ submit("帮忙分析一下项目产品功能以及优化点")

4. useAgent.submit()
   ├─ initialize() (首次)
   │ └─ 加载 AutoMemory (用户级 + 项目，驱逐 90 天前条目)
   │
   ├─ setState
   │ → messages 追加用户消息
   │ → isLoading = true
   │
   │ [终端显示]
   │ > 帮忙分析一下项目产品功能以及优化点
   │ ⠋ Thinking...
   │
   ├─ 构建 callbacks
   └─ agentLoop("帮忙分析一下项目产品功能以及优化点", model, options, callbacks)

5. agentLoop() — 第一轮
   ├─ messages: [{ role: 'user', content: '帮忙分析一下项目产品功能以及优化点' }]
   │
   ├─ buildKnowledgeContext()
   │ → 拼接用户级/项目 AGENTS.md chain、auto memory、local preferences
   │
   ├─ buildSystemPrompt()
   │ → 完整 system prompt (约 2000-3000 tokens)
   │ → 包含: 身份、工具列表、规则、环境信息、知识上下文
   │
   ├─ streamText({ model, system, messages, tools })
   │ → API 请求发送到 AI Provider (如 Anthropic)
   │
   ├─ AI 决定先了解项目结构，返回 tool-calls:
   │ ├─ tool-call: glob({ pattern: "**/\*.{ts,tsx,json}" })
   │ └─ tool-call: readFile({ filePath: "package.json" })
   │
   │ [终端显示 —— 只读工具(glob/readFile/listDir/grep)走 read-group collapser，
   │  ChatInput frame 上**不**显示逐 tool 的 ⠋ Running… live 行;只显示
   │  spinner 文案翻成 "Reading…":
   │ ⠋ Reading… (3s · esc to interrupt)
   │
   ├─ finishReason = 'tool-calls'
   ├─ processToolCalls()
   │ ├─ glob → 自动执行 (always-allow) → 返回文件列表
   │ └─ readFile → 自动执行 (always-allow) → 返回 package.json 内容
   │
   │ [工具完成后,read-group collapser 暂存,**不**立刻 commit。
   │  等链条结束(出现非只读工具 / text-delta / turn 结束)再一次性
   │  flush 成一行摘要 —— 见下面"轮 3 末尾"的合并形式。]
   │
   └─ continue (进入下一轮)

6. agentLoop() — 第二轮
   ├─ messages 现在包含: user + assistant(tool-calls) + tool-results
   │
   ├─ streamText() → AI 继续分析
   │
   ├─ AI 可能再次调用工具读取更多文件:
   │ ├─ readFile({ filePath: "packages/core/src/index.ts" })
   │ ├─ readFile({ filePath: "packages/cli/src/ui/components/App.tsx" })
   │ └─ listDir({ path: "packages/core/src/tools" })
   │
   │ [终端显示 —— 仍然在只读链中,collapser 继续累积,frame 仍只
   │  显示 "Reading…" spinner,不逐 tool 出 live 行]
   │
   └─ continue

7. agentLoop() — 第三轮 (可能更多轮)
   ├─ AI 已获得足够信息，开始生成分析报告
   │
   ├─ streamText() → AI 返回纯文本分析 (finishReason = 'stop')

会话内动态刷新：refreshPluginContributions 单一入口

启动序列把 plugin、skill、command、MCP、hook 都装在了对应 registry 里。但 registry 是一次性加载、会话内冻结的。如果会话期间用户装了新插件、改了订阅或修改了 user-config，要让 CLI 看见新状态该怎么处理？

X-Code CLI 不做 fs.watch 自动检测，而是要求用户显式执行 /plugin refresh（详见 Ch.39 决定四）。这个命令背后是 refreshPluginContributions() 一个单一入口，五件事按固定顺序执行：

PluginRefreshTargets 字段:
  pluginRegistry: PluginRegistry        // 必填 — 主 registry, 永远需要重 reload
  skillRegistry?: SkillRegistry         // 可选 — 不传则跳过 skill 折回
  subAgentRegistry?: SubAgentRegistry   // 可选 — 不传则跳过 sub-agent 折回
  commandRegistry?: CommandRegistry     // 可选 — 不传则跳过 command 折回
  hookBus?: HookBus                     // 可选 — 不传则跳过 hook bus 折回
  mcpRegistry?: McpRegistry             // 可选, 必须跟 askUser 一起传才会触发 MCP 重启
  askUser?: LoadOptions['askUser']      // 可选, 跟 mcpRegistry 配对
  cwd?: string                          // 可选, 默认 process.cwd()

refreshPluginContributions(targets):
  ├─ loadAllPlugins({ cwd })
  │    重读 installed_plugins.json + 项目级目录 + enabledPlugins 状态
  ├─ targets.pluginRegistry.reload(load.registry.listAll(), [...loadErrors()])
  │    替换主 registry 内的插件列表, 保留对象身份(所有持有引用的下游继续有效)
  ├─ buildPluginIntegration(load)
  │    重新算出 agentsDirs / skillsDirs / commandsDirs / mcpServers / hookBus
  ├─ 折回四个子 registry — 都用 reload-in-place 保留对象身份:
  │    if (targets.skillRegistry)    reloadSkillRegistry(..., { extraDirs })
  │    if (targets.subAgentRegistry) reloadSubAgentRegistry(..., { extraDirs })
  │    if (targets.commandRegistry)  reloadCommandRegistry(..., { extraDirs })
  │    if (targets.hookBus)          targets.hookBus.replaceRegistry(integration.hookRegistry)
  └─ 重启 MCP 服务器 (条件: mcpRegistry + askUser 都传了才走):
       loadMergedConfigsFromDisk({extraServers}) →
       targets.mcpRegistry.restartAll(merged.configs)

每个子 registry 都是可选的，--no-plugins 启动时上层不传 skillRegistry / subAgentRegistry，refresh 时这几步自动跳过。MCP 重启条件更特殊：必须 mcpRegistry 和 askUser 都传才执行（askUser 用于处理项目级 MCP 信任对话）。

CLI 端 handleRefreshPlugins 还做两件事：调 invalidateSystemPromptCache() 作废 system prompt cache（同 /skill refresh 第 1 步），输出文案告诉用户下一条消息会 cache miss 一次。

选择单一入口的原因在于五件事必须按上述顺序执行：先重扫拿到新插件列表，再计算 integration 拿到 extraDirs，再折进各子 registry。任何一步顺序错位都会让某项扩展不可见。把这条流程封装在一个函数里，CLI 的两个调用点（/plugin refresh slash 命令和 /mcp refresh 单独执行时也走类似路径）就不会因为漏写一步导致 silent data loss。

注：activeToolCalls 是数组而不是单值，因为 AI SDK 在一个 turn 里可能并行发出多个 tool call（tool-call A，tool-call B，tool-result A，tool-result B）。每个 ActiveToolCall 含可选 progress 字段（工具内部通过 reportProgress(toolCallId, msg) 流式上报“当前在做什么”，取代默认的 Running… 占位）和可选 subToolHistory（task 工具委派子 agent 时把子 agent 的 tool-call 汇成一行 progress 反馈给父级）。

注：flushBuffer()（刷出流式文本）和 setState（push 进 activeToolCalls）在同一同步 tick 完成，靠 React 18 自动批处理折叠成一帧。快工具会闪一下 “Running…” 行（~1 帧），慢工具（WebSearch / shell / 网络）的 text→tool-call 过渡没有可见闪烁。

注：没有独立的 streamingText state。useStreamBuffer(appendMessage) 每次 delta 进 bufferRef，在安全 markdown 边界（table/code fence 不被切断）切片，150ms 合并窗口内的多个切片合并成一次 appendMessage。每次提交直接落进 messages，ChatInput useEffect 把它经 writeMessageToStdout 写到终端历史区。不在 cell buffer 里做半截 markdown 预览，避免提交前后的视觉跳动。详见 B.10 节的「流式文本累积策略」。

B.7 阶段三：用户输入处理

ChatInput 自己挂 stdin 监听（Ink 自带的 useInput 不认 bracketed paste 标记，大粘贴会被拆成多个 chunk 逐字处理）。stdin 三层分流：

  1. bracketed paste 快路径：\x1b[200~ / \x1b[201~ 包裹的整块走 onPaste
  2. 30ms 防抖托底：老终端（cmd.exe）不支持标记时，依赖时间窗口区分逐键和粘贴突发
  3. 单段大小判定：防抖刷出时内容 ≥ 32 字符或含 \n 视为粘贴，否则视为文本

paste 入口统一做 \r\n?/g → \n 归一化（裸 \r 在终端里会被当 carriage return 覆盖之前的字符）。完整实现 + 阈值常量论证详见 [Ch.24。

          • 出现非只读工具(edit / write / shell / task / askUser ...)
          • 出现 text-delta(模型开始打文本)
          • turn 结束(finishReason='stop' / 'error' / 'aborted')
          • 用户 abort
        flush 动作:
          formatReadGroupSummary(buffered) →
            label  = "Read 3 files, searched for 1 pattern"
                     (按 readCount/grepCount/globCount/lsCount 分组,
                      首句首字大写,逗号连接)
            detail = "(foo.ts, bar.ts, +1 more)"  ← 只在 readPaths 非空时显示,
                     最多列 3 个 basename,超出 → "+N more"
          作为一行写进 scrollback,样式与单工具 ●/⎿ 行对齐(粗体 label +
          蓝紫色 detail)

期间 spinner 文案靠 AgentState.bufferingReads 翻:
  - 进入只读工具链          → bufferingReads = true  → "Reading…"
  - 文本流 / 写入 / 结束    → bufferingReads = false → "Thinking…"

为什么这么做:
  - 多数 readFile / glob 在 1-5ms 完成,显示 live 行会有"出现 → 立刻消失"
    的闪烁(commit 节流 50ms 比工具完成还慢)
  - 长链条上"Reading…"持续显示的体验比"逐 tool 短暂出现后立即消失"清晰
  - 慢 read 会丢失 per-file 可见性,但慢 read 在链中是少数情形
  - 链尾摘要列出每个 basename,用户仍能看到"读了什么"

权限系统详解

三级 PermissionLevel（always-allow / ask / deny） + Shell 智能分级（splitShellCommands / isReadOnly / isDestructive，混合命令 → ask） + Trust Mode（--trust 跳过所有权限确认，含 deny 级）。详见 Ch.29；对话框 UI（edit 走结构化 diff + (a)ccept-edits 切 permissionMode）详见 Ch.28。

Plan Mode 约束机制

Plan 模式下「模型只能调读 + enterPlanMode / exitPlanMode / todoWrite / task（只读子 agent）」的约束由 system prompt overlay 强制（system-prompt.ts 里的 plan-mode overlay，permissionMode === 'plan' 时拼到 base prompt 末尾），模型被 prompt-level hard rule 禁止调写工具。如果模型不遵守仍 emit writeFile / edit / shell tool-call，代码里没有专门的 isWriteTool 拦截将其替换成合成 error tool-result，而是仍走普通 permission 流程：default 模式下用户在对话框拒绝即可；acceptEdits 模式（用户 exitPlanMode 批准后翻到这档）则写工具自动放行，这是设计意图。

几个设计要点：

  • write 函数是 (data) => process.stdout.write(data)，直接进终端 stdout。但实际写入路径是先把终端历史区内容收到一个字符串里，跟 frame 写入合并成一次 process.stdout.write，整个提交由外层 BSU/ESU 包成一帧原子提交，杜绝撕裂。
  • 提交不做每帧 eraseRegion()，而是走「行内插入」路径：\x1b[startRow;1H\x1b[J 只擦旧 frame 区，然后写新的终端历史区内容，frame 在新位置重绘，避开了「擦了再画」的双重写入。
  • 不发 \x1b7（DECSC），避免跟 fork 内 log-update 抢光标寄存器；采用挂载时一次 ?25l 隐藏光标 + 按行绝对定位的方式替代。
  • frame 是浮动定位的：根据 freeBlanksAboveFrameRef，frame 上移贴到内容下方；内容撑满屏幕后才钉底。
  • 跨终端的工程细节（终端能力差异、副作用写入、节奏失配三类根因，对应光标可见性反复切换、空 BSU/ESU 包装、150ms 提交合并、进度指示器字符选择等）详见 Ch.25。
  • 跨平台 Unicode glyph 降级方面，老式 ConHost 缺装饰字符时由 cli/src/ui/terminal-glyphs.ts 单点降级（●→*、❯→>、⎿→|、spinner 走 ASCII palindrome）。检测逻辑与完整降级表详见 Ch.25。

B.11 阶段七：退出与清理

正常退出流程


/exit 命令 或 Ctrl+C 双击
│
├─ 触发源
│    ├─ /exit       → App handleSubmit → cleanup() (await) → exit()（Ink unmount）
│    ├─ Ctrl+C 1 次 → App handleCtrlC：
│    │   ├─ isLoading → useAgent.abort()（取消当前 turn，frame 仍在）
│    │   └─ 设 notice "Press Ctrl+C again to exit"，arm 2 秒窗口
│    │   （此时不退出 —— 用户有 2 秒反悔时间）
│    └─ Ctrl+C 2 次（在 2 秒窗口内）→ Ink exit() → unmount
│
├─ Ink unmount → waitUntilExit() 在 main() 里返回
│
└─ gracefulShutdown(0) (index.ts)
     ├─ cleanup().catch(() => undefined)   // fire-and-forget
     │    └─ saveSession(loopState, model)
     │         └─ flushPendingMessages(state)
     │             把 state.messages.slice(persistedMessageCount) 增量
     │             append 到 <slug>-<sessionId>.jsonl。最后一轮的内容
     │             （/exit 路径上一般已经被 agentLoop 末尾的 flush 写入
     │             过；这里是为 abort / 异常退出容错）。
     │
     │   注：saveSession 只 flush jsonl,不生成 LLM summary、不写
     │   latest.json / <id>.json。摘要以 compact-boundary 行嵌在 jsonl
     │   里（只在压缩时生成），usage 以 meta.usage 行嵌在 jsonl 里
     │   （每 turn 一次）。
     │
     │   cleanup 不被 await —— 进程可能在 flush 写入完成前就 exit。
     │   但 flushPendingMessages 是同步组装 + 单次 fs.appendFile，正常情况
     │   <10ms 完成；极端情况下丢失最后几条 message 是可接受代价。
     │   每轮 turn 顶端的 flush 已经把绝大部分内容写入了。
     │
     ├─ resetTerminal()
     │   → \x1b[0m SGR 重置 + \x1b[?2004l bracketed paste off
     │   + \x1b[?25h 光标显示 + \x1b[?1049l 退出 alt screen + \r\n + setRawMode(false)
     │

     │     Resume this session: xc --resume <slug-id>

Ctrl+C 处理（双层）


Layer 1 — App.handleCtrlC (主路径，cli/src/ui/components/App.tsx)
├─ ctrlCArmedAtRef = 0  默认值（未 arm）
├─ ctrlCArmWindowMs = 2000
│
├─ 第 1 次按下:
│    ├─ now - ctrlCArmedAtRef >= 2000 → 未在窗口内
│    ├─ ctrlCArmedAtRef = now（arm 2 秒窗口）
│    ├─ if state.isLoading → abort()（取消当前 turn）
│    └─ setNotice("Press Ctrl+C again to exit")
│       2 秒后 useEffect 自动清空 notice
│
└─ 第 2 次按下（2 秒内）:
     └─ now - ctrlCArmedAtRef < 2000 → 在窗口内 → exit()
        → Ink unmount → waitUntilExit → gracefulShutdown(0)

Layer 2 — process.on('SIGINT') (cli/src/index.ts) — 安全网
├─ sigintCount++ + process.exitCode = 0
├─ Layer 1 在 raw mode 下消化绝大多数 Ctrl+C；这里只在
│   Ink 已 unmount 后或 raw mode 已关时才生效
└─ sigintCount >= 2 → resetTerminal + printResumeHint + process.exit(0)
   极端场景: Ink unmount 卡住时跳过剩余的 fire-and-forget cleanup 强退

两次 Ctrl+C 退出码都是 0。区别在于第 1 层的「双击」是 2 秒内用户主动选择退出（取消在第 1 次就发生），第 2 层是托底，即使 Ink 卡死也能让终端恢复可用。

B.14 小结

从 xc 命令启动到用户输入、从 AI 流式回复到工具调用、从终端渲染到退出清理，七个阶段各自对应一组明确的文件入口，B.13 节的文件索引表按阶段做了汇总。

贯穿这七个阶段的有三大共享数据结构：Core 层的 LoopState（messages、tokenUsage、sessionId、systemPromptCache、permissionMode、taskSlug、persistedMessageCount、checkpoints 等 18 个字段，生命周期等于整个 CLI 会话）、React 侧的 AgentState（messages、activeToolCalls、permissionQueue、pendingQuestion、usage、bufferingReads 等，驱动 UI 渲染）、以及 SLASH_COMMANDS（/help、/model、/plan、/clear、/compact、/resume、/review、/memory 等，在 handleSubmit 里分发）。理解这三套结构的分工与同步机制，是读者排查任何具体环节的前提。

在持久化方面，每个会话对应一个 .x-code/sessions/<slug>-<sessionId>.jsonl 文件，六种 entry 类型（meta.header、msg、meta.usage、meta.compact-boundary、checkpoint、meta.interrupted）的写入分散在六个 fire-and-forget 函数里，不阻塞主循环。/resume、/usage-history、-c、-r 等恢复与查询操作都从同一个 jsonl 文件取数据。在渲染方面，所有 UI 元素只走 ChatInput cell buffer 一条路径，Ink 动态区始终为空，外层用 DEC 2026 BSU/ESU 做原子刷新。在中断方面，一条 abortSignal 从 useAgent.abort 一路传递到 agentLoop → streamText → execa，中断时 processToolCalls 会给所有未完成的 tool_call 补合成 tool-result，保持 tool-call 与 tool-result 的配对不变量，确保下一次 API 请求不被供应商拒收。
