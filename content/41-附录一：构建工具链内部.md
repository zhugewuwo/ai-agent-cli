## A.1 仓库结构与 pnpm 工作区

X-Code CLI 采用 pnpm 工作区（pnpm Workspace）管理的单仓多包结构，根目录的 `pnpm-workspace.yaml` 只有一行配置：

```yaml
packages:
  - 'packages/*'
```

`packages/` 下有两个包。`@x-code-cli/core` 是核心库，包含 Agent Loop 引擎、工具注册表、权限模型、上下文压缩、MCP 接入等所有与终端 UI 无关的逻辑；`@x-code-cli/cli` 是面向最终用户的命令行入口，负责终端渲染（基于 Ink/React）、命令行参数解析（基于 yargs）、以及调用 core 提供的 API 驱动整个交互流程。cli 通过 `"@x-code-cli/core": "workspace:*"` 声明对 core 的工作区依赖，pnpm 在本地开发时将这个依赖解析为指向 `packages/core` 目录的符号链接（Symbolic Link，一种文件系统快捷方式，指向另一个目录或文件），发布到 npm 时则替换为真实版本号。这种双包拆分的原因在于职责隔离：core 的变更（例如新增一个工具）不应该触发 cli 端 Ink 渲染管线的回归测试，反之亦然。拆开之后两个包各自拥有独立的构建配置、独立的测试集、独立的 `tsconfig.json`，日常开发中只需要关注当前修改所在的那个包。代价是跨包调试时需要先构建 core 再启动 cli，这一点在后面「tsx 开发模式」一节会详细讨论。

根 `package.json` 的关键字段如下：

```jsonc
{
  "private": true,
  "type": "module",
  "packageManager": "pnpm@10.7.1",
  "engines": { "node": ">=20.19.0" }
}
```

`"private": true` 防止根目录被意外发布到 npm；`"type": "module"` 令所有 `.js` 文件默认按 ESM（ECMAScript Modules）解析；`"packageManager"` 锁定 pnpm 版本，配合 Corepack（Node.js 内置的包管理器版本管理工具）使用时能保证团队成员和 CI 环境使用同一版本的包管理器。

## A.2 esbuild 单文件打包

> 源码：`packages/cli/esbuild.config.js`

cli 包的构建工具是 [esbuild](https://esbuild.github.io/)。选择 esbuild 而非传统的「先用 tsc 编译 TypeScript，再用 webpack 或 Rollup 打包」二段式方案，主要基于以下考量。esbuild 用 Go 编写，构建速度在亚秒级完成，比 tsc 加 webpack 的组合快一到两个数量级。esbuild 内置 TypeScript 和 JSX 支持，不需要额外配置 loader 或 plugin。esbuild 的树摇优化（Tree-shaking，即在打包时自动移除未被任何代码引用的模块，以减小产物体积）默认开启，配合 `platform: 'node'` 模式可以正确处理 Node.js 内置模块。整套配置的核心部分不超过 30 行，维护成本低。相比之下，二段式方案需要同时维护 `tsconfig.json`（控制 tsc 输出）和打包器配置（控制模块合并），两套配置之间的 source map 还需要正确串联，调试链路更长，出问题时排查难度也更高。esbuild 的代价是它只做语法转换、不做类型检查，类型安全由单独的 `tsc -b`（即 `pnpm typecheck`）保证，这在后面的「代码质量卡点」一节会进一步说明。

### 关键配置

<!-- check:ignore=code-source -->
```js
// packages/cli/esbuild.config.js (core)
import esbuild from 'esbuild'
import { builtinModules } from 'node:module'

await esbuild.build({
  entryPoints: ['src/index.ts'],
  bundle: true,
  platform: 'node',
  format: 'esm',
  target: 'node20',
  outfile: 'dist/cli.js',
  jsx: 'automatic',
  sourcemap: true,
  plugins: [stubPlugin, entitiesFixPlugin, signalExitFixPlugin],
  define: {
    'process.env.NODE_ENV': '"production"',
  },
  banner: {
    js: '#!/usr/bin/env node\n' + ESM_POLYFILLS,
  },
  external: [
    ...builtinModules,
    ...builtinModules.map((m) => `node:${m}`),
    '@vscode/ripgrep',
  ],
})
```

这段配置的每个字段都有明确的工程理由。`entryPoints` 指向 cli 包的入口文件 `src/index.ts`，esbuild 从这里出发递归解析所有 import，将整棵依赖树打成一个文件。`bundle: true` 开启打包模式，与之对应的 `platform: 'node'` 告诉 esbuild 目标运行环境是 Node.js 而非浏览器，这样 `fs`、`path` 等内置模块会被自动外部化。`format: 'esm'` 令产物使用 ESM 语法（`import`/`export`），`target: 'node20'` 控制语法降级的下限——Node 20 已支持几乎全部 ES2022 特性，因此这里几乎不产生降级代码。`jsx: 'automatic'` 启用 React 17+ 的新 JSX 转换，不需要在每个 `.tsx` 文件顶部手动 `import React`。`sourcemap: true` 生成独立的 `.map` 文件，线上报错时可以从调用栈还原到 TypeScript 源码行号。

`banner.js` 在产物开头注入两段内容。第一段是 shebang 行 `#!/usr/bin/env node`。shebang 是 Unix/macOS 系统的一个约定：当脚本文件的前两个字节是 `#!` 时，操作系统不会把文件内容当作纯文本，而是用 `#!` 后面指定的程序来执行它。`#!/usr/bin/env node` 的含义是「在 `PATH` 环境变量中找到 `node`，用它来执行本文件」。有了这一行，`dist/cli.js` 在 Unix 系统上设置可执行权限（`chmod +x`）后就能直接运行，无需手动输入 `node dist/cli.js`。Windows 不依赖 shebang 机制，npm 安装时会生成 `.cmd` 包装脚本来实现相同效果。

第二段是 ESM 兼容补丁（polyfill，即在不原生支持某特性的环境中用一小段代码模拟出该特性）`ESM_POLYFILLS`，它在文件顶部声明 `__filename`、`__dirname`、`require` 三个变量。原因在于产物是 ESM 格式，ESM 规范中不存在 `__dirname` 和 `require` 这两个 CommonJS（CJS，Node.js 早期的模块规范，使用 `require()` 导入、`module.exports` 导出）时代的全局变量，但打包进来的某些 CJS 依赖在源码中仍然使用了它们。这段补丁通过 `import.meta.url` 加 `fileURLToPath` 派生出 `__filename`，再用 `dirname` 得到 `__dirname`，最后用 `createRequire` 构造出一个可用的 `require` 函数，这样内联进来的 CJS 代码就能在 ESM 产物中正常运行。

### 外部化策略

`external` 数组决定哪些模块不被打进产物。Node.js 内置模块（`builtinModules` 及其 `node:` 前缀变体）显然不应该打包，因为它们在运行时由 Node.js 本身提供。npm 依赖中唯一被外部化的是 `@vscode/ripgrep`，原因在于这个包的核心是一个预编译的 `rg`（ripgrep）二进制文件，esbuild 无法将二进制文件打进 JavaScript 包。用户执行 `npm install -g @x-code-cli/cli` 时，`@vscode/ripgrep` 的 `postinstall` 脚本（npm 在包安装完成后自动执行的生命周期钩子）会自动下载当前平台对应的 `rg` 二进制，放到 `node_modules/@vscode/ripgrep/bin/` 下，这个过程必须在安装阶段完成，不能被 esbuild 提前内联。

除此之外的所有 npm 依赖（包括 core 包自身引入的 `mammoth`、`xlsx`、`officeparser`、`tesseract.js`、`pdf-parse` 等文档解析库）都被打进 `dist/cli.js`。打进去的产物约 20 MB（未压缩），体积不算小，但这些大依赖在运行时按需懒加载（通过动态 `import()`，只在文件读取工具实际触发对应文件类型时才付出加载成本），启动阶段不会有明显延迟。选择全部打进去而非外部化的考量是：用户执行 `npm install -g` 后能直接使用、不出安装意外，这比启动时冷加载慢几十毫秒更重要。外部化的包越多，用户安装后的目录结构越复杂，出现「某个可选依赖未能正确安装」的概率也越高。

### shebang 与 bin 字段

`packages/cli/package.json` 的 `bin` 字段声明了两个命令别名：

```jsonc
{
  "bin": {
    "x-code": "dist/cli.js",
    "xc": "dist/cli.js"
  }
}
```

npm 全局安装时会在 `PATH` 目录下创建指向 `dist/cli.js` 的符号链接。配合产物开头的 shebang 行，用户在终端中输入 `xc` 即可启动 CLI。`x-code` 是完整名称，`xc` 是简写，两者指向同一个文件。

## A.3 ESM/CJS 互操作与 esbuild 插件

Node.js 生态中同时存在 ESM 和 CJS 两种模块格式的依赖：有的库只发布 ESM，有的只发布 CJS，有的同时发布两种格式。esbuild 以 ESM 格式输出产物时，需要将 CJS 依赖的导出形态转换成 ESM 兼容的形式。大部分情况下 esbuild 的内置转换机制能够正确处理，但在本项目中有三处特殊情况需要自定义插件介入。

### stubPlugin：移除 react-devtools-core

Ink（终端 React 渲染框架）在源码中包含一条对 `react-devtools-core` 的 import 语句。这个依赖在开发模式下用于连接 React DevTools 调试器，生产环境中不会被实际调用，Ink 也将其声明为 `optionalDependencies`。问题在于 esbuild 的静态打包不会因为 `optionalDependencies` 就自动跳过——它会尝试解析每一个 import 路径，如果 `react-devtools-core` 没有安装（正常情况下确实不会安装），构建就会失败。`stubPlugin` 的做法是拦截对 `react-devtools-core` 的解析请求，返回一个 `export default undefined` 的空模块，让 esbuild 满足 import 解析的同时不引入任何实际代码。

### entitiesFixPlugin：修复 entities 子路径

`entities@4.x`（一个 HTML 实体编解码库，被 cheerio 间接依赖）对外暴露 `entities/decode` 和 `entities/escape` 两个子路径入口。在 pnpm 的嵌套 `node_modules` 布局下，esbuild 在解析这两个子路径时会遇到路径查找失败。`entitiesFixPlugin` 通过 `onResolve` 钩子拦截匹配 `entities/(decode|escape)` 的请求，将其硬编码指向 `node_modules/.pnpm/` 下的实际 ESM 文件路径。这是一个 pnpm 布局特有的问题，使用 npm 或 yarn 的扁平布局不会遇到。

### signalExitFixPlugin：归一化 signal-exit 的两个不兼容版本

`signal-exit` 是一个在进程退出时执行回调的工具库。这个库的 v3 和 v4 之间存在不兼容的导出变更：v3 使用 CJS 默认导出（`module.exports = onExit`，没有命名导出 `onExit`），v4 改为 ESM 命名导出（`export { onExit }`，没有 default）。在 X-Code CLI 的依赖树中，Ink 6.x 依赖 `signal-exit` v3，execa 9.x 依赖 `signal-exit` v4，两个版本在树中共存。pnpm 按消费方隔离不同版本，开发模式下 Node.js 的 ESM 解析器分别找到各自对应的版本，运行一切正常。但 esbuild 打包时情况不同：它对每个 `import 'signal-exit'` 位置只解析一次，只会选中一个版本注入，导致另一个消费方拿到的导出形态不匹配。

`signalExitFixPlugin` 用一个垫片（shim，即一小段中间代码，用来桥接两个原本不兼容的接口）解决这个问题。它拦截所有对 `signal-exit` 的解析请求，替换为一段归一化代码，这段代码用 `import * as _m from 'signal-exit'` 拿到完整的命名空间对象，然后通过一系列回退逻辑来确保兼容性：先尝试 `.default`（v3 路径），再尝试 `.onExit`（v4 路径），使得无论底层解析到的是 v3 还是 v4，`import onExit` 和 `import { onExit }` 都能拿到正确的函数。完整的垫片代码如下：

<!-- check:ignore=code-source -->
```js
const signalExitFixPlugin = {
  name: 'fix-signal-exit-default',
  setup(build) {
    build.onResolve({ filter: /^signal-exit$/ }, (args) => {
      if (args.namespace === 'signal-exit-shim') return
      return {
        path: args.path,
        namespace: 'signal-exit-shim',
        pluginData: { resolveDir: args.resolveDir },
      }
    })
    build.onLoad({ filter: /.*/, namespace: 'signal-exit-shim' }, (args) => ({
      contents: `
        import * as _m from 'signal-exit';
        // Bracket access via a variable key so esbuild can't statically
        // prove that 'default' is missing from the v4 namespace and emit
        // an "import-is-undefined" warning.
        const _ns = _m;
        const _defaultKey = 'default';
        const _raw = _ns[_defaultKey] ?? _ns;
        const _fn = typeof _raw === 'function'
          ? _raw
          : (_raw.onExit ?? _ns.onExit);
        export { _fn as onExit };
        export default _fn;
      `,
      loader: 'js',
      resolveDir: args.pluginData.resolveDir,
    }))
  },
}
```

垫片中有一个需要说明的细节：访问 `.default` 属性时没有直接写 `_m.default`，而是通过中间变量 `_defaultKey = 'default'` 做方括号访问（`_ns[_defaultKey]`）。原因在于 esbuild 的静态分析器会检测到 v4 命名空间上不存在 `default` 导出，并发出「import-is-undefined」警告。用变量做方括号访问使 esbuild 无法在编译期证明这个属性一定缺失，避免了误报。运行时行为与直接写 `_m.default` 完全等价。

这类「同一个包名在依赖树中共存两个不兼容主版本」的问题有一个容易误判的特点：开发模式下一切正常，打包后产物才出问题。pnpm 在开发时按消费方隔离版本，Node.js 的 ESM 解析器分别定位到正确的版本，执行 `pnpm dev` 不会暴露任何错误。问题只在 `esbuild bundle` 这一步才出现，因此「打包后的产物行为异常」不能用「开发时运行正常」来排除。遇到类似现象时，应该先检查依赖树中是否存在同名包的多版本共存（`pnpm list <package>`），再看 esbuild 打包时选中了哪个版本。

## A.4 版本号的两条路径

> 源码：`packages/cli/src/version.ts`

`version.ts` 为 CLI 提供当前版本号。它的设计意图是支持两条获取路径：构建时注入（Build-time Define）优先，运行时从 `package.json` 读取作为降级。

```ts
declare const __CLI_VERSION__: string | undefined

function resolveVersion(): string {
  if (typeof __CLI_VERSION__ === 'string' && __CLI_VERSION__) {
    return __CLI_VERSION__
  }
  try {
    let dir = dirname(fileURLToPath(import.meta.url))
    for (let i = 0; i < 6; i++) {
      const pkgPath = join(dir, 'package.json')
      if (existsSync(pkgPath)) {
        const pkg = JSON.parse(readFileSync(pkgPath, 'utf-8')) as { name?: string; version?: string }
        if (pkg.name === '@x-code-cli/cli' && pkg.version) {
          return pkg.version
        }
      }
      const parent = dirname(dir)
      if (parent === dir) break
      dir = parent
    }
  } catch {}
  return '0.0.0-dev'
}

export const VERSION = resolveVersion()
```

函数 `resolveVersion()` 的逻辑分为两个分支。第一个分支检查全局常量 `__CLI_VERSION__` 是否在编译时被 esbuild 的 `define` 机制替换为一个字符串字面量，如果是，直接返回该字符串，运行时零开销。第二个分支是降级路径：从当前文件所在目录向上逐级查找 `package.json`，找到名为 `@x-code-cli/cli` 的包后读取其 `version` 字段。这个向上查找最多走 6 层，覆盖了从 `dist/cli.js` 到 `packages/cli/package.json` 的典型目录深度。如果两条路径都失败（极端情况，例如文件被单独拷贝到别处运行），则返回 `'0.0.0-dev'` 作为最终降级值。

在 v0.3.3 版本中，`esbuild.config.js` 的 `define` 字段实际只定义了 `process.env.NODE_ENV`，并没有定义 `__CLI_VERSION__`。因此在打包产物中，`typeof __CLI_VERSION__` 的值始终是 `'undefined'`，第一个分支永远不会命中，运行时总是走第二条路径从 `package.json` 读取版本号。这一偏差提示读者：源码注释描述的可能是设计意图而非当前实现，核对行为时应以代码逻辑为准。release 脚本在发布前会先 bump `packages/cli/package.json` 的版本号再执行构建，因此发布到 npm 的产物通过降级路径读到的始终是正确版本。保留构建时注入这条路径是为将来做准备：如果需要将 `package.json` 从产物中移走（例如做纯单文件分发），只需在 `esbuild.config.js` 中加一行 `'__CLI_VERSION__': JSON.stringify(pkg.version)` 即可切换。

## A.5 tsx 开发模式

> 源码：根 `package.json` 的 `scripts.dev`

```jsonc
{
  "scripts": {
    "dev": "pnpm -r run build && pnpm --filter @x-code-cli/cli run dev"
  }
}
```

`pnpm dev` 的实际行为分为两步。第一步 `pnpm -r run build` 递归构建所有工作区包：core 包执行 `tsc -b` 将 TypeScript 编译到 `dist/`，cli 包执行 `node esbuild.config.js` 生成 `dist/cli.js`。第二步 `pnpm --filter @x-code-cli/cli run dev` 进入 cli 包，执行 `tsx src/index.ts`。tsx 是一个基于 esbuild 的 TypeScript 即时运行器（JIT Runner），它在 Node.js 的模块加载钩子中插入 esbuild 的转换步骤，使 `.ts` 和 `.tsx` 文件不需要预编译即可直接运行。第一步的全量构建是必要的，因为 cli 通过 `import from '@x-code-cli/core'` 引用 core 包，而 `@x-code-cli/core` 的 `exports` 字段指向 `./dist/index.js`，tsx 只能即时转换当前包的 TypeScript 源码，跨包引用使用的是编译后的 `dist/` 产物。

一个容易产生的误解是将 `pnpm dev` 等同于监听模式（Watch Mode）。实际上它不是，每次修改源码后需要重新运行 `pnpm dev`。这是有意为之的设计选择，原因在于跨包的监听模式在单仓多包架构下实现起来比较复杂：core 改了一个导出类型，cli 端是否需要重启？tsx 缓存是否需要失效？让开发者手动控制重启时机比依赖自动化更可靠。如果读者在本地开发时确实需要监听行为，可以在两个终端中分别运行：一个终端在 core 包内执行 `pnpm dev`（脚本为 `tsc -b --watch`，增量编译 TypeScript），另一个终端在 cli 包内执行 `tsx --watch src/index.ts`（监听文件变化自动重新运行）。两个终端配合即可获得接近实时的开发反馈。

## A.6 TypeScript 项目引用

X-Code CLI 的 TypeScript 配置采用项目引用（Project References）机制，通过根目录的 `tsconfig.json` 串联两个包：

```jsonc
// tsconfig.json（根目录）
{
  "files": [],
  "references": [{ "path": "packages/core" }, { "path": "packages/cli" }]
}
```

`"files": []` 表示根配置本身不包含任何源文件，它的唯一作用是声明引用关系。`tsc -b`（即 `pnpm typecheck`）从这个入口出发，按依赖顺序先检查 core、再检查 cli。两个包共享一份基础配置 `tsconfig.base.json`：

```jsonc
// tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "lib": ["ES2022"],
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "isolatedModules": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
```

`module: "NodeNext"` 配合 `moduleResolution: "NodeNext"` 启用 Node.js 原生的 ESM 解析策略，要求 import 路径带文件扩展名（如 `import { foo } from './bar.js'`）。`strict: true` 开启全部严格类型检查。`declaration: true` 和 `declarationMap: true` 生成 `.d.ts` 类型声明文件和对应的 source map，确保 cli 包引用 core 时 IDE 能跳转到 TypeScript 源码而非编译产物。`isolatedModules: true` 是与 esbuild 配合的关键选项：esbuild 按文件独立转换、不做跨文件类型分析，`isolatedModules` 令 tsc 在类型检查阶段就禁止那些依赖跨文件信息的语法（如 `const enum`、不带类型标注的 `export { ... } from`），这样 tsc 通过检查的代码在 esbuild 中也能正确转换。

两个包在此基础上各自扩展。core 包的 `tsconfig.json` 只需声明 `composite: true`（项目引用要求）、`rootDir: "src"`、`outDir: "dist"`。cli 包额外开启 `jsx: "react-jsx"`（新 JSX 转换，与 esbuild 的 `jsx: 'automatic'` 对应），并通过 `references: [{ "path": "../core" }]` 告知 tsc：cli 依赖 core，检查 cli 之前需要先确保 core 的类型是最新的。

## A.7 测试链与 Vitest

### 根级入口与包级配置

根 `package.json` 的 `test` 脚本是 `vitest run`。Vitest 会自动发现工作区中每个包的 `vitest.config.ts`，每个包单独配置 `include` 范围，一次执行拿到所有测试结果。两个包都使用相同的基础配置：`globals: true`（无需手动 import `describe`/`it`/`expect`）、`environment: 'node'`。cli 包显式声明了 `include: ['tests/**/*.test.{ts,tsx}']`，后缀列表中带有 `.tsx`，因为 cli 包存在基于 Ink 的 React 组件单测。core 包没有 `include` 字段，走 Vitest 的默认全局扫描规则。这种「每个包独立 `vitest.config.ts`」的结构虽然多了两个配置文件，但换来的是包级别的测试范围隔离：将来如果 cli 端需要接入类 jsdom 环境来测试 Ink 渲染逻辑，只需修改 cli 的配置，不会影响 core 的纯 Node.js 测试环境。

## A.8 代码质量卡点：Husky、lint-staged 与 commitlint

除了开发者主动执行的 `pnpm ci` 之外，项目还配置了一套在 `git commit` 时自动触发的检查机制。根 `package.json` 中 `"prepare": "husky"` 脚本在 `pnpm install` 后自动注册两个 Git Hook（Git 钩子）：

```sh
# .husky/pre-commit
npx lint-staged

# .husky/commit-msg
npx --no -- commitlint --edit "$1"
```

提交流程被这两个钩子切成两步。`pre-commit` 阶段执行 `lint-staged`，对暂存区（Staging Area）中的文件按类型分别处理：

```jsonc
// 根 package.json 中的 lint-staged 配置
{
  "*.{ts,tsx,js,jsx,mjs}": ["eslint --fix", "prettier --write"],
  "*.{json,md,yaml}":      ["prettier --write"]
}
```

对 TypeScript 和 JavaScript 文件，先执行 ESLint 自动修复（主要是移除未使用的 import，由 `eslint-plugin-unused-imports` 提供），再执行 Prettier 格式化。对 JSON、Markdown、YAML 文件只执行 Prettier。修复后的改动自动加回暂存区，因此 commit 进 Git 的版本始终是 lint 和格式化之后的版本。任何一步报错则 commit 被取消。

`commit-msg` 阶段执行 `commitlint`，按约定式提交（Conventional Commits）规范校验 commit message。`commitlint.config.js` 中声明的合法 type 白名单为：

```text
build / chore / ci / docs / feat / fix / perf /
refactor / revert / release / style / test / wip
```

这条规则不仅是风格统一。发布脚本 `scripts/release.mjs` 生成变更日志（CHANGELOG）时按 type 前缀过滤 commit，只保留 `feat`（新功能）、`fix`（修复）、`perf`（性能）三种用户可感知的变更类型。如果 commit message 格式不规范，发布脚本将无法正确归类，变更日志会遗漏条目。`commit-msg` 钩子从源头上防止了这种情况。

关于 ESLint 和 Prettier 的具体配置：ESLint 采用扁平配置格式（Flat Config，ESLint 10 起推荐），基于 `typescript-eslint` 做 TypeScript 解析，搭配 `eslint-plugin-react-hooks`（确保 React Hook 调用规则）和 `eslint-plugin-unused-imports`（自动移除未使用的 import，这是保存时自动修复的核心功能）。Prettier 配置为单引号、无分号、120 字符行宽、尾逗号，并通过 `@trivago/prettier-plugin-sort-imports` 插件按约定顺序排列 import 语句（`node:` 内置模块在前，相对路径在后）。这两个工具的职责划分清晰：ESLint 负责逻辑层面的代码质量（未使用的变量、Hook 规则），Prettier 负责纯粹的格式统一（缩进、引号、换行）。两者在 lint-staged 中串联执行，先 ESLint 修复、再 Prettier 格式化，顺序不能颠倒，因为 ESLint 的修复可能产生不符合 Prettier 规范的代码，需要 Prettier 在最后一步统一格式。

整体来看，代码质量形成三层卡点。第一层是开发期的手动检查：`pnpm ci` 按顺序执行类型检查、lint、测试、构建，任何一步失败则整体失败。第二层是 commit 时的自动化检查：`pre-commit` 确保代码格式、`commit-msg` 确保 message 规范。第三层是推送后的 CI 检查：`.github/workflows/pr-check.yml` 在 PR 上再执行一遍 lint、typecheck、跨平台测试和 commitlint。每一层防御的是不同类型的遗漏：手动 ci 防「忘了跑测试」、pre-commit 防「代码没格式化」、commit-msg 防「message 不规范」、PR CI 防「本地环境和 CI 环境不一致」。

## A.9 发布流程

> 源码：`scripts/release.mjs` + `.github/workflows/release.yml`

发布流程分为本地脚本和 CI 自动化两个阶段。执行 `pnpm release` 启动本地阶段，脚本会依次完成以下步骤：

（1）交互式提示选择版本类型（patch / minor / major / custom），按语义化版本（Semantic Versioning, SemVer）规则计算目标版本号。

（2）同步更新 `packages/core/package.json` 和 `packages/cli/package.json` 的 `version` 字段为目标版本号。

（3）从上一个 Git tag 到 `HEAD` 的 commit 历史中提取 commit message，按约定式提交的 type 前缀分组，只保留 `feat`、`fix`、`perf` 三种用户可感知的变更，写入 `CHANGELOG.md` 头部。`refactor`、`docs`、`chore`、`ci` 等非用户可见的变更类型不会出现在变更日志中。

（4）执行 `pnpm build` 完成完整构建。

（5）创建 Git commit（message 为 `release: v<version>`）、打 `v<version>` tag、推送到 GitHub。

tag 推送到 GitHub 后触发 CI 阶段。`.github/workflows/release.yml` 监听 `v*` 格式的 tag 事件，执行以下操作：在 ubuntu-latest 环境中安装依赖并构建；将仓库根目录的 `LICENSE` 复制到两个包目录（npm 发布时需要包含许可证文件），`README.md` 和 `README.en.md` 只复制到 `packages/cli/`（cli 是面向最终用户的包，需要在 npm 页面展示 readme；core 只是依赖包，不需要）；依次执行 `pnpm publish --provenance --access public --no-git-checks` 发布 core 和 cli 到 npm；从 `CHANGELOG.md` 中提取最新一段变更记录，调用 `softprops/action-gh-release@v2` 创建 GitHub Release。

### npm OIDC 来源证明

`pnpm publish --provenance` 利用 GitHub Actions 的 OIDC（OpenID Connect）令牌让 npm 验证发布来源。这也是 `release.yml` 在 `permissions` 块中声明 `id-token: write` 的原因（同一块中的 `contents: write` 则用于推送 tag 和创建 GitHub Release），没有 `id-token: write` 权限，GitHub Actions 无法签发 OIDC 令牌。来源证明（Provenance）的安全价值在于供应链攻击防御：即使攻击者窃取了维护者的 npm 令牌，在自己的机器上执行 `npm publish` 也无法附带有效的来源证明。下游用户可以在 npm 页面上区分「从仓库 CI 构建并发布的版本」和「从任意环境发布的版本」，前者带有绿色的「Provenance」徽章，后者没有。

## A.10 Node.js 版本要求

根 `package.json` 和 `packages/cli/package.json` 都声明了 `"engines": { "node": ">=20.19.0" }`。选择 20.19 作为最低版本基于三方面考量：Ink 6、ESLint 10、yargs 18 等核心依赖都要求 Node 20+ 以上版本；Node 20 是当前的长期支持版本（LTS），覆盖了绝大多数开发者的运行环境；`process.loadEnvFile()`（用于加载 `.env` 文件，避免引入 dotenv 依赖）从 Node 20.12 起内置，20.19 的下限保证了这个 API 的可用性。

启动时的版本校验由 `packages/cli/src/index.ts` 中的 `checkNodeVersion()` 函数执行：

<!-- check:ignore=code-source -->
```ts
const MIN_NODE_VERSION = [20, 19, 0]

function checkNodeVersion(): void {
  const [major, minor, patch] = process.versions.node
    .split('.').map((v) => parseInt(v, 10))
  const [reqMajor, reqMinor, reqPatch] = MIN_NODE_VERSION
  if (
    major < reqMajor ||
    (major === reqMajor && minor < reqMinor) ||
    (major === reqMajor && minor === reqMinor && patch < reqPatch)
  ) {
    console.error(
      `Error: X-Code CLI requires Node.js >= ${MIN_NODE_VERSION.join('.')}, ` +
      `but you are running ${process.versions.node}.\n` +
      'Please upgrade Node.js: https://nodejs.org/',
    )
    process.exit(1)
  }
}
```

这个校验在 CLI 启动的最早阶段执行，早于命令行参数解析和 Ink 渲染框架初始化。如果 Node.js 版本不满足要求，程序立即输出清晰的错误信息并退出，避免在后续流程中出现难以排查的兼容性错误。`package.json` 的 `engines` 字段和运行时的 `checkNodeVersion()` 形成双重校验：前者在 `npm install` 阶段给出警告（取决于包管理器的 `engine-strict` 配置），后者在实际运行时强制拦截。

## A.11 后续优化方向

打包后的 CLI 单文件约 20 MB（未压缩），运行时启动开销主要来自 Node.js 本身的冷启动。已经实施的优化是按需动态导入：`mammoth`、`xlsx`、`officeparser`、`tesseract.js` 等文档解析库都在 core 包的文件读取工具内部通过动态 `import()` 加载，只在触发对应文件类型时才付出加载成本，启动阶段不受影响。潜在的进一步优化方向是开启 esbuild 的代码压缩。当前构建没有压缩，是为了让线上调用栈能直接对照 TypeScript 源码。如果将来接入 source map 上报系统（例如 Sentry），就可以安全地开启压缩，显著缩小产物体积。

关于运行时的选择：当前使用 Node.js 而非 Bun 作为运行时。Bun 的启动速度比 Node 快 2 到 3 倍，在 CLI 场景下体感提升明显。但 `npm install -g @x-code-cli/cli` 是默认安装路径，任何安装了 Node.js 的环境都可以直接使用；如果要求用户先安装 Bun 才能运行 CLI，渗透率会下降一个量级。选择 Node.js 是在启动速度和安装门槛之间取的平衡。

## A.12 小结

本附录覆盖了 X-Code CLI 从源码到可执行产物的完整构建工具链。仓库采用 pnpm 工作区管理的双包结构（`@x-code-cli/core` 和 `@x-code-cli/cli`），职责隔离使两个包各自拥有独立的构建配置、测试集和 `tsconfig.json`。esbuild 将 cli 包的入口文件 `src/index.ts` 及其全部依赖打包为单个 ESM 文件 `dist/cli.js`，banner 中注入 shebang 行和 ESM polyfill，只外部化 `@vscode/ripgrep`（原生二进制无法内联）。三个自定义 esbuild 插件分别处理 react-devtools-core 的空桩替换、entities 子路径在 pnpm 布局下的解析失败、以及 signal-exit v3/v4 两个不兼容版本在打包时的导出归一化。版本号通过 `version.ts` 的双路径机制获取，当前版本实际走运行时读取 `package.json` 的降级路径，构建时注入的通道已预留但尚未启用。

开发模式方面，`pnpm dev` 不是监听模式，而是「全包构建一遍加 tsx 直接执行 TypeScript」的一次性流程。TypeScript 采用项目引用机制，`tsc -b` 按依赖顺序编译 core 再编译 cli，`isolatedModules` 保证 tsc 检查通过的代码在 esbuild 中也能正确转换。Vitest 测试链通过工作区级别的 `vitest.config.ts` 实现包级隔离，core 包的 53 个测试文件覆盖了从 Agent Loop 到插件系统的主要模块。

质量与发布方面，代码质量由三层卡点保证：开发期的 `pnpm ci`、commit 时的 Husky 钩子（lint-staged 加 commitlint）、推送后的 PR CI 检查。发布是本地脚本加 CI 的两段式流程：本地 `pnpm release` 完成版本号计算、变更日志生成、构建、打 tag 并推送；GitHub Actions 收到 `v*` tag 后带 OIDC 来源证明发布到 npm。Node.js 最低版本要求为 20.19.0，由 `package.json` 的 `engines` 字段和运行时 `checkNodeVersion()` 形成双重校验。当前产物约 20 MB 未压缩，后续可通过开启 esbuild 压缩配合 source map 上报显著缩小体积。
