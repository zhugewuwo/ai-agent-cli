第 31 章 上下文压缩：轻量、主动与反应式三层

长对话在多轮工具调用后容易逼近模型的上下文窗口上限。Ch.30 将压缩列为四层 token 防御的第三层；本章展开这一层，讨论压缩机制内部按触发条件和成本再分的三条路径。三条路径从轻到重依次是：轻量压缩（纯本地 O(n) 扫描，不调用 LLM）、主动式预防（每轮开头按阈值触发，先轻量后 LLM 摘要）、反应式容错（流式响应抛出「context too long」错误时立即压缩并重试）。Ch.30 的「层」是四个独立防御机制，本章的「层」是同一个压缩机制内部的三条触发路径，读者留意两处「层」含义不同。本章将分为如下几个部分进行介绍。

  • 31.1 节梳理压缩总策略：两个核心常量、触发流程，以及压缩前后消息历史的变化。
  • 31.2 节讲解本地预清理，包括轻量压缩删除 loop guard 残骸和旧工具结果截短回收大型 tool-result 正文，两步都不调用 LLM。
  • 31.3 节讲解主动式预防，讨论每轮开头按阈值触发的双重判定条件及其设计取舍。
  • 31.4 节讲解反应式容错，讨论流式响应抛出「context too long」类错误时的压缩与重试。
  • 31.5 节讲解 LLM 摘要的实现，讨论摘要策略与角色选择。
  • 31.6 节讨论压缩边界与 JSONL 会话存档的协作。
  • 31.7 节给出本章小结。

AI 知识背景：上下文窗口为什么不能「开足够大就完了」

2022 年 GPT-3 的上下文窗口是 4k tokens，2024 年 Claude 和 GPT 普遍达到 128k–200k，2025–2026 年 Sonnet 4.6、Opus 4.7、DeepSeek V4 等已经把 1M 窗口做成默认配置。窗口看似已经足够大，超限问题似乎不再存在。但 2023 年 Stanford 的 Lost in the Middle 论文揭示一个反常规事实：长上下文里，模型对中间位置的内容召回率显著低于开头和结尾——即使是声称支持长上下文的模型，性能曲线呈 U 形。这意味着把 50k 旧消息加 5k 新消息放入 200k 窗口，不等于模型能用上全部 55k，中间部分会被实质性忽略。更实用的策略是主动压缩：把不重要的旧消息总结成 5k 摘要再加 5k 新消息，10k 有效上下文比 55k 含大量「看不见」中间内容更可靠。这是 X-Code CLI 即使在 1M 窗口模型上也要做压缩的原因。Anthropic 自己的 Long context tips 文档也建议把关键信息放在开头或结尾，避免埋在中间。

整个压缩动作和写会议纪要比较像——相同点是把一段冗长的过程内容凝练成一份短摘要供后续参考，丢掉无关细节、留住关键决策与结论。不同点是会议纪要由人手写、目的是给人看；上下文压缩由 LLM 自己用 generateText 生成摘要再作为后续请求的输入，目的是给模型看，因此摘要 prompt 特别强调「保留关键决策、文件改动、继续工作所需的上下文」——三类信息丢了模型就接不上之前的工作，等于纪要漏了关键决策导致下次会议无法继续。

31.1 压缩总策略

Ch.30 已经说明工具结果是 token 消耗的主体（占比 60–80%），几轮工具调用就足以让 token 用量逼近上下文窗口上限。X-Code CLI 的压缩策略是在每轮 agent loop 开头检查上下文长度，如果超过阈值就触发压缩——把消息历史浓缩，保留关键信息、丢弃细节，让模型能在更少的 token 中继续之前的工作。这一策略由两个核心常量控制。

（1）KEEP_RECENT = 6：最近 6 条消息永远保留，保持当前工作上下文不被压缩。

（2）COMPRESSION_TRIGGER_RATIO = 0.8：如果 token 用量达到模型上下文窗口的 80%，就触发压缩。阈值留出 20% 的缓冲区，原因在于压缩自身也需要发起 API 请求，如果等到 95% 才触发，压缩请求本身就可能因为上下文不足而失败。

三条路径在一轮 turn 生命周期中分别介入不同环节：

   │     或 estimateTokenCount(messages) > 80% 阈值                │
   └────────────────┬────────────────────────────────────────────┘
                    │ 是

│ 一段 LLM 写的摘要       │ msg50                           │

KEEP_RECENT = 6 是切割线：最近 6 条消息永远不进摘要，保证当前正在做的工作能完整保留。例如最近改了哪个文件、模型刚说要尝试什么方案，这些细节如果进入 LLM 摘要，下一轮模型就可能接不上之前的工作。切割位置还有一个边界处理：如果第 6 条消息恰好是 tool 角色（即一条没有对应 tool_calls 的孤立工具结果），保留窗口会自动多保留一条消息以跳过这条孤立结果（即保留 7 条而非 6 条），避免供应商因收到「无 tool_calls 的 tool result」而拒绝请求。

31.2 本地预清理：轻量压缩与旧工具结果截短

轻量压缩的思路是扫一遍消息历史，删除被循环护栏阻断后留下的 tool-call / tool-result 对。凡是 tool-result 内容以 [loop-guard] 开头的合成结果，连同对应的 assistant tool-call 部分一起删除。这里只需要理解一点：被阻断的调用在后续轮次中不会再提供有用的信息，是纯粹的冗余内容。

以一个具体例子说明。假设模型对同一个 pnpm test 反复重试并触发了循环护栏，消息历史会呈现以下形态：

压缩前 messages 历史：
   ┌──────────────────────────────────────────────────────────────┐
   │ [user]  "看看 pnpm test 能跑吗"                                │
   │ [asst]  → tool_call(id_1) shell { command: 'pnpm test' }      │
   │ [tool]  id_1 → [loop-guard] 软阻断：同一命令第 3 次            │  ← 冗余
   │ [asst]  → tool_call(id_2) shell { command: 'pnpm test' }      │  ← 冗余
   │ [tool]  id_2 → [loop-guard] 第 4 次                            │  ← 冗余
   │ [asst]  → tool_call(id_3) shell { command: 'pnpm test' }      │  ← 冗余
   │ [tool]  id_3 → [loop-guard] 第 5 次硬退出                      │  ← 冗余
   │ [user]  "改用 pnpm test --reporter=verbose"                    │
   │ [asst]  ...                                                    │
   └──────────────────────────────────────────────────────────────┘

   lightCompactMessages 扫两遍：
   ① 第一遍收集 [loop-guard] 标记的 toolCallId: { id_1, id_2, id_3 }
   ② 第二遍重写：丢掉对应 tool-result 消息，
                 从 assistant 消息里剥掉同 id 的 tool-call 部分
                 （整条 assistant 全剥完则连消息一起丢）

压缩后 messages：
   ┌──────────────────────────────────────────────────────────────┐
   │ [user]  "看看 pnpm test 能跑吗"                                │
   │ [user]  "改用 pnpm test --reporter=verbose"                    │
   │ [asst]  ...                                                    │
   └──────────────────────────────────────────────────────────────┘
   三对 [loop-guard] 残骸全删，冗余内容清空，不调用 LLM

轻量压缩不调用 LLM、不发网络请求，纯本地 O(n) 扫描即可完成。处理掉的冗余内容往往就足够把 token 拉回阈值之下，省掉后续更昂贵的步骤。轻量压缩成功后单独写一条 compact-boundary（不带摘要文本）到 JSONL，保证 /resume 不会把已经删掉的 loop guard 对从磁盘恢复回来（详见 31.6 节）。

轻量压缩只处理 loop guard 残骸，但 token 超标不一定是 loop guard 导致的。更常见的场景是模型连续读了几个大文件（readFile、grep 结果、shell 输出），每条工具结果动辄几千行，即使没有重复调用，积累下来也会逼近阈值。为此，主动式压缩流程在轻量压缩之后、LLM 摘要之前加了第二步：截短旧工具结果。这一步遍历保护窗口（最近 10 条消息）之外的所有 tool-result，如果某条结果超过 500 字符，就将其替换为简短的占位信息（保留工具名、原始输出的字符数和前 3 行预览），丢弃中间正文。edit、writeFile、todoWrite 等改动类工具的结果永远不截短，因为这些结果代表关键决策，丢失后模型可能重复修改同一文件。

为什么不直接走 LLM 摘要？原因在于 prompt cache。LLM 摘要会把所有旧消息替换成一条 [Previous summary]，整个消息序列发生结构性变化，下一轮请求的 prompt cache 必然失效（详见 Ch.33）。截短旧工具结果只替换单条 tool-result 的正文内容，消息结构和顺序不变，prompt cache 的前缀匹配更可能命中。能用截短解决的场景，就不必付出 cache 失效的代价。

31.3 主动式预防

每轮 agent loop 开头执行以下判断：

const needsCompression =
  state.lastInputTokens > threshold ||
  estimateTokenCount(state.messages) > threshold

if (!needsCompression || state.messages.length <= KEEP_RECENT) return

两个条件取或，原因在于它们各自处理不同的情况。lastInputTokens 是上一轮 API 返回的真实 input token 数，是最可信的数据源。estimateTokenCount 按字符数除以 3.0 估算 token 数，作为安全网。为什么需要安全网？考虑这种场景：当前轮模型一次性 readFile 读了一个 5000 行的文件，lastInputTokens 是上一轮的值尚未更新，但当前消息历史已经接近上限。如果只看 lastInputTokens，会等到发完一轮请求把上下文顶到极限后才反应过来。字符估算按保守的 3.0 字符每 token 计算（英文实际约 4 字符每 token，CJK 和代码更低），故意偏高，因为估算的目的是安全网而非精确计费，宁可提前压缩一次也不能漏掉一次真正逼近上限的场景。

阈值的具体值等于模型的上下文窗口大小（从 MODEL_CONTEXT_WINDOWS 查表获取）乘以 COMPRESSION_TRIGGER_RATIO。下表节选部分模型的窗口大小和对应的 80% 阈值：

模型 上下文窗口 80% 阈值
anthropic:claude-opus-4-7 1M 800k
anthropic:claude-sonnet-4-6 1M 800k
anthropic:claude-haiku-4-5 200k 160k
openai:gpt-4.1 系列 ~1M (1,047,576) ~838k
openai:o3 / o4-mini 200k 160k
deepseek:deepseek-v4-flash / pro 1M 800k
alibaba:qwen3-coder-plus 1M 800k

查表未命中时回退到 PROVIDER_CONTEXT_WINDOWS（按供应商给出该系列模型通用的默认值），仍未命中则回退到 DEFAULT_CONTEXT_WINDOW = 128000。这样新发布但尚未登记的模型也有保守上限，不会因为查不到表而误判窗口无限大。触发后依次尝试三步：轻量压缩删除 loop guard 残骸 → 旧工具结果截短回收大型 tool-result 正文 → LLM 摘要（三步细节详见 31.2 和 31.5 节），每步完成后都会重新检查是否仍超阈值，已经降回阈值之下就提前返回。压缩完成后 lastInputTokens 重置为 0，下一轮重新估算。

31.4 反应式容错

前两层是「防止逼近上限」，但无法覆盖所有情况。字符估算虽然偏保守，极端情况下仍可能偏低；供应商在某些请求上可能动态降低上下文限制；工具结果在截断之前已经被追加到消息历史。反应式层处理这些遗漏：流式响应抛出错误且匹配上下文超限模式时，直接调用 LLM 摘要并重试当前轮。之所以跳过轻量压缩和工具结果截短，是因为主动式检查在本轮开头已经执行过一次。如果那时判定低于阈值，说明两步本地清理并不能解决当前的超限问题，反应式作为紧急路径直接走最彻底的压缩。

这一路径面临的工程难点在于错误识别：不同供应商对「上下文超限」的报错格式各不相同。OpenAI 返回 maximum context length 或 context_length_exceeded，Anthropic 返回 prompt is too long 或 prompt_too_long，还有些供应商直接通过 HTTP 413 状态码报告超限。X-Code CLI 用一个字符串模式数组加 HTTP 状态码检查来统一识别，当前覆盖了 7 条模式和 HTTP 413，新增供应商时遇到新的报错表述只需往数组里追加一条。反应式压缩成功后，agent loop 会重试本轮，同时回退轮次计数，确保这次因超限导致的重试不计入循环上限（语义详见 Ch.08 TurnOutcome 节）。

用户也可以通过 /compact 命令主动触发压缩，不必等待阈值。这个命令适用于用户知道当前任务已结束、想清出空间给下个任务但又不想用 /clear 丢掉全部历史的场景。

31.5 LLM 摘要的实现

compressMessages 是三条路径最终汇聚的执行函数。主动式压缩流程在本地预清理仍超阈值时调用它，反应式容错在捕获上下文超限错误后直接调用它，/compact 命令也直接调用它。与前两步本地扫描不同，这是真正昂贵的操作：需要发起一次额外的 generateText 调用，按完整 token 计费。

async function compressMessages(messages, model) {
  const recent = messages.slice(-KEEP_RECENT)        // 保留最后 6 条
  const old = messages.slice(0, -KEEP_RECENT)         // 旧消息

  const { text: summary } = await generateText({
    model,
    system: 'Summarize the following conversation concisely, preserving key decisions, file changes, and context needed to continue.',
    messages: old,
  })

  return [
    { role: 'user', content: `[Previous conversation summary]\n${summary}` },
    ...recent,
  ]
}

这段代码有两个值得展开的设计决策。

摘要以 user 角色消息注入，而不是放入 system。原因在于 system 字段是提示词缓存的前缀起点，如果把摘要放进 system，每次压缩后 system 内容都会变化，导致整个会话的缓存失效。因此摘要走 user 角色，让 system 保持字节稳定。

摘要 prompt 强调保留「关键决策、文件改动、继续工作所需的上下文」。这三类信息对模型继续工作的能力各有不同作用：关键决策丢失会导致模型重新讨论已经做过的选择，文件改动丢失会导致模型重读已经修改过的文件，工作上下文丢失会导致模型从头开始而不是继续当前方案。

31.6 压缩边界与 JSONL 会话存档

X-Code CLI 把每个会话写成一份 append-only 的 .jsonl 文件，每条用户输入、每个工具调用、每条 assistant 消息按顺序追加到 .x-code/sessions/<slug>-<sessionId>.jsonl。/resume 启动时读这份文件 replay 即可把对话恢复到内存里。

但压缩打破了一个前提假设：直接重放 JSONL 文件就能恢复完整对话。压缩之后，内存里只有 [Previous summary] 加最近 6 条消息，但磁盘 JSONL 上还保存着原始 50 条旧消息。如果 /resume 从头重放整个文件，刚压缩省下的 token 全部又被读回来，等于压缩无效。解决办法是在 JSONL 里写入一条压缩边界（compact-boundary）：

JSONL 内容（按时间从上往下追加）：

   msg1
   msg2
   ...
   msg44
   ────── compact-boundary { summary: "..." } ──────   ← 边界行
   [Previous conversation summary]                      ← 重刷：摘要（user 角色）
   msg45                                                ← 重刷：最近 6 条原文
   msg46
   ...
   msg50

加载器遇到 boundary → 清空累积器 → 只读 boundary 之后的重刷内容

/resume 启动时不从头读，而是扫描到最后一条 compact-boundary 时清空消息累积器，然后只读取边界之后的条目。边界之后紧跟的是压缩完成时写入的一组消息：第一条是 [Previous conversation summary] 摘要（user 角色），后面是压缩时保留的最近 6 条原文。这组消息与压缩完成时的内存状态完全一致，因此 /resume 只读这一段就能恢复到压缩后的状态。写入边界的具体流程是：先在 JSONL 里追加一行 compact-boundary 元数据（附带一份摘要文本供会话列表展示），然后把内存里压缩后的完整消息数组逐条追加到同一文件。

轻量压缩也写边界，但摘要字段为空。轻量压缩只删除 loop guard 残骸、没有调用 LLM，因此没有摘要文本可填。即便如此仍然需要写一行边界，原因在于如果缺少这行标记，/resume 就会从 JSONL 的起始位置开始 replay，loop guard 残骸会从磁盘恢复回内存，轻量压缩等于白做。摘要生成也可能失败（网络中断、供应商暂时不可用），此时同样用空摘要写入边界。内存中的压缩照常发生，token 照常收回，只是 /resume 恢复时缺少了那段历史的摘要。这一设计体现了压缩机制的优先级：保证当前对话能继续进行（通过压缩收回 token）是第一目标，摘要质量是第二目标。摘要缺失只影响 /resume 恢复后模型对之前工作的了解程度，不影响当前正在进行的会话。

31.7 小结

本章讨论了 X-Code CLI 上下文压缩的三条路径：主动式在每轮开头按阈值触发，依次尝试轻量压缩、旧工具结果截短、LLM 摘要三步（前两步纯本地 O(n)、不调用 LLM）；反应式在流式响应抛出上下文超限错误时直接走 LLM 摘要并重试当前轮。LLM 摘要保留最近 6 条原文，摘要以 user 角色注入以保持 system 字节稳定。压缩完成后在 JSONL 里写入 compact-boundary，/resume 据此定位恢复点。
