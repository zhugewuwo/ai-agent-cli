第 30 章 Token 经济学：四层防御一览

每个大语言模型都有上下文窗口（Context Window）上限，如果一轮对话的消息总量超过这个上限，API 就会直接返回错误，当前对话无法继续。对于普通的聊天机器人，用户消息通常不长，很少触及上限。但 Agent 的情况不同——它在每轮对话中会调用工具，而工具返回的结果往往体量很大：一次 grep 可能匹配 2000 行源码，一次 readFile 可能读入 1000 行文件内容。这些工具结果作为消息历史的一部分，会随着后续每一轮请求一起发送给模型，因此 token 消耗增长极快。为了应对这个问题，X-Code CLI 设计了四层防御机制协同控制 token 总量：工具结果截断、循环护栏（Loop Guard）拦截重复调用、轻量压缩、提示词缓存（Prompt Cache）。本章先建立全景视图，把每层防御的目标、代价与适用场景理清楚；Ch.31–34 将逐层展开各自的实现细节。本章将分为如下几个部分进行介绍。

  • 30.1 节梳理一轮对话中 token 的消耗分布，找出优化的主战场。
  • 30.2 节按从轻到重的顺序展开四层防御的目标、机制与代价。
  • 30.3 节讨论可观测渠道以及不在 CLI 控制范围内的部分。
  • 30.4 节澄清「中文是否能省 token」这一常见误区。
  • 30.5 节给出本章小结。

AI 知识背景：token 是怎么算出来的

「token」不是字符也不是单词，是 tokenizer 把文本切出来的语义片段。主流 LLM 用 BPE（Byte-Pair Encoding）：从单字节开始，把训练语料里最常一起出现的相邻字节对合并成新 token，反复迭代——常见词被合并成单 token，罕见词拆成几个 token。因为 BPE 基于训练语料频率，不同语言的 token 密度差异很大：英语训练数据占比最高，function / implementation 几乎都是 1 token；中文训练数据少，单个汉字常占 1–2 token。直观例子：Hello world（11 字符）= 2 tokens，你好世界（4 字符）≈ 4 tokens。所以「中文密度大、应该省 token」是直觉错觉——实际持平甚至更费。这是 token 成为 LLM「计费货币」的根源：供应商按 input token + output token 收费，所有优化都是为了在能完成任务的前提下少花 token。

30.1 token 的消耗分布

在讨论优化手段之前，我们需要先看清楚 token 到底消耗在哪里。下表列出了一轮典型对话中各部分的 token 占比：

部分 占比 是否能优化
system prompt + 知识库 5–15% 可（命中 cache 后按 10% 计费）
用户消息 1–5% 用户决定，不可控
工具结果 60–80% 占比最高——截断 + 防止失控
模型输出 5–15% 已跟随用户语言
思考 / reasoning 0–20% thinking 模型独有

从表中可以看出，工具结果是 token 消耗的绝对主体，占比达到 60–80%。原因在于 Agent 的工作方式：模型每调用一次工具，工具返回的完整结果就会作为一条消息追加到对话历史中。如果一次 grep 匹配了 2000 行源码，这 2000 行就会原封不动地进入消息历史，并在后续每一轮请求中重复发送给模型。因此，token 防御策略的首要目标就是控制工具结果的体量。后续四层防御正是按这个优先级展开的。

30.2 四层防御一览

四层防御并非线性递进的关系，每一层介入的位置各不相同。如果我们把一轮 turn 的生命周期展开来看，四层防御分别落在不同的环节上：

   ┌──────────────────────────── 一轮 turn 的生命周期 ────────────────────────────┐
   │                                                                              │
   │  ① turn 开头：检查 token 用量是否超 80% 阈值                                  │
   │       │                                                                      │
   │       │ 超阈值                                                               │
   │       ▼                                                                      │
   │  ─ ─ ─ [第 3 层-a] 轻量压缩：删重复对 ─ ─ ─                                   │
   │       O(n) 本地扫描，删 loop-guard 残骸                                       │
   │       │                                                                      │
   │       │ 仍超阈值？                                                           │
   │       ▼                                                                      │
   │  ─ ─ ─ [第 3 层-b] 轻量压缩：截旧结果 ─ ─ ─                                  │
   │       把非近期的大体量 tool-result 正文替换为简短占位信息                               │
   │       │                                                                      │
   │       │ 仍超阈值？                                                           │
   │       ▼                                                                      │
   │  ─ ─ ─ [LLM 摘要] ─ ─ ─                                                      │
   │       generateText 将旧消息摘要为 [Previous summary]                              │
   │       │                                                                      │
   │       ▼                                                                      │
   │  ② 发起 API 请求                                                              │
   │       │                                                                      │
   │       │  ─ ─ ─ [第 4 层] Prompt cache ─ ─ ─                                  │
   │       │  固定前缀命中按 ~10% 计费                                             │
   │       ▼                                                                      │
   │  ③ 模型流式响应 → 触发工具调用                                                │
   │       │                                                                      │
   │       │  ─ ─ ─ [第 2 层] Loop guard ─ ─ ─                                    │
   │       │  SHA-256 检测重复；3 次软阻断 / 5 次硬退出                             │
   │       ▼                                                                      │
   │  ④ 工具执行 → 拿到结果                                                        │
   │       │                                                                      │
   │       │  ─ ─ ─ [第 1 层] 工具结果截断 ─ ─ ─                                   │
   │       │  单条超长结果按 head-tail / head-only 策略截断                                  │
   │       ▼                                                                      │
   │  ⑤ 结果回到模型 → 继续 turn 或结束                                            │
   │                                                                              │
   └──────────────────────────────────────────────────────────────────────────────┘

每层防御针对一种不同的 token 膨胀场景：第 1 层防止单次工具调用的返回结果过大，第 2 层阻止模型对同一命令反复重试造成的 token 消耗黑洞，第 3 层先删除重复调用残骸、再截短旧工具结果，第 4 层让跨轮不变的固定前缀按折扣价计费。只有当前面四层都未能将 token 降回阈值之下时，才会启用 LLM 摘要作为最后手段。下面按从轻到重的顺序逐层展开。

第一层：工具结果截断

当单条工具结果超过长度限制时，CLI 会按工具预设的截断策略对其进行截断。多数工具采用 head-tail 策略（保留头部 20% 和尾部 80%），shell 等工具采用 head-only 策略，被截掉的中间部分用 [truncated N chars] 标记替代。除了逐条截断之外，工具自身也有内置的输出限制：grep 默认只返回前 250 条匹配，readFile 默认读取 2000 行，shell 输出上限为 20 MB。这两层限制共同将单轮的 token 总规模控制在可接受的范围内。这种做法的代价是模型可能错过被截掉的中间部分，但相比 token 超限导致整轮对话中断，局部信息缺失是更可接受的结果。详见 Ch.17。

第二层：循环护栏（Loop Guard）拦截重复调用

循环护栏通过滚动窗口对每次工具调用计算 SHA-256 哈希值（基于工具名和参数），检测短窗口内是否出现重复调用。如果同一调用连续出现 3 次，就注入一条合成的 tool-result 提示模型「换个思路」（软阻断）；如果达到 5 次，则强制退出当前 turn（硬退出）。典型的触发场景是模型对某个 shell 命令的引号格式不熟悉，反复用同样的写法重试。每次失败都会把 stderr 追加到消息历史中，如果没有循环护栏拦截，token 消耗就会随重试次数快速增长。循环护栏在第 3 次重复时就介入，避免了后续的无效消耗。这种做法的代价是模型被硬退出时需要用户手动介入。详见 Ch.32。

第三层：轻量压缩

在发起 LLM 摘要之前，CLI 会先做两遍 O(n) 的本地扫描。第一遍删除消息历史中重复的 tool-call / tool-result 对，典型的清理对象是循环护栏拦截后留下的残骸——模型因引号格式错误反复重试 shell 命令，每次重试都留下一对几乎相同的调用和返回。如果删除这些重复对之后 token 总量已经回到阈值以下，就不需要继续后续步骤。如果仍然超标，第二遍会把非近期的大体量工具结果替换为简短的占位信息（保留工具名和调用参数摘要，丢弃完整输出），因为早期对话中读过的文件内容或 grep 结果在后续轮次已经没有原文保留的必要。只有两遍本地扫描都未能降回阈值时，才需要发起 LLM 摘要。这一层的代价几乎为零：两遍 O(n) 扫描，不涉及任何 API 调用。详见 Ch.31。

第四层：Prompt cache

对于 Anthropic 模型，CLI 在 system prompt 和知识库内容上打 cache_control 断点。由于这部分内容在每轮请求中保持不变，下一轮请求就能命中缓存，input token 的实际计费降至约 10%。对于 OpenAI 兼容端点（如 DeepSeek、Moonshot 等），则依赖供应商自身的前缀缓存机制自动命中。这一层的代价有两方面：缓存未命中时需要额外支付 10–30% 的创建成本（仅 Anthropic），并且前缀内容必须保持字节级稳定——任何微小的变化都会破坏缓存命中。详见 Ch.33。

LLM 摘要

当前面四层都未能将 token 降回阈值之下时，CLI 会启用最后手段：把旧消息发送给模型，让模型生成一段摘要来替换原文。这一步的代价较高——需要发起一次额外的 generateText 调用，并按完整 token 数计费。前面四层防御的设计目的，正是为了尽量延缓这一步的触发，使大多数场景不需要走到 LLM 摘要这一步。详见 Ch.31 后半段。

读者可能会问：为什么不在 shell 工具里内置输出过滤器（如 RTK 这类对 git / vitest 等命令做有损过滤的工具）？原因有两条。其一，AI 调试时恰恰需要原始输出——编译失败的展开路径、依赖树的层级关系、测试通过的初始化步骤，这些是过滤器会去掉的细节；模型预训练时见的是原始格式，提供过滤后的版本会破坏推理依据。其二，X-Code CLI 把 shell 命令的 stdout 同样展示给用户和模型，中间加一层过滤后，用户看到的输出与模型看到的不一致，出问题时用户无法理解模型为什么这样判断。如果读者希望模型使用过滤后的版本，可以在 prompt 里显式指示模型加 rtk 前缀，选择权留给用户。

30.3 可观测性与不可控部分

上述四层防御的实际效果都可以通过 CLI 内置的命令进行观测。/usage 命令用于显示当前会话的 token 消耗和缓存命中率：

Usage (current session)

- Session:         2t8nz1a
- Model:           anthropic:claude-sonnet-4-6
- Input tokens:    128,432
- Output tokens:   12,847
- Cache read:      95,213  (74.1% of input)
- Cache creation:  33,219
- Total:           141,279

/usage-history 命令则用于跨会话查看趋势，列出本项目所有会话的 sessionId、模型、总 token 数与缓存命中率。具体的命中率会因供应商和对话类型而有所不同，读者应该用自己的实际数据来验证优化效果。

不过，有些部分不在 CLI 端的控制范围内。用户消息的长度由用户自己决定，工具结果中的代码和文件原文必须完整传给模型才能让它正常工作，模型输出的长度则由模型自身决定（CLI 只能通过 system prompt 引导模型给出简洁的回复）。四层防御覆盖的是 CLI 能够控制的部分，对于这些不可控部分，只能依赖可观测渠道来监控其消耗。

30.4 误区：中文是否能省 token

中文母语开发者在讨论 token 优化时，最常提出的一个问题是：如果强制让模型用中文输出或思考，是否能够节省 token？本章开头的 AI 知识背景已经用 Hello world 与 你好世界 的对比说明了直觉与实际的偏差。下面我们来看看具体的原因。

（1）中文相比英文最多省 5–15%，且只发生在自然语言段落上。各家 tokenizer 的实测结果是：每个汉字 1–2 token，少数针对中文优化的 tokenizer（如 DeepSeek）能做到 1 字 1 token，但都没有数量级优势。代码、文件路径、工具名、JSON 参数全是 ASCII，语言切换对它们没有影响。

（2）token 的主要消耗在不可控的工具结果（30.1 节已说明），不在语言切换。强制中文最多影响 system prompt + 思考 + 输出这 10–30% 的部分；省 10% 折算到整体只有 1–3%。

（3）强制中文的代价高于节省。指令遵守率方面，主流 LLM 的指令微调数据英文比例远高于中文，同一段系统指令的英文版遵守率明显更高。思考链质量方面，数学、逻辑、代码任务的 RL 训练以英文为主，中文思考准确率会下降；模型有时会先用英文推理一遍再翻译，反而多花 token。此外，思考链里夹杂英文标识符和中文连接词时，BPE 在语言边界处会拆出更多 token，中英混合反而更耗 token。

X-Code CLI 的策略是：system prompt 用英文（指令稳定性优先），明确指示模型用用户语言回复（Reply in the same language the user uses.），不限制思考语言（让模型按其 RL 训练默认值选择）。真正的 token 优化杠杆在本章前面四层防御，不在语言切换。

30.5 小结

本章建立了 X-Code CLI token 防御的全景视图。工具结果占 token 消耗的 60–80%，是优化的首要目标。四层防御从轻到重协同工作：工具结果截断（Ch.17）、循环护栏（Ch.32）、轻量压缩与 LLM 摘要（Ch.31）、提示词缓存（Ch.33），只有前面各层都未能降回阈值时才启用 LLM 摘要作为最后手段。强制中文输出并非有效手段，真正的杠杆在四层防御。/usage 和 /usage-history 是验证优化效果的可观测入口。
