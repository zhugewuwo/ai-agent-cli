第 26 章 流式输出

流式输出（Streaming Output）指模型边生成、边把文本切成小片段连续推给客户端，用户不用等整段生成完就能看到文字逐字出现。每个片段（text-delta）通常只携带 1-5 个字符，客户端不能每收到一个就触发 UI 更新——每秒几十次的重渲染会引发 CJK 宽度计算错误和终端写入过载。X-Code CLI 的策略是在 SDK 与 UI 之间加入缓冲节流层 useStreamBuffer，把连续到达的 delta 累积到安全的 markdown 边界才统一刷出。本章围绕这一策略展开，分为如下几个部分进行介绍。

  • 26.1 节从整体设计出发，介绍 useStreamBuffer 的两段缓存结构、三种流式情况和代码骨架。
  • 26.2 节讲解 findSafeBoundary 的安全边界切割算法：为什么按单个换行符切而不按段落切。
  • 26.3 节讨论 streamingChunk 标记如何让多个片段在终端上无缝拼接。
  • 26.4 节介绍只读工具组折叠：连续只读工具如何折叠成一行摘要。
  • 26.5 节给出本章小结。

流式输出指模型边生成、边把文本切成小片段连续推给客户端，用户不用等整段生成完就能看到文字逐字出现。AI Provider SDK（Anthropic、OpenAI、Vercel AI SDK 等）把每一个这种小片段事件叫做一个 text-delta——一次事件常常只携带 1-5 个字符（典型是一两个 token）。问题在于，客户端不能每收到一个 text-delta 就立即更新 UI，具体原因如下：

（1）每个 delta 进 React state。

delta 到达 → setState({ streamingText: prev + delta }) → React 重渲染
           → Ink 重绘动态区 → Yoga 算 CJK 宽度

每秒几十次 setState 会触发多次 Yoga 计算宽度——CJK 字符宽度算错时，光标退回过头，旧内容被覆盖、新旧内容拼接成乱码（详见 Ch.23）。

（2）每个 delta 直接写到 stdout。

delta 到达 → process.stdout.write(delta)

终端写入量过大——每秒几十次的 stdout 写入，且和 Ink 动态区互相干扰（Ink 重绘时也在 stdout 写入）。

两种方式都无法满足要求，必须在 SDK 与 UI 之间加入节流层。X-Code CLI 的策略是缓冲节流——把连续到达的 delta 累积到合理的 markdown 边界才统一刷出。

26.1 useStreamBuffer 的设计

源码：packages/cli/src/ui/hooks/use-stream-buffer.ts

先看 useStreamBuffer 在整体流水线里的位置。从模型 SDK 到终端屏幕，文本要经过三个互不重叠的处理层，useStreamBuffer 只负责其中第一层——把 text-delta 累积、切割、合并成一条消息。下面的示意图展示了一个 text-delta 从进入缓冲区到最终写入终端历史区的完整路径：

   模型流式 SDK             useStreamBuffer (本章)             ChatInput (Ch.24)         终端 (Ch.25)
   ───────────             ────────────────────             ──────────────────         ──────────

   text-delta ──→ 累加到 bufferRef
                       │
                       │ 扫描到安全 markdown 边界
                       ▼
                  移入 pendingChunksRef
                       │
                       │ 150ms 定时器到点
                       ▼
                  appendMessage(...) ────→ messages 数组
                                                │
                                                │ useEffect 触发
                                                ▼
                                          writeMessageToStdout
                                          + renderMarkdown ──→ ANSI 字节流 ──→ BSU/ESU 原子帧
                                                                                    │
                                                                                    ▼
                                                                          写到终端历史区

图中三层各有明确的职责边界。第一层是本章讨论的 useStreamBuffer，负责决定何时把哪段文本变成一条消息——按安全 markdown 边界切片，再用 150ms 合并窗口将密集到达的切片聚合成一次提交。第二层是 Ch.24 讨论的 ChatInput 渲染逻辑，负责消息进入数组后如何渲染到终端——通过 cell-level diff 比对差异，由 writeMessageToStdout 经换行符触发 auto-scroll 把内容推入终端历史区。第三层是 Ch.25 讨论的跨终端写入层，负责包装写入的字节流使其在不同终端上都稳定——BSU/ESU 原子帧、消除副作用写入等。三层之间的分工意味着本章只需要关心「在哪个位置切割文本」和「在什么时机把切片提交给 UI」，不需要关心写入终端的底层细节。

两段缓存的设计

每个 text-delta 到达后不直接推送到屏幕，而是依次经过两段缓存。第一段是 bufferRef，累加所有尚未切割的原始文本；第二段是 pendingChunksRef，存放已经通过安全边界检测、等待合并窗口到期后统一提交的切片。下面的示意图展示了一个 text-delta 从到达缓冲区到最终推送给 UI 的完整路径：

   模型 text-delta（每次 1-5 字符）
          │
          ▼
   ┌──────────────────────────────────────────────┐
   │ bufferRef: string                             │  ← 累加未切割的原始文本
   │ 例："你好，建议用 R"（末尾没有换行，还不能切） │
   └──────────────────────────────────────────────┘
          │ 找到一个可以切割的换行符
          │ （该换行符不在代码块或表格内部，切割不会破坏 markdown 结构）
          ▼
   ┌──────────────────────────────────────────────┐
   │ pendingChunksRef: string[]                    │  ← 等待 150ms 合并窗口的切片
   │ 例：["你好。\n", "建议用 React。\n"]           │
   └──────────────────────────────────────────────┘
          │ 150ms 定时器到点
          ▼
   appendMessage({ streamingChunk: true })   ← 把 pending 里的几段合并成一条消息推给 UI

读者可能会问，为什么需要分两段而不是只用一个缓冲区。原因在于两段缓冲各自解决了一个不同的问题。bufferRef 解决的是「还没到达安全边界就不能切」——比如 markdown 表格的表头刚写了一行 | col |，下一行还没到达，此时不能切割，否则 markdown 解析器会因为表格结构不完整而无法正确解析。pendingChunksRef 解决的是「密集到达的多个切片应合并成一次写入」——当模型连续生成段落、分隔符、标题时，150ms 内产生的多个切片会合并到同一次 appendMessage 调用，让终端少做一次重绘。如果只用一个缓冲区，要么在安全边界到达时立即提交（失去合并窗口的收益），要么在合并窗口到期前无法判断哪些内容已经通过安全检测（逻辑耦合）。两段分离让每一段只承担单一职责。

流式过程中的三种情况

回到开头的示例：用户提交请求后，模型的 text-delta 源源不断到达缓冲区。在一次完整的流式输出过程中，缓冲区会遇到三种不同的情况，useStreamBuffer 为每种情况提供了对应的处理方式。

第一种是常规流入。每个 text-delta 到达时调用 appendTextDelta，delta 累加到 bufferRef，扫描安全边界，能切就切到 pendingChunksRef，首个切片启动 150ms 定时器。定时器到点时内部的 drainPending 把所有等待中的切片拼起来，作为一条带 streamingChunk: true 标记的消息推给 UI。这是绝大多数时间里缓冲区的工作状态——text-delta 持续到达、累积到安全边界即切片、定时器到期即提交。

第二种是被工具调用打断。回想示例中模型写到「好的，我先看一下这个文件的当前实现」后突然决定调 readFile——这时 bufferRef 里可能还有没到安全边界的残留文本。如果不处理，用户会先看到工具调用、后看到文字，顺序错乱。下面的时序图对比了不做 flush 和做 flush 两种走法：

时间轴 ──→

不 flush（错乱）：
   t1: stream "好的，我先 readFile X" ──→ 落到 bufferRef，等 \n
   t2: 模型决定 tool-call 触发 onToolCall
   t3: UI 显示：● readFile X.ts          ← 工具调用先出现
   t4: 150ms 定时器到点 drainPending
   t5: UI 显示："好的，我先 readFile X"   ← 文字后出现（顺序错乱）

flush（顺序正确）：
   t1: stream "好的，我先 readFile X" ──→ 落到 bufferRef
   t2: onToolCall 回调第一行 → flushBuffer()
   t3: UI 显示："好的，我先 readFile X"  ← 文字先出现
   t4: UI 显示：● readFile X.ts          ← 工具调用后出现

因此 onToolCall 回调的第一行就调 flushBuffer：把 bufferRef 里的残留移入 pendingChunksRef，清掉定时器，立即执行一次 drainPending——t2 到 t3 之间没有 150ms 等待，残留文本在同一帧内推到 UI，视觉顺序正确。一轮正常结束时 submit 也会调一次 flushBuffer 刷出末尾残留。此外还有一种边界情况：某些推理模型不通过 onTextDelta 回调推送文本，而是把全部文本放在 response.messages 的最终 part 里，整轮没有触发过一次 onTextDelta。针对这种情况，submit 收尾时会调 extractLastAssistantText 从 loopState.messages 中提取 assistant 文本作为消息追加。工具执行完，模型继续输出时，新的 text-delta 从空缓冲重新累加、重新合并、再推给 UI；前后两段消息都带 streamingChunk: true 标记，不加末尾空行，在 UI 上自然连续成一段（详见下文「streamingChunk 标记与片段拼接」），用户看到的是一段完整文字被工具调用打断后继续，不会有断裂感。

第三种是用户中断。用户按 Esc 或 Ctrl+C、输入 /clear 时，缓冲区里的残留文本已经没有意义。resetBuffer 把三个 ref 全部清空、取消定时器，不调 drainPending——残留直接丢弃，避免下一轮开头出现上一轮未完成的残留文本。flushBuffer 和 resetBuffer 的核心区别在于残留文本的去向：前者把残留推到 UI 让用户看见，后者把残留直接丢弃。下面的表格汇总了三种情况。

情况 调用的函数 残留文本的去向
常规流入 appendTextDelta → 150ms 定时器 → drainPending 切片合并后推给 UI
工具调用打断 / 一轮收尾 flushBuffer 立即推给 UI
用户中断 resetBuffer 直接丢弃

代码骨架

输入侧只有一个 appendTextDelta 函数——累加 delta、找安全边界切片、首切片启动 150ms 定时器：

function useStreamBuffer(appendMessage: (msg) => void) {
  const bufferRef = useRef('') // 累加未切的原始文本
  const pendingChunksRef = useRef<string[]>([]) // 等待合并的安全切片
  const emitTimerRef = useRef<Timer | null>(null)

  const appendTextDelta = (delta: string) => {
    bufferRef.current += delta
    const boundary = findSafeBoundary(bufferRef.current)
    if (boundary > 0) {
      pendingChunksRef.current.push(bufferRef.current.slice(0, boundary))
      bufferRef.current = bufferRef.current.slice(boundary)
    } else if (bufferRef.current.length > CODE_FENCE_COMMIT_THRESHOLD && hasOpenMarkdownBlock(bufferRef.current)) {
      // 长 code fence 容错：最后一个 \n 处强制切
    }
    // 首切片启动定时器；后续切片合并到同一次提交
    if (!emitTimerRef.current) {
      emitTimerRef.current = setTimeout(drainPending, COMMIT_BATCH_MS)
    }
  }
  // ... drainPending / flushBuffer / resetBuffer 见下
}

输出侧有三个回调——drainPending 定时器的常规提交、flushBuffer 工具调用前的强制刷出、resetBuffer 被中断后的丢弃残留：

const drainPending = () => {
  const combined = pendingChunksRef.current.join('')
  if (combined) {
    appendMessage({ role: 'assistant', content: combined, streamingChunk: true })
  }
  pendingChunksRef.current = []
  emitTimerRef.current = null
}

const flushBuffer = () => {
  // 残留挪进 pending、清定时器、立即 drain
  if (bufferRef.current) pendingChunksRef.current.push(bufferRef.current)
  bufferRef.current = ''
  if (emitTimerRef.current) {
    clearTimeout(emitTimerRef.current)
    emitTimerRef.current = null
  }
  drainPending()
}

const resetBuffer = () => {
  // 三个 ref 全清，不 drain（残留直接丢）
  bufferRef.current = ''
  pendingChunksRef.current = []
  if (emitTimerRef.current) {
    clearTimeout(emitTimerRef.current)
    emitTimerRef.current = null
  }
}

26.2 findSafeBoundary——按安全边界切，不按段落切

// 从尾部向前扫描，找最晚的"安全单 \n"切点
function findSafeBoundary(text: string): number {
  let scan = text.length
  while (scan > 0) {
    const found = text.lastIndexOf('\n', scan - 1)
    if (found < 0) return -1
    const prefix = text.slice(0, found + 1)
    if (!hasOpenMarkdownBlock(prefix)) return found + 1
    scan = found
  }
  return -1
}

hasOpenMarkdownBlock(prefix) 检测两种未闭合结构：一是奇数个 ```，表明当前还在 code fence 内部，在此处切割会把 code fence 切断；二是末行以 | 开头的 markdown 表格行——表格至少需要表头、分隔行、数据行三行才能被 marked.lexer 识别为 table token，在行数不足时切割会导致切出去的片段无法被解析为表格。下面通过两个例子说明这个算法的具体工作过程。例 1 是 buffer 当前正好停在 code fence 中间的情况：

bufferRef 当前内容（每行末尾的 \n 是潜在切点）：
   ┌─────────────────────────────────────────────┐
   │ 你好。\n                ← ✓ 安全切点         │
   │ 这是代码示例：\n        ← ✓ 安全切点         │
   │ ```ts\n                 ← ✗ 切了会把 fence 切断│
   │ const x = 1;\n          ← ✗ 在 fence 内部     │
   │ console.log(x);         ← (还没换行)         │
   └─────────────────────────────────────────────┘
            │
            │ findSafeBoundary 从尾部向前扫，跳过 fence 内的 \n
            ▼
   返回最晚安全切点：第 2 行末尾
   切 "你好。\n这是代码示例：\n" 进 pendingChunks
   剩下 "```ts\nconst x = 1;\nconsole.log(x);" 留在 bufferRef，
   等下游 delta 把 fence 闭合（再来一个 ``` ）再切

例 2 是 buffer 停在表格中间的情况：

   ┌─────────────────────────────────────────────┐
   │ 这是一个表格：\n        ← ✓ 安全切点         │
   │ | 列名 | 类型 |\n       ← ✗ 末行是表格行     │
   │ | ---- | ---- |         ← (还没换行)         │
   └─────────────────────────────────────────────┘
            │
            ▼
   切 "这是一个表格：\n"，剩余部分留在 bufferRef 等表格行完整闭合

读者可能会问，为什么按单个 \n 切而不是按段落分隔符（\n\n）切。原因在于按段切会产生成块出现的效果，长回答会一段一段弹出来；按行切则让每行依次落定，更贴近打字机式逐行流出的阅读节奏。

26.3 streamingChunk 标记与片段拼接

回到开头的示例：模型的回答被 readFile 工具调用分成了前后两段，但用户看到的是一段连贯的文字，中间没有多余的空行或分隔线。这个视觉效果靠的是 streamingChunk 标记。缓冲区每次刷出时，累积的文本作为一条 DisplayMessage 推给 messages 数组，这条消息带有 streamingChunk: true 标记。普通 assistant 消息末尾会自动加一个空行（在视觉上分隔多条消息），而带 streamingChunk 标记的消息不加——这样多个片段在终端上连续成一段，用户看到的不是一条一条独立的消息，而是同一段文字逐段出现。直观对比：

streamingChunk: false（普通 assistant 消息）：
   ┌─────────────────────────────────┐
   │ 好的，我帮你看一下这个文件。      │
   │                                  │  ← 末尾自动加空行
   ├─────────────────────────────────┤
   │ 这个文件的作用是 ...              │
   │                                  │  ← 末尾自动加空行
   └─────────────────────────────────┘
   视觉上：两条独立消息（有分隔感）

streamingChunk: true（流式中途刷出的片段）：
   ┌─────────────────────────────────┐
   │ 好的，我帮你看一下这个文件。      │  ← 末尾不加空行
   │ 这个文件的作用是 ...              │  ← 末尾不加空行
   │ 它实现了 ...                      │
   └─────────────────────────────────┘
   视觉上：同一段文字逐段出现（连续感）

26.4 只读工具组折叠：连续只读工具折叠成一行摘要

流式输出还有一个相关的 UI 优化——模型频繁连发只读工具调用时（readFile / glob / grep / listDir），UI 不逐工具铺行展示，而是把整段缓存起来，等到链条结束（出现非只读工具 / text-delta 片段 / 一轮结束 / 用户中断）才一次性输出一行摘要：

 ● Read 4 files(README.md, package.json, package.json, +1 more)

为什么要折叠？coding agent 在回答「看一下这个项目」「修一下 X 模块」这类问题时，模型常常连续发出多个只读工具调用——多数是 readFile 读源码，也会穿插 glob 找文件、grep 找符号、listDir 看目录。如果每一次工具调用都在终端历史区铺一行，看起来会是这样：

 ● ReadFile src/index.ts            ← 模型连续发出的 8 次只读工具
 ● ReadFile src/app.tsx                各自占一行 → 屏幕被刷满
 ● ReadFile src/components/A.tsx       用户实际想看的回答被推到屏幕外
 ● ReadFile src/components/B.tsx       （往上滚才能找到）
 ● ReadFile src/components/C.tsx
 ● ReadFile src/utils.ts
 ● ReadFile src/hooks/useAuth.ts
 ● ReadFile src/api/client.ts

8 次只读工具调用意味着至少 8 行屏幕空间被占用，而这些信息对用户的价值很低——读了什么文件只是模型推理过程的中间步骤，不是最终结论。折叠成一行摘要后有两种典型形态：

 ● Read 8 files(index.ts, app.tsx, A.tsx, +5 more)        ← 纯 readFile 链条
 ● Read 1 file, listed 2 directories(index.ts)            ← 混合多类只读工具

8 行变 1 行，节省出来的屏幕空间留给模型真正的回答。摘要括号里只放 readFile 的文件名，grep / glob / listDir 不进入摘要详情，因为这些工具的参数（搜索模式、glob pattern、目录路径）对一行摘要的价值不大。只读工具的副作用为零，折叠不丢失任何用户需要的状态信息；如果中间出现写操作（writeFile / edit / shell），折叠链条立刻结束，写工具单独成行展示——原因在于写操作影响真实文件系统，每一次都应当让用户看到。折叠期间进度指示器文案从 Thinking… 切换到 Reading…，让用户知道模型正在读取文件而非陷入沉默。链条结束时 CLI 把累积的各类只读工具调用次数汇成首字大写、逗号连接的标签，再附上前 3 个文件名作为摘要。

26.5 小结

本章围绕一个核心问题展开：模型每秒产生几十个只携带几个字符的 text-delta，如何在不触发 Yoga CJK 宽度计算错误的前提下让用户看到逐行流出的文字。useStreamBuffer 的设计思路是两段缓冲加合并窗口——先在 bufferRef 中累加原始文本，扫描到安全 markdown 边界（不在未闭合的 code fence 或表格中间）时切片放入 pendingChunksRef，再由 150ms 定时器把多个切片合并成一次 appendMessage 提交。三个强制刷出时机（工具调用前、一轮收尾、一轮中断）保证缓冲区不会在关键节点残留未显示的文本。提交时每个片段已经走完 markdown 渲染，没有纯文本到 markdown 的二次刷新跳动。
