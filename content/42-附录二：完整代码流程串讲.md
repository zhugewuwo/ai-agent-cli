## B.2 架构概览

两个核心包 `cli` → `core` 构成单向依赖，详见 Ch.04。

渲染层面，Ink 动态区始终为空，`App` 组件只返回单个 `<ChatInput />`，没有 Ink 子树。所有 UI 元素（输入框、进度指示器、对话框、终端历史区提交）都由 `<ChatInput>` 自己通过 cell 级别 diff + `process.stdout.write` 渲染。Yoga 抖动溯源与 cell buffer 实现详见 Ch.23 和 Ch.24。

下面这张终端区域示意图作为速查（按区域划分 ChatInput 内部 cell buffer 的渲染元素）：

## B.4 具体示例

用户输入：「帮忙分析一下项目产品功能以及优化点」

### 完整执行流程

```

1. 用户在终端输入 "帮忙分析一下项目产品功能以及优化点"，按 Enter

2. ChatInput 组件
   └─ onSubmit("帮忙分析一下项目产品功能以及优化点")

3. App.handleSubmit()
   └─ 非 / 开头，走普通提交路径
   └─ submit("帮忙分析一下项目产品功能以及优化点")

4. useAgent.submit()
   ├─ initialize() (首次)
   │ └─ 加载 AutoMemory (用户级 + 项目，驱逐 90 天前条目)
   │
   ├─ setState
   │ → messages 追加用户消息
   │ → isLoading = true
   │
   │ [终端显示]
   │ > 帮忙分析一下项目产品功能以及优化点
   │ ⠋ Thinking...
   │
   ├─ 构建 callbacks
   └─ agentLoop("帮忙分析一下项目产品功能以及优化点", model, options, callbacks)

5. agentLoop() — 第一轮
   ├─ messages: [{ role: 'user', content: '帮忙分析一下项目产品功能以及优化点' }]
   │
   ├─ buildKnowledgeContext()
   │ → 拼接用户级/项目 AGENTS.md chain、auto memory、local preferences
   │
   ├─ buildSystemPrompt()
   │ → 完整 system prompt (约 2000-3000 tokens)
   │ → 包含: 身份、工具列表、规则、环境信息、知识上下文
   │
   ├─ streamText({ model, system, messages, tools })
   │ → API 请求发送到 AI Provider (如 Anthropic)
   │
   ├─ AI 决定先了解项目结构，返回 tool-calls:
   │ ├─ tool-call: glob({ pattern: "**/\*.{ts,tsx,json}" })
   │ └─ tool-call: readFile({ filePath: "package.json" })
   │
   │ [终端显示 —— 只读工具(glob/readFile/listDir/grep)走 read-group collapser，
   │  ChatInput frame 上**不**显示逐 tool 的 ⠋ Running… live 行;只显示
   │  spinner 文案翻成 "Reading…":
   │ ⠋ Reading… (3s · esc to interrupt)
   │
   ├─ finishReason = 'tool-calls'
   ├─ processToolCalls()
   │ ├─ glob → 自动执行 (always-allow) → 返回文件列表
   │ └─ readFile → 自动执行 (always-allow) → 返回 package.json 内容
   │
   │ [工具完成后,read-group collapser 暂存,**不**立刻 commit。
   │  等链条结束(出现非只读工具 / text-delta / turn 结束)再一次性
   │  flush 成一行摘要 —— 见下面"轮 3 末尾"的合并形式。]
   │
   └─ continue (进入下一轮)

6. agentLoop() — 第二轮
   ├─ messages 现在包含: user + assistant(tool-calls) + tool-results
   │
   ├─ streamText() → AI 继续分析
   │
   ├─ AI 可能再次调用工具读取更多文件:
   │ ├─ readFile({ filePath: "packages/core/src/index.ts" })
   │ ├─ readFile({ filePath: "packages/cli/src/ui/components/App.tsx" })
   │ └─ listDir({ path: "packages/core/src/tools" })
   │
   │ [终端显示 —— 仍然在只读链中,collapser 继续累积,frame 仍只
   │  显示 "Reading…" spinner,不逐 tool 出 live 行]
   │
   └─ continue

7. agentLoop() — 第三轮 (可能更多轮)
   ├─ AI 已获得足够信息，开始生成分析报告
   │
   ├─ streamText() → AI 返回纯文本分析 (finishReason = 'stop')
   │
   ├─ 第一个 text-delta 到达 → bufferingReads = false（spinner 切回 "Thinking…"），
   │  read-group collapser flush:
   │  在 scrollback 里写一行
   │    ● Read 6 files, listed 1 directory (package.json, index.ts, App.tsx, +3 more)
   │    ⎿
   │  (label 粗体,detail 蓝紫色,样式与单工具行对齐)
   │
   ├─ 流式输出过程（按"安全单 \n 切点"逐行 commit，150ms 合并窗口去抖）:
   │ ├─ text-delta: "## 项目产品功能分析\n\n"
   │ │ → callbacks.onTextDelta(delta)
   │ │ → useStreamBuffer.bufferRef.current += delta
   │ │ → findSafeBoundary 找到末尾安全 \n → queueChunk(prefix)
   │ │ → 150ms 窗口合并多个 chunk → drainPending → appendMessage
   │ │ → setState: messages 追加 { role: 'assistant', content: chunk, streamingChunk: true }
   │ │ → ChatInput useEffect: writeMessageToStdout → renderMarkdown → 落到 scrollback
   │ │
   │ │ [终端显示 — 直接到 scrollback, 由 ChatInput 经 process.stdout.write 直写]
   │ │ 项目产品功能分析
   │ │
   │ ├─ text-delta: "### 核心功能\n\n1. 多模型支持..."
   │ │ → 累积至 300 字或下一个 \n\n → 继续 flush
   │ ├─ text-delta: "### 2. 智能工具调用\n..."
   │ ├─ ... (持续段落 flush，每段独立 scrollback 写入)
   │ └─ text-delta: "### 优化建议\n..."
   │
   └─ finishReason = 'stop' → break 退出循环

8. 回到 useAgent.submit()
   ├─ flushBuffer() // drain buffer 的最后一段残留到 messages
   │
   ├─ 安全网：若本轮 onTextDelta 从未触发
   │ → extractLastAssistantText(loopState.messages) 降级取文本
   │ → 追加为 assistant message
   │
   ├─ setState({
   │ isLoading: false,
   │ activeToolCalls: [],
   │ })
   │
   │ [终端最终显示 — 所有 message 已在 scrollback 里]
   │
   │ ❯ 帮忙分析一下项目产品功能以及优化点 ← user message (writeUserMessage)
   │
   │ ● Read 6 files, listed 1 directory ← 只读链摘要 (formatReadGroupSummary)
   │ ⎿ (package.json, index.ts, App.tsx, +3 more)
   │ ← AI 回复 (按行 flush 拼接)
   │ 项目产品功能分析 ← h2, bold + underline + accent blue
   │
   │ 核心功能 ← h3, bold
   │
   │ 1. 多模型 AI 对话 ← ordered list
   │ 支持 Anthropic, OpenAI, Google,
   │ DeepSeek 等多个 AI 服务商...
   │
   │ 2. 智能工具调用
   │ 11 个内置工具: 文件读写, Shell 执行,
   │ 代码搜索, 网络搜索...
   │
   │ 3. 知识管理系统
   │ - 分层知识加载 (用户级/项目/本地)
   │ - AutoMemory 自动记忆
   │ - 会话持久化与恢复
   │
   │ ...
   │
   │ 优化建议
   │
   │ 1. 性能优化
   │ - 工具结果截断阈值可配置化
   │ - 流式刷新频率自适应
   │ ...
   │
   │ > █ ← ChatInput 重新可用
   │
   └─ 等待用户下一次输入

```

### AI 回复中可能的工具调用序列示意

对于“分析项目产品功能以及优化点”这类问题，AI 可能执行如下工具调用链：

```

Turn 1: AI 需要了解项目结构
├─ glob({ pattern: "\*\*/package.json" }) → 找到 monorepo 结构
```

### 会话内动态刷新：`refreshPluginContributions` 单一入口

启动序列把 plugin、skill、command、MCP、hook 都装在了对应 registry 里。但 registry 是一次性加载、会话内冻结的。如果会话期间用户装了新插件、改了订阅或修改了 user-config，要让 CLI 看见新状态该怎么处理？

X-Code CLI 不做 fs.watch 自动检测，而是要求用户显式执行 `/plugin refresh`（详见 Ch.39 决定四）。这个命令背后是 `refreshPluginContributions()` 一个单一入口，五件事按固定顺序执行：

```
PluginRefreshTargets 字段:
  pluginRegistry: PluginRegistry        // 必填 — 主 registry, 永远需要重 reload
  skillRegistry?: SkillRegistry         // 可选 — 不传则跳过 skill 折回
  subAgentRegistry?: SubAgentRegistry   // 可选 — 不传则跳过 sub-agent 折回
  commandRegistry?: CommandRegistry     // 可选 — 不传则跳过 command 折回
  hookBus?: HookBus                     // 可选 — 不传则跳过 hook bus 折回
  mcpRegistry?: McpRegistry             // 可选, 必须跟 askUser 一起传才会触发 MCP 重启
  askUser?: LoadOptions['askUser']      // 可选, 跟 mcpRegistry 配对
  cwd?: string                          // 可选, 默认 process.cwd()

refreshPluginContributions(targets):
  ├─ loadAllPlugins({ cwd })
  │    重读 installed_plugins.json + 项目级目录 + enabledPlugins 状态
  ├─ targets.pluginRegistry.reload(load.registry.listAll(), [...loadErrors()])
  │    替换主 registry 内的插件列表, 保留对象身份(所有持有引用的下游继续有效)
  ├─ buildPluginIntegration(load)
  │    重新算出 agentsDirs / skillsDirs / commandsDirs / mcpServers / hookBus
  ├─ 折回四个子 registry — 都用 reload-in-place 保留对象身份:
  │    if (targets.skillRegistry)    reloadSkillRegistry(..., { extraDirs })
  │    if (targets.subAgentRegistry) reloadSubAgentRegistry(..., { extraDirs })
  │    if (targets.commandRegistry)  reloadCommandRegistry(..., { extraDirs })
  │    if (targets.hookBus)          targets.hookBus.replaceRegistry(integration.hookRegistry)
  └─ 重启 MCP 服务器 (条件: mcpRegistry + askUser 都传了才走):
       loadMergedConfigsFromDisk({extraServers}) →
       targets.mcpRegistry.restartAll(merged.configs)
```

每个子 registry 都是可选的，`--no-plugins` 启动时上层不传 skillRegistry / subAgentRegistry，refresh 时这几步自动跳过。MCP 重启条件更特殊：必须 `mcpRegistry` 和 `askUser` 都传才执行（`askUser` 用于处理项目级 MCP 信任对话）。

CLI 端 `handleRefreshPlugins` 还做两件事：调 `invalidateSystemPromptCache()` 作废 system prompt cache（同 `/skill refresh` 第 1 步），输出文案告诉用户下一条消息会 cache miss 一次。

选择单一入口的原因在于五件事必须按上述顺序执行：先重扫拿到新插件列表，再计算 integration 拿到 extraDirs，再折进各子 registry。任何一步顺序错位都会让某项扩展不可见。把这条流程封装在一个函数里，CLI 的两个调用点（`/plugin refresh` slash 命令和 `/mcp refresh` 单独执行时也走类似路径）就不会因为漏写一步导致 silent data loss。

```typescript
{
  messages: initialSession ? modelMessagesToDisplay(...) : [],
                                   // resume 时直接用 session 的消息填充，第一帧
                                   //   就有历史 scrollback；fresh launch 是空数组
  isLoading: false,                // 加载状态

                                   //   { id, toolName, input, progress?, subToolHistory? };
                                   //   完成时按 id 移除）
  shellOutput: '',                 // Shell 实时输出（保留数据，frame 上不直接显示）
  permissionQueue: [],             // 待用户确认的权限请求队列（FIFO，按 toolCallId 去重）
  pendingQuestion: null,           // askUser / /model / /theme / /resume 等交互选择
  usage: initialSession ? { ...session.tokenUsage } : {

    cacheReadTokens: 0, cacheCreationTokens: 0,

  },
  error: null,

                                   //   AgentOptions.trustMode 旁路，跳过所有权限确认含 deny）
                                   //   plan = 只读 + 必须 enterPlanMode 提交后才能改文件

  bufferingReads: false,           // 进入连续只读工具链（Read/Glob/Grep/ListDir）
                                   //   时翻 true，驱动 spinner 文案从 "Thinking…"
                                   //   切到 "Reading…"。任何非只读工具 / 文本流 /
                                   //   abort / loop 结束都会翻回 false。
  compressionLabel: null,          // 压缩阶段的 spinner 文案（如 "Compressing — light compact"）;
                                   //   非空时 spinner label 显示 `Compressing — ${label}`,
                                   //   优先级高于 bufferingReads / 默认 "Thinking…"

```

> 注：权限请求是队列而不是单值。同一轮 `processToolCalls` 里可能触发多次 `onAskPermission`（例如 AI 一次返回多个 edit 调用），UI 逐个弹出，这些权限对话框在 ChatInput 内部的 cell buffer 里渲染。

> 注：`activeToolCalls` 是数组而不是单值，因为 AI SDK 在一个 turn 里可能并行发出多个 tool call（`tool-call A`，`tool-call B`，`tool-result A`，`tool-result B`）。每个 `ActiveToolCall` 含可选 `progress` 字段（工具内部通过 `reportProgress(toolCallId, msg)` 流式上报“当前在做什么”，取代默认的 `Running…` 占位）和可选 `subToolHistory`（task 工具委派子 agent 时把子 agent 的 tool-call 汇成一行 progress 反馈给父级）。
>
> 注：`flushBuffer()`（刷出流式文本）和 `setState`（push 进 activeToolCalls）在同一同步 tick 完成，靠 React 18 自动批处理折叠成一帧。快工具会闪一下 “Running…” 行（~1 帧），慢工具（WebSearch / shell / 网络）的 text→tool-call 过渡没有可见闪烁。

> 注：没有独立的 streamingText state。`useStreamBuffer(appendMessage)` 每次 delta 进 bufferRef，在安全 markdown 边界（table/code fence 不被切断）切片，150ms 合并窗口内的多个切片合并成一次 `appendMessage`。每次提交直接落进 `messages`，ChatInput useEffect 把它经 `writeMessageToStdout` 写到终端历史区。不在 cell buffer 里做半截 markdown 预览，避免提交前后的视觉跳动。详见 B.10 节的「流式文本累积策略」。

几个设计要点：

- `<ChatInput>` 通过 props 接收所有动态信息，内部构建 cell buffer 一帧。
- ChatInput 自己根据 `permission`/`selectRequest` 是否存在决定键盘路由，无需外层 `disabled`/`hidden` prop。加载中不锁键盘（允许预输入下一个问题，Enter 被 `spinner != null` 守卫忽略）。
- 整个 useEffect 包在 DEC 2026 `\x1b[?2026h` / `\x1b[?2026l` 同步更新块里，终端历史区内容 + frame diff 一次原子写入，消除「擦了再画」的闪烁。
- 底栏行（输入框下分隔线下方）由窄 cell 序列组成：左侧 `notice` / `· plan mode · /plan to toggle` / `· accept edits`（互斥，优先级 notice > plan > acceptEdits）；右侧 `6.6k / 200k · 3%` 进度条（读 `contextUsage`）。两侧都为空则整行省略。底栏不右对齐到 `termWidth-1`，原因在于末 cell 落在终端 wrap-column 时，xterm.js 的 BSU/ESU 同步路径会在每次 commit 的 LF 自动滚动时把残留 cell 漏进终端历史区，留下幽灵「Thinking…」行。

## B.7 阶段三：用户输入处理

组件：`cli/src/ui/components/ChatInput.tsx`
输入 Hook：`cli/src/ui/hooks/use-prompt-input.ts`
Paste 辅助：`cli/src/ui/paste-refs.ts`

### 输入管线：`usePromptInput`

ChatInput 自己挂 stdin 监听（Ink 自带的 `useInput` 不认 bracketed paste 标记，大粘贴会被拆成多个 chunk 逐字处理）。stdin 三层分流：

1. **bracketed paste 快路径**：`\x1b[200~` / `\x1b[201~` 包裹的整块走 `onPaste`
2. **30ms 防抖托底**：老终端（cmd.exe）不支持标记时，依赖时间窗口区分逐键和粘贴突发
3. **单段大小判定**：防抖刷出时内容 ≥ 32 字符或含 `\n` 视为粘贴，否则视为文本

paste 入口统一做 `\r\n?/g → \n` 归一化（裸 `\r` 在终端里会被当 carriage return 覆盖之前的字符）。完整实现 + 阈值常量论证详见 [Ch.24。

### ChatInput 的 onPaste / onText / onKey 处理

```

  ├─ lineCount = content.split(/\r\n|\r|\n/).length

  │    └─ 否 → setText(text + content)           // 短粘贴内联
  │
onText(chunk)

  //  setCompletionIndex(0)

       ├─ 若文本末尾是 [Pasted text #N ...] → 整体剥离整个 ref + 从 pastedContents 删除对应 id
       └─ 否则 → text.slice(0, -1)              // 删一个字符
```

### 多行渲染 + 上限

### 权限系统详解

三级 `PermissionLevel`（`always-allow` / `ask` / `deny`） + Shell 智能分级（`splitShellCommands` / `isReadOnly` / `isDestructive`，混合命令 → `ask`） + Trust Mode（`--trust` 跳过所有权限确认，含 deny 级）。详见 Ch.29；对话框 UI（edit 走结构化 diff + `(a)ccept-edits` 切 `permissionMode`）详见 Ch.28。

### 子 Agent 嵌套循环

当父 turn 命中 `tool-call: task({ agentName, prompt, model? })` 时，`processToolCalls` 走 `runSubAgent` 而不是普通 execute：

```

  │      name, description, longDescription,    // longDescription 进父 prompt
  │      tools: ['readFile','glob','grep',...], // 白名单, 派生新 toolRegistry
  │      systemPromptOverlay,                   // 子 agent 专属 prompt 段

  │    }
  │
  ├─ 2. 派生 nested LoopState（独立、不继承父 messages）
  │    subState = createLoopState('default')        // 普通 LoopState,无 parentSessionId
  │                                                 //   / depth / transcriptPath 这类字段
  │    subState.systemPromptCache = subSystemPrompt // 预填子 agent 专属 prompt
  │                                                 // 递归靠 subAgentRegistry: undefined 阻断,
  │                                                 // 不靠 depth 字段计数
  │
  ├─ 3. 派生 child callbacks
  │    subCallbacks = {
  │      onTextDelta:  delta  => parentCallbacks.onSubAgentEvent({ kind:'text-delta', ... })
  │      onToolCall:   ...    => parentCallbacks.onSubAgentEvent({ kind:'tool-call', ... })
  │                              + onToolProgress(toolCallId, '<subTool>: <preview>')
  │      onUsageUpdate: () => {}   // no-op；子 token 在 agentLoop 返回后
  │                                //   由 runner 直接累加到 parentState.tokenUsage
  │      onAskPermission: ... => 父 permission queue (统一审批)
  │    }
  │
  ├─ 4. await agentLoop(prompt, model, subOptions, subCallbacks, subState)
  │     其中 subOptions.subAgentRegistry = undefined —— 这就是禁止 task 工具
  │     套 task 工具的硬约束:子 agent 的 buildTools 看到 registry 是 undefined
  │     就不注册 task 工具,模型连这个工具名都看不到
  │
  └─ 5. 把 child 的 finalText 当作 tool-result 回灌父 turn
       parent.tool-result = { toolUseId, output: childFinalText, usage: childUsage }
```

在 UI 层面，父 ChatInput 的 `activeToolCalls[]` 里 task entry 显示 `▼ Task(agentName)` + 子 turn 的 progress 行；深度 ≥1 的 entry 在左侧多一道竖线缩进，与 markdown blockquote 视觉一致。详见 Ch.19。

### Plan Mode 约束机制

Plan 模式下「模型只能调读 + `enterPlanMode` / `exitPlanMode` / `todoWrite` / `task`（只读子 agent）」的约束由 system prompt overlay 强制（`system-prompt.ts` 里的 plan-mode overlay，`permissionMode === 'plan'` 时拼到 base prompt 末尾），模型被 prompt-level hard rule 禁止调写工具。如果模型不遵守仍 emit `writeFile` / `edit` / `shell` tool-call，代码里没有专门的 `isWriteTool` 拦截将其替换成合成 error tool-result，而是仍走普通 `permission` 流程：`default` 模式下用户在对话框拒绝即可；`acceptEdits` 模式（用户 exitPlanMode 批准后翻到这档）则写工具自动放行，这是设计意图。

工具集合本身在 plan 模式下也不被剔除，`buildTools(options)` 只看 `subAgentRegistry` + `toolFilter`，不看 `permissionMode`。

详见 Ch.21。

## B.10 阶段六：终端 UI 渲染

### 渲染架构

X-Code CLI 用 Ink（React for CLI）渲染终端 UI，但消息历史完全不走 Ink 的布局引擎，而是直接打到终端的滚动缓冲区。Ink 只管底部一小块动态区。

```
┌─────────────────────────────────────────┐
│  终端滚动缓冲区 (由终端自己管理)           │  ← 不走 Ink 布局
│  - 启动 Banner (printHeader, Ink 外)     │
│  - 历史消息 (走 ChatInput 内部提交)       │
│    - 用户消息: "❯ 问题内容"               │
│    - AI 回复: Markdown 渲染后的文本       │
│    - 工具调用记录 (committed 后落进 scrollback) │
├─────────────────────────────────────────┤
│  Ink 动态区 (永远是空)                   │
│  - 没有任何 Ink 子节点；ChatInput 独占底部 │
│  - askUser / 权限 / 选择菜单 / spinner / │
│    错误 / 输入框全部在 ChatInput cell     │
│    buffer 里渲染                          │
├─────────────────────────────────────────┤
│  <ChatInput> cell buffer (浮动定位)     │  ← cell-level diff + BSU/ESU 同步更新
│  - 内容少时 frame 紧贴最后内容行下方;    │
│    内容多到撑满屏幕后 frame 自然到底部   │
│  - Error 行  (可选)                      │
│  - 工具调用 live 状态 (运行中, 完成后    │
│    会 commit 到 scrollback)              │
│  - Permission 对话框 (含键盘路由)       │
│  - Thinking... spinner                   │
│  - ─── 输入框顶部分隔线                  │
│  - 输入框 (多行 textarea)               │
│  - ─── 输入框底部分隔线                  │
│  - / 补全菜单 (可选)                    │
└─────────────────────────────────────────┘
```

为什么消息历史不走 Ink 布局、Ink 动态区永远为空、对话框统一进 ChatInput cell buffer，详见 Ch.23（Yoga 抖动溯源 + 混合方案）。

### 消息写入管线（`stdout-writer.ts` + ChatInput useEffect）

```
use-agent.ts setState({ messages: [...prev, newMsg] })
  │
  └─ React commit
       │
       └─ ChatInput useEffect 触发（无 deps，每次 render 都跑）
            │
            ├─ 进入 DEC 2026 同步更新块 \x1b[?2026h (BSU)
            │
            ├─ 检测 messages.length > writtenMessageCountRef.current?
            │   │
            │   └─ 是 (有新消息要 commit) →
            │      ├─ 收集 scrollbackContent (各条 message 走
            │      │   writeMessageToStdout 拼成一个大字符串)
            │      ├─ 计算 startRow / preScrollRows / leftoverBlanks
            │      ├─ 按需在 termRows 行写 \n 触发 auto-scroll
            │      │   (把顶部行推入终端 scrollback 历史)
            │      ├─ \x1b[startRow;1H\x1b[J  擦旧 frame 区
            │      ├─ 写 scrollbackContent (行内插入)
            │      └─ 重绘 frame at 新的 frameTop (浮动定位)
            │
            ├─ 帧高变化 (spinner 出现/消失,permission 开关) →
            │  按 grow/shrink 路径处理 (consume freeBlanks 或 preScroll)
            │
            ├─ cell-level diff 对比 prevFrameRef 只写差异
            │  per-row 绝对定位 \x1b[absRow;colH (不走相对 walk)
            │  未变行完全跳过 (不踢渲染状态机)
            │
            └─ 结束 \x1b[?2026l (ESU)
               不发 \x1b7 (DECSC) —— 会跟 fork 内部的 log-update
               抢同一个 cursor 寄存器
```

`writeMessageToStdout` 的消息格式化流程如下：

```
writeMessageToStdout(write, msg)
  ├─ 归一化 \r\n / \r → \n
  ├─ user message     → write("❯ <line1>\n  <line2>...\n\n")
  ├─ assistant toolCalls:
  │   每个 tc 顺序写:
  │     ├─ ` ● Tool(preview)`           ← 绿色 ● + 粗体 label + 蓝紫色 input
  │     ├─ tc.editPayload 存在(writeFile/edit) →
  │     │   render-diff.ts 输出主题化彩色 unified diff:
  │     │     ` ⎿  src/index.ts (file edit)`
  │     │     `      37 │  const old = '...'`        ← 旧行红 bg
  │     │     `      37 │  const new = '...'`        ← 新行绿 bg
  │     │   diff bg / fg 取自当前 theme(setTheme 设的);syntax 高亮取自
  │     │   syntax-highlight.ts 的当前 palette。窄屏自适应宽度。
  │     └─ tc.editPayload 不存在 → ` ⎿  result_summary (Nms)` 单行摘要
  │   连续被 read-group collapser 缓存的只读工具:在 flush 时机改输出
  │     ` ● Read 3 files (foo.ts, bar.ts, +1 more)\n   ⎿` 摘要格式,详见
  │     上面《折叠连续只读工具（read-group collapser）》小节
  └─ assistant content   → renderMarkdown → 2 空格缩进 → write(indented + '\n\n')
```

几个设计要点：

- `write` 函数是 `(data) => process.stdout.write(data)`，直接进终端 stdout。但实际写入路径是先把终端历史区内容收到一个字符串里，跟 frame 写入合并成一次 `process.stdout.write`，整个提交由外层 BSU/ESU 包成一帧原子提交，杜绝撕裂。
- 提交不做每帧 `eraseRegion()`，而是走「行内插入」路径：`\x1b[startRow;1H\x1b[J` 只擦旧 frame 区，然后写新的终端历史区内容，frame 在新位置重绘，避开了「擦了再画」的双重写入。
- 不发 `\x1b7`（DECSC），避免跟 fork 内 log-update 抢光标寄存器；采用挂载时一次 `?25l` 隐藏光标 + 按行绝对定位的方式替代。
- frame 是浮动定位的：根据 `freeBlanksAboveFrameRef`，frame 上移贴到内容下方；内容撑满屏幕后才钉底。
- 跨终端的工程细节（终端能力差异、副作用写入、节奏失配三类根因，对应光标可见性反复切换、空 BSU/ESU 包装、150ms 提交合并、进度指示器字符选择等）详见 Ch.25。
- 跨平台 Unicode glyph 降级方面，老式 ConHost 缺装饰字符时由 `cli/src/ui/terminal-glyphs.ts` 单点降级（`●→*`、`❯→>`、`⎿→|`、spinner 走 ASCII palindrome）。检测逻辑与完整降级表详见 Ch.25。

### Markdown 渲染

```
renderMarkdown(text)  (cli/src/ui/render-markdown.ts)
  ├─ marked.lexer(text) → AST Token 树 (禁用 del 扩展防 ~/path 误判)
  ├─ renderTokens(tokens) 递归 → ANSI (主题色从 theme.ts import)
  └─ 外层 try/catch 容错 → 半截 fence 时直接 return 原文不崩
```

每类 token 的具体 ANSI 样式（h1/h2 字重、行内 code BLUE_PURPLE、链接 SPINNER_BLUE+OSC 8、列表 / 表格 / blockquote / hr 各样式）详见 Ch.27 主题色表与 token 渲染分支。

### 流式文本累积策略

`useStreamBuffer` hook (`use-stream-buffer.ts`)：

1. `onTextDelta(delta)` 累积到 `bufferRef`
2. `findSafeBoundary(buffer)` 找最晚的“安全单 `\n`”切点（跳过未闭合的 table / code fence；800 字节 + 未闭合 fence 时强制切断）
3. `queueChunk(chunk)` 推入 `pendingChunksRef`，第一个 chunk 来时 `setTimeout(drainPending, 150ms)`（`COMMIT_BATCH_MS` 合并窗口；后续 chunk 加入同一窗口不延期）
4. `drainPending` 合并 chunks → `appendMessage({ role: 'assistant', ..., streamingChunk: true })` → ChatInput useEffect 写到终端历史区

强制刷出时机：onToolCall 前 / submit 收尾 / 轮中断（resetBuffer）。完整实现 + `CODE_FENCE_COMMIT_THRESHOLD` 容错常量 + “按行切 vs 按段切” 取舍详见 Ch.26。

### Spinner / Footer / Todo 面板（cell buffer 内的非滚动元素）

ChatInput 的 cell buffer frame 自下而上依次包含：

```
[error 行]                        ← 仅 state.error 非空
[active tool 块]                  ← activeToolCalls 过滤掉只读后的逐项
                                    ` ● Tool(preview)\n   ⎿  Running…`
[permission 对话框]               ← permissionQueue[0] 存在时
[选择对话框 SelectOptions]        ← pendingQuestion 存在时
[空行]
[todo 面板]                        ← state.todos 非空时
                                     ` ☐ pending item`
                                     ` ▣ in-progress item`         ← 高亮
                                     ` ☑ completed item (灰)`
[Thinking… / Reading…]             ← state.isLoading + 无 modal 时
                                     `⠋ Thinking… (3s · esc to interrupt)`
                                     文案规则:
                                       - state.bufferingReads → "Reading…"
                                       - 否则                 → "Thinking…"
                                     mode (内部用):
                                       - activeToolCalls.length > 0 → 'tool-use'
                                       - 否则                       → 'requesting'
                                     spinner 行不显示 token 计数 —— 计数在 footer
[─── 输入框顶分隔线 ───]
[> 用户输入(支持多行)]
[─── 输入框底分隔线 ───]
[/<command> 补全菜单]              ← 用户在输入 / 时
[footer 行]                        ← 左右两侧任一非空时才显示
   左:                              右:
     · plan mode · /plan to toggle    6.6k / 200k · 3%
     · accept edits
     "Press Ctrl+C again to exit"   ← notice 优先级最高
   右侧 contextUsage 来自 state.usage.currentContextTokens
   (collectTurnResponse 每轮 overwrite,不是累加),分母从
   getContextWindow(modelId) 拿
```

底栏的关键工程细节在于整行用窄 cell 序列，不右对齐到 `termWidth-1`：

```
✓  ` · plan mode · /plan to toggle  6.6k / 200k · 3%`           ← 末 cell 离 wrap-column 还有空白
✗  ` · plan mode · /plan to toggle ........... 6.6k / 200k · 3%` ← 一直补到 termWidth-1,末 cell 落在 wrap 边界
```

末 cell 落到终端 wrap-column 时，xterm.js（VS Code 内置终端）在 BSU/ESU 同步模式下，每次提交触发的 LF 自动滚动都会把残留 cell 漏进原生终端历史区，表现为 frame 上方堆积「Thinking…」幽灵行。走非 LF 自动滚动的 TUI 栈不存在该问题；ChatInput 这条 BSU/ESU + LF auto-scroll 路径必须避开 wrap-column，因此底栏不右对齐。

### writeMessageToStdout 的输出格式

用 `cli/src/ui/utils.ts` 提供的共享显示函数（`getToolLabel` / `formatReadGroupSummary` / `isCollapsibleReadOnlyTool` 等）+ chalk 直出 ANSI：

```

user message (writeUserMessage):
❯ <first line>
<line 2 — 两空格缩进对齐>
<line 3>
...

assistant with toolCalls (formatToolCall):
● ToolName(input_preview) ← 绿色圆点 + 粗体标签
⎿ result_summary (duration) ← 缩进结果 + 耗时
(denied 状态显示为红色)

- bullet
  ...

```

所有路径都先跑 `replace(/\r\n?/g, '\n')` 归一化，防止裸 `\r` 在终端里被当 carriage return（会导致后续字符覆盖之前打印的内容，产生粘贴拼接 bug）。

## B.11 阶段七：退出与清理

### 正常退出流程

```

/exit 命令 或 Ctrl+C 双击
│
├─ 触发源
│    ├─ /exit       → App handleSubmit → cleanup() (await) → exit()（Ink unmount）
│    ├─ Ctrl+C 1 次 → App handleCtrlC：
│    │   ├─ isLoading → useAgent.abort()（取消当前 turn，frame 仍在）
│    │   └─ 设 notice "Press Ctrl+C again to exit"，arm 2 秒窗口
│    │   （此时不退出 —— 用户有 2 秒反悔时间）
│    └─ Ctrl+C 2 次（在 2 秒窗口内）→ Ink exit() → unmount
│
├─ Ink unmount → waitUntilExit() 在 main() 里返回
│
└─ gracefulShutdown(0) (index.ts)
     ├─ cleanup().catch(() => undefined)   // fire-and-forget
     │    └─ saveSession(loopState, model)
     │         └─ flushPendingMessages(state)
     │             把 state.messages.slice(persistedMessageCount) 增量
     │             append 到 <slug>-<sessionId>.jsonl。最后一轮的内容
     │             （/exit 路径上一般已经被 agentLoop 末尾的 flush 写入
     │             过；这里是为 abort / 异常退出容错）。
     │
     │   注：saveSession 只 flush jsonl,不生成 LLM summary、不写
     │   latest.json / <id>.json。摘要以 compact-boundary 行嵌在 jsonl
     │   里（只在压缩时生成），usage 以 meta.usage 行嵌在 jsonl 里
     │   （每 turn 一次）。
     │
     │   cleanup 不被 await —— 进程可能在 flush 写入完成前就 exit。
     │   但 flushPendingMessages 是同步组装 + 单次 fs.appendFile，正常情况
     │   <10ms 完成；极端情况下丢失最后几条 message 是可接受代价。
     │   每轮 turn 顶端的 flush 已经把绝大部分内容写入了。
     │
     ├─ resetTerminal()
     │   → \x1b[0m SGR 重置 + \x1b[?2004l bracketed paste off
     │   + \x1b[?25h 光标显示 + \x1b[?1049l 退出 alt screen + \r\n + setRawMode(false)
     │
     ├─ printResumeHint()
     │   读 getSessionExitInfo() 同步快照（App 通过 onSessionInfoReady
     │   注册的 getter；进程死后才读 React state 是不可能的）。打印一行:
     │     Resume this session: xc --resume <slug-id>
     │   有 taskSlug 时优先 `<slug>-<sessionId>`（人类可读），无 slug 时
     │   退回纯 sessionId。session 没有任何 message（用户启动但没提交）
     │   时跳过 —— 提示也没意义。
     │
     └─ process.exit(0)

```

> 注：退出不打印 token 用量摘要。原因在于 pnpm/tsx 多级 stdout 缓冲会让该行在 shell 提示符之后才闪现，观感像 bug。退出只打印一行「想回看这次会话用 `xc --resume`」的恢复提示。要查看本会话 token 用量，应在交互态使用 `/usage` 命令。

### Ctrl+C 处理（双层）

```

Layer 1 — App.handleCtrlC (主路径，cli/src/ui/components/App.tsx)
├─ ctrlCArmedAtRef = 0  默认值（未 arm）
├─ ctrlCArmWindowMs = 2000
│
├─ 第 1 次按下:
│    ├─ now - ctrlCArmedAtRef >= 2000 → 未在窗口内
│    ├─ ctrlCArmedAtRef = now（arm 2 秒窗口）
│    ├─ if state.isLoading → abort()（取消当前 turn）
│    └─ setNotice("Press Ctrl+C again to exit")
│       2 秒后 useEffect 自动清空 notice
│
└─ 第 2 次按下（2 秒内）:
     └─ now - ctrlCArmedAtRef < 2000 → 在窗口内 → exit()
        → Ink unmount → waitUntilExit → gracefulShutdown(0)

Layer 2 — process.on('SIGINT') (cli/src/index.ts) — 安全网
├─ sigintCount++ + process.exitCode = 0
├─ Layer 1 在 raw mode 下消化绝大多数 Ctrl+C；这里只在
│   Ink 已 unmount 后或 raw mode 已关时才生效
└─ sigintCount >= 2 → resetTerminal + printResumeHint + process.exit(0)
   极端场景: Ink unmount 卡住时跳过剩余的 fire-and-forget cleanup 强退
```

> 两次 Ctrl+C 退出码都是 `0`。区别在于第 1 层的「双击」是 2 秒内用户主动选择退出（取消在第 1 次就发生），第 2 层是托底，即使 Ink 卡死也能让终端恢复可用。

## B.14 小结

从 `xc` 命令启动到用户输入、从 AI 流式回复到工具调用、从终端渲染到退出清理，七个阶段各自对应一组明确的文件入口，B.13 节的文件索引表按阶段做了汇总。

贯穿这七个阶段的有三大共享数据结构：Core 层的 `LoopState`（messages、tokenUsage、sessionId、systemPromptCache、permissionMode、taskSlug、persistedMessageCount、checkpoints 等 18 个字段，生命周期等于整个 CLI 会话）、React 侧的 `AgentState`（messages、activeToolCalls、permissionQueue、pendingQuestion、usage、bufferingReads 等，驱动 UI 渲染）、以及 `SLASH_COMMANDS`（`/help`、`/model`、`/plan`、`/clear`、`/compact`、`/resume`、`/review`、`/memory` 等，在 `handleSubmit` 里分发）。理解这三套结构的分工与同步机制，是读者排查任何具体环节的前提。

在持久化方面，每个会话对应一个 `.x-code/sessions/<slug>-<sessionId>.jsonl` 文件，六种 entry 类型（`meta.header`、`msg`、`meta.usage`、`meta.compact-boundary`、`checkpoint`、`meta.interrupted`）的写入分散在六个 fire-and-forget 函数里，不阻塞主循环。`/resume`、`/usage-history`、`-c`、`-r` 等恢复与查询操作都从同一个 jsonl 文件取数据。在渲染方面，所有 UI 元素只走 ChatInput cell buffer 一条路径，Ink 动态区始终为空，外层用 DEC 2026 BSU/ESU 做原子刷新。在中断方面，一条 `abortSignal` 从 `useAgent.abort` 一路传递到 `agentLoop` → `streamText` → `execa`，中断时 `processToolCalls` 会给所有未完成的 tool_call 补合成 tool-result，保持 tool-call 与 tool-result 的配对不变量，确保下一次 API 请求不被供应商拒收。
