附录三 术语表

本附录是全书术语的集中索引。正文中跨章节复用的术语、缩写和内部标识符按主题分组，每条给出一句话定义并标注详讲章节，方便读者在阅读过程中随时查阅。每个组内按术语首字符 a-z 排序，读者在章节中遇到不熟悉的名词时，可回到本附录查定义并跳转到展开章节。

本附录按以下 7 个主题分组。

  • C.3 供应商与流：多供应商适配、流式处理与缓存策略。
  • C.4 UI 渲染：终端渲染引擎、cell buffer、frame 管理与协议。
  • C.5 上下文管理：会话持久化、压缩、知识加载与记忆提炼。

C.1 Agent Loop

abortSignal

把用户 Esc / Ctrl+C 取消信号从 React UI 一路穿透到 streamText 和 execa 子进程的标准 Web API。runTurn / streamText / 工具 execute 都接 options.abortSignal，缺一环就有孤儿 tool_call。详见 Ch.08。

agentLoop

多轮工具调用的主循环驱动函数，接收用户消息后反复调用 runTurn 直到 finishReason 为 stop、用户 Esc 取消、或可选的 MAX_TURNS 上限触发。生产级实现比 50 行 demo 额外处理会话元数据、cache_control、orphan 修复等 5 类任务。返回 { state, turnCount }，其中 state 是长期会话状态，turnCount 是本次调用的局部计数。详见 Ch.08。

chunk（流式 chunk / 事件）

fullStream 吐出的单个事件。主要类型：text-delta（文本增量）、tool-call（模型决定调工具）、tool-result（工具返回）、reasoning（思维链）、finish（本轮结束带 finishReason）。streamChunksToUI 按类型分流到 UI 不同通道。详见 Ch.10。

classifyApiError

错误恢复层的核心：用 14 条 pattern 把 API / 网络 / 协议异常分类成 retryable: true（可重试）和 retryable: false（不可重试）两档，由 runTurn 的 catch 块据此决定下一步。详见 Ch.11。

collectTurnResponse

runTurn 收尾阶段把 SDK 返回的 response.messages 推入 state.messages 之前先执行 truncateToolResultsInMessages 截断保护，保证下一轮请求体大小可控。详见 Ch.08。

drainStreamResult

stream 结束后对 SDK 内部的 4 个 sibling promise（response / finishReason / usage / toolCalls）附加空 .catch(noop) 处理，防止 NoOutputGeneratedError 等流外错误变成未处理 rejection。在 streamText 返回后、chunk 分流前执行。详见 Ch.10 流式 chunk 处理。

finishReason

AI SDK 流结束时给出的取值之一：stop / tool-calls / length / content-filter。agentLoop 据此决定终止、继续工具调用、续写、还是报错。详见 Ch.08。

LoopState

跨多轮共享的会话级状态容器，含 messages / tokenUsage / sessionId / taskSlug / recentToolCalls / systemPromptCache 等 18 个字段，生命周期等于整个 CLI 会话。本次 agentLoop 调用的轮数计数不在此结构中，它是函数局部变量。详见 Ch.08。

MAX_TURNS

单次 agentLoop 调用的可选轮数上限。交互模式不传此参数（默认无上限，用户按 Esc 终止）；sub-agent 与 --print 模式各自带具体上限，达到后强制终止循环。详见 Ch.08。

processToolCalls

finishReason === 'tool-calls' 后的执行入口：先 bypass 组（askUser / task / todoWrite / enterPlanMode / exitPlanMode / listMcpResources / readMcpResource）→ loop guard 检测 → permission → 分发到 write / shell。abort 时短路并 push 占位 tool_result。详见 Ch.08。

repairOrphanToolCalls

每轮 stream 之前把 state.messages 里没配对 tool_result 的 assistant tool_call 修补成合法序列，避免供应商报 “tool_use without tool_result”。详见 Ch.11。

runTurn

agentLoop 内的单轮执行单元：前处理（修复 orphan / 降级图像 / cache_control / thinking）→ 调用 streamText（含 maxOutputTokens 参数）→ drainStreamResult 防 rejection → chunk 分流 → 收尾返回 TurnOutcome。详见 Ch.08。

streamChunksToUI

把 streamText 的 fullStream 按 chunk 类型分流到 UI：text-delta 走流式 buffer、tool-call 注册到进度通道、tool-result 触发 truncate、error 进 catch。详见 Ch.10。

sub-agent

task 工具委派出去的子 agent，运行在隔离的 LoopState 中、只把最终 assistant message 返回给父 agent，复用父级的 abortSignal。内置 4 种：explore / general-purpose / plan / code-reviewer。详见 Ch.19。

turn（轮）

agentLoop 反复执行的单元。一轮 = 一次「调用 AI → 获取回复或 tool-call → 必要时执行工具 → 把结果加回消息」的往返。一个用户问题往往需要经历多轮才能完成。runTurn 是一轮的执行函数；本次 agentLoop 调用的轮数计数是函数局部变量，不在 LoopState 上。详见 Ch.08。

TurnOutcome

runTurn 的返回值，判别联合 4 种：{ kind: 'done', finishReason, result } / { kind: 'error' } / { kind: 'retry' } / { kind: 'aborted' }。agentLoop 据此走分支处理（done 内部再按 finishReason 分 stop / tool-calls / length / content-filter；retry 回退 turnCount 重试本轮；aborted 不调 onError 直接 break）。详见 Ch.08。

C.2 工具系统

AllowRule

权限层把“don't ask again”决策固化下来的规则结构，三种匹配策略（exact / prefix / tool），运行时存 session、可选持久化到磁盘。详见 Ch.29。

askUser

向用户提问并挂起等待响应的工具，结果作为下一轮 user message 注入。采用单槽 pendingQuestion + resolve 模式（与 permission 的队列式 permissionResolversRef 结构不同，但交互流程类似）。详见 Ch.18。

BYPASS_LOOP_GUARD_HANDLERS

绕过 loop-guard 检测且自行 push tool_result 的工具白名单：askUser / task / todoWrite / enterPlanMode / exitPlanMode / listMcpResources / readMcpResource，因为这些工具的重复调用属于正常行为。详见 Ch.32。

edit

行级文件编辑工具，按 oldString / newString 做唯一匹配替换；要求 oldString 在文件内唯一，否则模型必须扩大上下文重试。详见 Ch.13。

enterPlanMode / exitPlanMode

让模型进出计划模式的成对控制工具。进入时主 agent 依赖系统提示词约束模型不执行写操作，子 agent 则由 toolFilter 在工具集层面硬禁写工具；退出时把最终 plan 文本作为 user message 注入主对话。详见 Ch.21。

execute

每个工具定义的实际执行函数，接 (input, { toolCallId, abortSignal })；可在内部调 reportProgress(toolCallId, msg) 推流式进度。详见 Ch.12。

glob

按文件名通配符列文件路径的搜索工具，底层走 ripgrep，按 mtime 排序、尊重 .gitignore。详见 Ch.15。

grep

正则搜文件内容的工具，参数包括 pattern（正则）、path（搜索路径）、glob（文件过滤）、headLimit（结果上限）。返回匹配行的文本内容。详见 Ch.15。

hashToolCall

loop-guard 的指纹函数：SHA-256(toolName + '\x00' + stable-stringify(input))，用空字节分隔工具名和参数以避免哈希碰撞。结果推入 recentToolCalls 滚动窗口（存储上限 16，扫描窗口 8）做重复检测。详见 Ch.32。

inputSchema

工具的参数 schema，用 Zod 写、AI SDK 在执行前校验；校验失败时 SDK 发 tool-error chunk 而不是 tool-result，需要 repairOrphanToolCalls 做修复保护。详见 Ch.12。

listDir

列目录条目的工具，结果为扁平列表（子目录名后缀 / 标记），按文件系统原始顺序排列；适合让模型先看结构再选要读哪个文件。详见 Ch.15。

loop guard

外部约束机制：通过 hashToolCall 在最近 8 次调用的滑动窗口中检测重复，软阈值 3 / 硬阈值 5。软阈值触发时注入提示让模型自纠，硬阈值触发时短路调用并 push 假结果。详见 Ch.32。

PER_TOOL_POLICY

按工具名查截断策略的表：readFile / webFetch / webSearch 走 head-tail；grep / glob / listDir 走 head + maxLines = 500；shell 走 head；未登记的工具默认 head-tail。每个方向的工程理由（信息密度分布）详见 Ch.17 决定三。

permissionMode

LoopState 上的会话级权限模式，三档：default / acceptEdits / plan。决定 checkPermission 是否弹对话框、toolFilter 是否拒绝写工具。bypassPermissions 不在 X-Code 这套实现里，对应到 X-Code 的语义是 --trust CLI 参数走 trustMode 旁路，与 permissionMode 是两个不同的开关。详见 Ch.29。

plan mode

模型只读、不写、不执行命令的规划专用 permissionMode。强制方式分两路：主 agent 依赖 PLAN_MODE_OVERLAY 系统提示软约束（模型若不遵守，写工具仍走正常 ask 路径，由用户在对话框中拒绝）；plan mode 下派出的子 agent 才会被 toolFilter 在工具集合层面硬禁写工具。详见 Ch.21。

pushToolResult

手动 dispatch 类工具（writeFile / edit / shell 等）把结果写回 messages 数组的入口。截断由调用方在传入前完成（如 pushSuccessfulToolResult 先调 truncateToolResult 再调本函数），pushToolResult 自身只负责 push 消息、清理进度、通知 UI。AI SDK 自动执行类工具不经由此函数。详见 Ch.17。

readFile

读文件内容的工具，head-tail 截断、支持指定行号范围；与 writeFile 配对走“先读后写”模式。详见 Ch.13。

reportProgress

工具 execute 内部调用、流式上报当前在做什么的接口，结果挂在 ActiveToolCall.progress 字段被 UI 实时展示。详见 Ch.10。

shell

执行 shell 命令的工具，用 execa 子进程、abortSignal 透传以保证 Esc 能 SIGKILL 整条进程树；命中 forbidden patterns 时标记为 deny 级并在对话框显示 [dangerous] 警告，需用户确认后才执行。详见 Ch.14。

subAgentRegistry

CLI 启动时构建、整个会话冻结的子 agent 注册表（built-in + 项目级 .x-code/agents/*.md + 用户级 ~/.x-code/agents/*.md）；新增 agent 需要重启 CLI 才能生效。详见 Ch.19。

task

委派子 agent 的工具：模型给 prompt + 选 sub-agent type，CLI 启动一个隔离的 agentLoop 执行完毕后只把最终 message 返回。子 agent 不能再调 task。详见 Ch.19。

todoWrite

让模型自己维护任务清单的工具：状态 pending / in_progress / completed、强制单一 in_progress。UI 在终端历史区渲染清单视图。详见 Ch.20。

toolFilter

buildTools 和 sub-agent runner 用的工具门控结构（{ allow?: string[]; deny?: string[] }），按 permissionMode 或 sub-agent 定义动态拒绝某些工具。与 permissions/ 目录下的 checkPermission 机制是两个独立的门控层。详见 Ch.29。

toolRegistry

tools/index.ts barrel export 出来的工具总注册表，buildTools(options) 在它基础上叠加 task 工具和 toolFilter 后生成最终 effectiveTools。详见 Ch.12。

truncateToolResult / truncateToolResultsInMessages

工具结果截断器：前者切单条结果（按 PER_TOOL_POLICY），后者在 messages 数组上就地修改 output.value，对 AI SDK 自动执行类工具做截断保护。详见 Ch.17。

webFetch

抓取一个 URL 并把 HTML 转 Markdown 的工具：流式读取 + 10 MB 硬封顶 + 15 分钟 LRU 缓存 + Cloudflare cf-mitigated 检测后 UA 降级 + SSRF 私有 IP / link-local 黑名单。详见 Ch.16。

webSearch

按关键词搜索 Web 的工具，Tavily 优先、Brave 降级备选，description 里注入当前年份提升时效性。详见 Ch.16。

writeFile

写整个文件的工具，要求模型先 readFile 拿到当前内容才能覆盖，避免不带上下文的盲写。详见 Ch.13。

C.3 供应商与流

applyCacheControl

每轮 stream 之前对 system + messages + tools 注入供应商特定的 cache 控制元数据：Anthropic 显式 cache_control breakpoint（共 4 个：system / 最后一个 tool / 最后两条消息）、OpenAI 注 promptCacheKey、自动 prefix caching 的供应商无需额外处理。详见 Ch.33。

cache_control

Anthropic 协议里的显式缓存 breakpoint 字段：在 system / 最后一个 tool 定义 / messages 上标 { type: 'ephemeral' } 让前缀进缓存，命中后按约 10% 价格计费；每请求最多 4 个 breakpoint。详见 Ch.33。

cacheReadTokens / cacheCreationTokens

X-Code CLI 在 token 用量里上报的两个细分字段：本轮命中缓存读了多少 token、新写入缓存的多少。cacheCreationTokens 来自 AI SDK inputTokenDetails.cacheWriteTokens（本项目内部字段名为 cacheCreationTokens）。结合定价能算出真实节省。详见 Ch.33。

createProviderRegistry

AI SDK 把多家供应商装进一个 registry 的工厂，调用时按 '<provider>:<model>' 字符串路由到正确的 client。详见 Ch.09。

downgradeBinaryPartsForProvider

针对 DeepSeek / 自定义端点等纯文本供应商，把消息里的 ImagePart 就地替换成本地 OCR（ocrBuffer，基于 tesseract.js）生成的文本描述；多模态供应商走短路。与 vision-fallback 是两个不同机制。详见 Ch.35。

finishReason

见 Agent Loop 组。

fullStream

streamText 返回的统一 chunk 流，含 text-delta / tool-call / tool-result / reasoning / error / finish 等所有事件类型。详见 Ch.10。

generateText

AI SDK 的一次性非流式调用，X-Code CLI 用在会话摘要 / 压缩 / 视觉降级 / 记忆提炼这类后台任务。详见 Ch.04。

getMaxOutputTokens

按 modelId 查“本轮最多让模型输出多少 token”的上限，给 streamText 当 maxOutputTokens 参数；过小会被 finish=length 截断、过大浪费预算。详见 Ch.08。

getThinkingProviderOptions

把统一的 thinking: boolean 翻译成 8 家供应商各自的 thinking 参数（thinking: { type: 'enabled' } / thinkingConfig: { thinkingBudget } / reasoning_effort 等）。详见 Ch.34。

LanguageModel

AI SDK 的统一模型类型，createProviderRegistry 返回的 model 都满足这个接口，下游用 streamText / generateText 时不再关心是哪家供应商。详见 Ch.04。

promptCacheKey

OpenAI 协议里显式的 cache key，让用户标 “下面这段前缀我希望复用缓存”；OpenAI 兼容端点（DeepSeek / Moonshot 等）多数走自动 prefix caching，不需要。详见 Ch.33。

providerOptions

streamText 按供应商透传的参数袋，cache_control / thinking 这类协议差异都装在这里；mergeThinkingOptions 合并时不能覆盖用户已有字段。详见 Ch.34。

PROVIDER_DETECTION_ORDER

启动时按这个顺序探测环境变量，第一个有 key 的就当默认供应商。X-Code CLI 把 DeepSeek 排首位（面向国内开发者的有意选择）。详见 Ch.09。

reasoning_content

DeepSeek-V4 在多轮 thinking 模式下把思维链单独放在这个字段；上游 SDK 存在兼容问题时 ensureReasoningContentParts 做 shim 将其写回 messages 以保持 cache 命中。详见 Ch.34。

reasoning_effort

OpenAI o-series 模型的 thinking 参数，由 getThinkingProviderOptions 从统一布尔翻译而来：true 映射为 'high'，false 映射为 'minimal'。详见 Ch.34。

streamText

AI SDK 的流式入口：传 model + messages + tools，返回 fullStream。X-Code CLI 的 runTurn 围着它构建。详见 Ch.04。

systemPromptCache

LoopState 上保存的系统提示词字节串，整个会话期间必须保持字节级稳定（包括子 agent 列表）才能让 OpenAI 兼容供应商命中自动 prefix caching。详见 Ch.33。

thinking mode

把 8 家供应商不同的“开启推理”机制统一成一个布尔开关，用户用 /thinking on|off 切换、thinkingRef 现读现用做到立刻生效。详见 Ch.34。

vision-fallback

DeepSeek 等纯文本供应商用户贴图时，自动借一个多模态供应商当 caption 子 agent，把图描述成文本注入用户消息；结果 session 内缓存。详见 Ch.35。

C.4 UI 渲染

appendMessage

往 React messages 数组追加一条消息（含 streamingChunk: true 标记），由 ChatInput 的 useEffect 经 writeMessageToStdout 写到终端历史区。详见 Ch.26。

bracketed paste（括号粘贴模式）

终端的工作模式：应用发 ESC[?2004h 开启后，终端会在每段粘贴文本前后插入 \x1b[200~ / \x1b[201~ 标记。usePromptInput 据此把"整块粘贴"和"逐键输入"分开走 onPaste / onText，避免长贴入被当成几千次连续敲键。详见 Ch.25。

BSU / ESU

DEC 2026 同步更新的开启 / 结束序列（\x1b[?2026h / \x1b[?2026l）。一对之间的所有 stdout 写入对用户原子可见，避免边写边渲染产生撕裂。详见 [Ch.24]。

cell

终端按字符格子排布显示，一格称为一个 cell（中文字符占 2 cell）。X-Code CLI 按 cell 粒度做对比和重绘，规避 Ink 按字符串 / 逻辑行的粗粒度测宽问题。详见 Ch.24。

cell buffer

ChatInput 维护的内存 2D 网格，每个 cell 存 { char, style, width: 1 | 2 }；状态变化时算 diff、用绝对定位 \x1b行;列H 跳过去只写变化 cell。详见 [Ch.24。

CJK 宽度

汉字 / 全角符号在终端占两列宽，stringWidth / string-width 等通用库对部分字符算错；X-Code CLI 用 text-width.ts 自维护 Unicode 表绕开。详见 Ch.24。

commit（提交到终端历史区）

把 frame 中的实时行沉淀到 scrollback：工具运行完成后调用 writeMessageToStdout 把最终态写到终端历史区，再从 frame 中移除运行行；AI 流式文本累积到安全切点也执行 commit。本质是「从临时区搬运到永久区」的动作。详见 Ch.26。

COMMIT_BATCH_MS

流式 text-delta 合并窗口（150ms）：首切片 arm timer、期内后续切片合并进同一次 appendMessage，避免连发“段落 → 分隔 → 标题”触发三次大 frame 重绘。详见 Ch.26。

DEC 2026

终端协议扩展（Synchronized Update Mode），定义了 BSU/ESU 让终端在收到 ESU 前暂停渲染、原子提交一帧；iTerm2 / Windows Terminal / Alacritty 等原生支持，老 ConHost 忽略仍可用。详见 Ch.24。

DECSC / DECRC

VT 终端协议的「保存光标位置 / 恢复光标位置」转义（\x1b7 / \x1b8）。终端层面只有一个保存槽位，任何系统调用一次 DECSC 都会覆盖前一次。X-Code CLI 不使用 DECSC 定位 frame（fork 的 log-update 已占用该槽位），frame 采用按行绝对定位 \x1b[absRow;colH。详见 Ch.24。

diff（cell 级别 diff）

比较新 cell buffer 与上一帧的差异，只把有变化的 cell 通过 ANSI 光标跳转 + 重写输出，避免整块擦除重画。是 ChatInput 高频重绘开销低的核心机制。详见 Ch.24。

frame（帧）

<ChatInput> 自行维护的临时显示区，浮动定位在终端历史区下方。包含输入框以及上方的进度指示器、工具调用运行行、权限对话框等。每次状态变化即重画一帧；帧内容不进终端历史区，只覆盖在终端底部，需要保留时通过 commit 写入 scrollback。详见 Ch.24。

freeBlanksAboveFrameRef

记录当前帧顶部上方有多少行可用空白，下一次帧重绘时据此决定要不要先 \n 推一行触发 auto-scroll 把旧内容保留到终端历史区。

Ink

React-for-CLI 渲染器，X-Code CLI 把 ink 别名到 @jrichman/ink@6.6.9（Gemini CLI 同款 fork），但只使用其 lifecycle 能力：mount / unmount / Ctrl+C / stdin raw mode。所有动态 UI 均不经由 Ink 子树渲染。详见 Ch.23。

Ink 动态区（Ink dynamic region）

Ink 自带的「可重绘」区域，Ink 在此区域内反复擦除旧内容重新绘制。X-Code CLI 不使用 Ink 动态区，该区域始终为空，所有可见 UI 均通过 cell buffer 渲染。详见 Ch.23。

IS_LEGACY_TERMINAL

terminal-glyphs.ts 里的运行时检测常量，判定是不是老 ConHost；为真则把 ❯→> / ⎿→| / ⏸→= / ⚡→* 等 Unicode glyph 整体降级到 ASCII。详见 Ch.25。

live（实时行）

frame 里那些跟着状态变化、还没提交到终端历史区的临时行（运行中的工具进度、流式打字过程等）。完成时通过 commit 落到 scrollback。详见 Ch.26。

renderMarkdown

把 Markdown 字符串 ANSI 化的入口函数（cli/src/ui/render-markdown.ts）。复用 marked 的 lexer() 获取 AST，渲染器是自行实现的 formatToken() 递归，不使用 marked-terminal 包装层。表格对齐用 stripAnsi + 自定义 visualWidth 计算可见宽度而非 string.length；删除线 tokenizer 被禁用。详见 Ch.27。

scrollback

终端的历史区，向上滚屏看到的内容。X-Code CLI 在 termRows 行写 \n 触发 auto-scroll 把顶部行推进 scrollback（这是跨终端唯一可靠的保留方式，SU 序列会被多数终端 splice 忽略）。详见 Ch.24。

spinner

进度指示器，X-Code CLI 用「原地呼吸」动画而非 braille 旋转。富终端使用 6 帧基础序列（· / ✢ / * / ✶ / ✻ / ✽），老 ConHost 降级为 ASCII 序列（· / : / + / * / + / :），正反各走一遍形成 12 帧呼吸循环。详见 Ch.25。

useStreamBuffer

流式 chunk 节流 hook：text-delta 攒在 useRef buffer 里，扫到不在开放 markdown 结构里的安全边界（如换行）才切片，再走 150ms 合并窗口 appendMessage。详见 Ch.26。

writeMessageToStdout

ChatInput 的 effect 把 messages 数组里新增的 streaming / final 消息经 renderMarkdown 化后写出。函数签名接收 write: InkWrite 回调参数，内容先缓冲到 pendingScrollbackRef，随后在 BSU/ESU 原子帧内一并刷出到终端历史区。cell buffer 不渲染半截 markdown 预览，避免视觉跳动。详见 Ch.26。

Yoga

Facebook 的跨平台 Flexbox 布局引擎，Ink 默认用它算盒模型。X-Code CLI 绕开是因为它对 CJK / IME / 长流式文本算宽度有误，每秒几十次重算还会放大错误。详见 Ch.23。

C.5 上下文管理

AGENTS.md

人工编写的项目说明文件（位于项目根目录，不在隐藏目录中），事实标准之一。X-Code CLI 找不到时降级读取 CLAUDE.md，写入永远只往 AGENTS.md 写。详见 Ch.36。

auto-memory

也称 Memory / 自动记忆。AI 在 finishReason='stop' 后台运行的 memory extractor 把对话中学到的事实写到 ~/.x-code/memory/auto.md（用户级）或 .x-code/memory/auto.md（项目级）；均不纳入版本控制。4 类严格分类：user / feedback / project / reference；同 (category, key) 自动覆盖；90 天 TTL 驱逐。与人工编写的 Knowledge 严格分开。详见 Ch.36。

checkAndCompressContext

每轮 stream 之前的 proactive 检查：用上一轮 API 返回的 lastInputTokens 比对模型上下文上限，超过 COMPRESSION_TRIGGER_RATIO 就先压一次。详见 Ch.31。

CLAUDE.md fallback

各层目录优先读 AGENTS.md、找不到才回退读 CLAUDE.md。让 Claude Code 用户切过来零迁移成本，但 /init 只往 AGENTS.md 写。详见 Ch.36。

compact-boundary

JSONL transcript 里的特殊行，标记一次压缩事件发生过（light compaction、tool-result truncation、LLM summary、reactive 压缩四条路径完成后均会写入）。/resume 重放时跳过这条边界之前的内容，避免把已丢弃的 loop-guard 配对从磁盘复活。详见 Ch.31。

compressMessages

reactive / proactive 走到 LLM summary 这一步时调的函数：用 generateText 把老消息总结成一段文字，配 KEEP_RECENT 最近 6 条原文保留。详见 Ch.31。

COMPRESSION_TRIGGER_RATIO

proactive 压缩触发阈值（0.8）：token 用量到模型上下文窗口的 80% 就先压，留 20% 给压缩本身的请求 + 输出空间。详见 Ch.31。

handleContextTooLong

reactive 压缩入口：stream 抛出错误且匹配上下文超限 pattern 时立即压缩、不计这一轮、重试当前 turn，用户感知不到这次重试。详见 Ch.31。

JSONL transcript

每条消息独立写一行的会话记录文件（<slug>-<sessionId>.jsonl），加载时按行重放。崩溃恢复 + 跨进程接续 + /resume 历史选择器全靠它。详见 Ch.36。

KEEP_RECENT

压缩保留区大小（6）：最近 6 条消息永远保留原文，保持当前工作上下文不被压走；保留头还会跳过悬空 tool 角色消息避免供应商拒收。详见 Ch.31。

Knowledge

也称知识系统。人工编写的项目说明与偏好，长期不变。文件：每个目录的 AGENTS.md（项目根 / monorepo 子包 / 用户级 ~/.x-code/），缺失时回退 CLAUDE.md；本地偏好 AGENTS.local.md（项目根，gitignored）。AGENTS.md / CLAUDE.md 纳入版本控制跟随项目，AGENTS.local.md 不纳入版本控制。与 AI 写入的 auto-memory 严格分开。详见 Ch.36。

light compaction

纯本地 O(n) 压缩：删除 loop-guard 命中的失败工具调用并剥离对应 tool-call/result 配对，不调用 LLM。proactive 触发时先执行此步骤，仍超阈值才进入 LLM summary。详见 Ch.31。

memory extractor

finishReason='stop' 后台运行的子流程，分析当轮对话并挑出值得记录的事实增量写入 auto.md；主 agent 自身不写记忆文件，避免每轮污染 systemPromptCache。详见 Ch.36。

proactive 压缩

主动型：每轮 stream 之前比对 token 用量与阈值，超过即先压缩再请求。共 3 步依次尝试：（1）light compaction 删除 loop-guard 失败配对；（2）truncateOldToolResults 截断旧的大型 tool_result 为紧凑 stub；（3）仍超阈值才进入 compressMessages LLM summary。每步完成后检查是否已降至阈值以下，是则提前返回。详见 Ch.31。

reactive 压缩

被动型：stream 抛出错误且匹配上下文超限 pattern 时立即压缩并重试当前 turn；7 条 CONTEXT_TOO_LONG_PATTERNS 覆盖 OpenAI / Anthropic / 通用三家错误措辞。详见 Ch.31。

recentToolCalls

LoopState 上的滚动窗口（存储上限 16，扫描窗口 8），存最近若干次 { toolName, hash } 供 loop-guard 判重使用。详见 Ch.32。

/resume

历史会话选择器 slash command：列出本项目的 JSONL transcript 让用户选一个续接。恢复时通过 hydrateLoopState 重建消息历史和 token 用量等会话状态，历史消息回显到终端 scrollback。pendingWork 字段存在于 SessionSummary 类型中，但 resume 流程不会自动将其注入为 user message。详见 Ch.36。

taskSlug

首条用户消息推导的人类可读短串，用作 <slug>-<sessionId>.jsonl 文件名。只设一次永不更新，中途修改会导致本会话文件名错位留下孤儿文件。详见 Ch.08。

C.6 扩展系统

MCP transport

MCP 客户端与 server 之间的传输协议。X-Code CLI 支持两种：stdio（client 启动一个本地子进程与 server 通过 stdin/stdout 通信）和 HTTP（client 通过 HTTP POST 与远端 server 通信，需要 OAuth 认证）。前者运行本地 binary（如 node mcp-server.js），后者连接远端服务（如 https://mcp.linear.app/mcp）。详见 Ch.37。

<server>__<tool>

MCP 远端工具映射到本地工具时的命名规则：server 名加双下划线加 tool 名（如 linear__create_issue）。X-Code CLI 有意不加 mcp__ 总前缀（Claude Code 加此前缀），原因在于每个工具描述都进 system prompt，多一段 mcp__ 会额外消耗 token。详见 Ch.37 + Ch.39。

OAuth 2.1 / callback-server / token-storage

远端 HTTP MCP server 的认证机制：/mcp auth <name> 触发后 CLI 启动一个本地 HTTP server 接收 callback，浏览器打开授权页，授权完 token 存到 ~/.x-code/mcp-auth.json（0o600 文件，不用 OS keychain）。详见 Ch.37。

consent / consent preview

插件安装第一道门：在文件写入磁盘前把"这个插件包含什么、会运行什么子进程"展示给用户、等显式同意。预览里特别强调有"安全爆炸半径"的两类：hook 事件名（要执行 shell）和 MCP server 名（要起子进程）。详见 Ch.39。

userConfig

插件 manifest 里声明的"安装时要问用户的字段"，如 LINEAR_API_KEY。安装时 installer 逐项 prompt 用户输入、写到 ~/.x-code/plugins/user-config.json（0o600），运行时由 getPluginUserConfigEnv() 注入到 MCP server / hook 子进程的 env。sensitive: true 控制输入回显（git 风格 * 代替字符）。详见 Ch.39。

SKILL.md / frontmatter

skill 文件格式：YAML frontmatter（name + description 两字段）+ Markdown body。文件按 scope 分两层组织（user / project），CLI 启动一次性加载，激活时 body 注入消息历史。详见 Ch.38。

activateSkill

模型自主激活 skill 的工具。模型在工具调用中给出 skill 名，CLI 把对应 SKILL.md 的 body 包在 <activated_skill> envelope 里作为 tool_result 回填。只有当 registry 里至少有一条 enabled skill 时这个工具才注册。详见 Ch.38。

disabledSkills

settings.json（user scope：~/.x-code/settings.json）或 settings.local.json（project scope：<repo>/.x-code/settings.local.json）中的顶层数组，列出本 scope 禁用的 skill 名。两层 scope 采用并集语义，任一层列出即视为 disabled。详见 Ch.38。

plugin manifest

.x-code-plugin/plugin.json 或 .claude-plugin/plugin.json（或裸 plugin.json），三条候选路径按优先级探测、第一条命中胜出。name 必填、其他都 optional；五个扩展字段（skills / agents / commands / mcpServers / hooks）走两段式解析：显式声明优先、缺字段走约定目录探测。详见 Ch.39。

enabledPlugins

settings.json 顶层 boolean map（{ "linear@anthropic-marketplace": true, ... }），缺省按 DEFAULT_ENABLED = true。两层 scope（project > user），高优先级 scope 显式赋值即胜出。之所以使用 boolean map 而非 set，是为了允许 project 单独打开 user 已禁用的插件。详见 Ch.39。

PluginLoadError

loadAllPlugins 为每个插件包裹 try/catch，因此某个插件 manifest 损坏不会阻塞 CLI 启动，错误进 PluginLoadError[] 跟 LoadedPlugin[] 一起放进 PluginRegistry、/plugin doctor 命令读取展示。详见 Ch.39。

HookEventName / DecisionEvent

HookEventName 是 10 个固定枚举（SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / PreCompact / PostCompact / SubagentStart / SubagentStop / TurnComplete / SessionEnd）。DecisionEvent 是其中 3 个的子集（UserPromptSubmit / PreToolUse / PostToolUse），只有这三个事件的 hook 通过 stdout 返回的 JSON 能影响 agent 下一步。其余 7 个是 fire-and-forget。详见 Ch.39。

matcher

HookConfigEntry 字段，正则字符串，只对 PreToolUse / PostToolUse 生效，因为其他事件没有 tool name 概念。格式无效的正则降级到 return true（「匹配每个工具」）而非 false（「一个都不匹配」），让 hook 不至于静默失效。详见 Ch.39。

failurePolicy

HookConfigEntry 字段，'allow'（默认）或 'block'。hook 子进程非零退出 / 超时 / crash 时，前者把失败视为同意（permissive 默认）、后者拒绝当前操作。block 是需要作者主动启用的危险开关。详见 Ch.39。

marketplace.json

marketplace 的索引文件，列出本 marketplace 提供的所有 plugin entry（plugins[] 数组，每条带 name / description / source 等）。通常放在 .claude-plugin/marketplace.json（Claude Code 约定），CLI 也接受根目录 marketplace.json。详见 Ch.40。

known_marketplaces.json

用户订阅列表，路径 ~/.x-code/plugins/known_marketplaces.json。每条记录含 name（本地别名）/ source（git URL 或 HTTPS）/ reservedName? / officialSource?。顶层还可以有 strictKnownMarketplaces 和 blockedPlugins 两个企业部署 gate。详见 Ch.40。

wire form vs PluginSource

marketplace.json 里 source 字段有 8 种 distinct wire form 分支：3 种字符串简写（相对路径 "./plugins/foo"、"github:owner/repo[#ref]"、原始 git URL "https://…" / "git@…"）+ 5 种对象形态（{source:'git-subdir'} / {source:'url'} / {source:'git'} / {source:'github'} / {source:'local'}）。对象形态的 discriminator 字段名可以是 source 也可以是 kind（后者是 X-Code CLI 自家 legacy 写法，代码里 o.source ?? o.kind 都接），但逻辑共用，因此不算独立分支。这 8 种由 normalizeMarketplaceSource 归一成统一的 PluginSource 类型，installer 只看 PluginSource。详见 Ch.40。

sha pinning

marketplace.json 里每条 plugin entry 可以声明 sha（7-40 字符 hex commit hash），installer clone 完成后执行 git rev-parse HEAD 用 startsWith 前缀匹配，不匹配则拒绝安装。防御 force-push / repo 被攻陷。anthropic-marketplace 里 153 个远程源 100% 都 pin 了 sha。详见 Ch.40。

RESERVED_MARKETPLACE_NAMES

marketplace.ts 里的常量映射表，把几个特定 marketplace 名（anthropic-marketplace / claude-plugins / x-code-official）钉死到对应的 GitHub org（anthropics / anthropics / woai3c）。注册时 addKnownMarketplace 校验 source 必须在那个 org 下，防止冒充。详见 Ch.40。

${CLAUDE_PLUGIN_ROOT} / ${CLAUDE_PLUGIN_DATA}

slash 命令模板中的变量。前者展开成插件根目录的绝对路径（版本化 cache 目录，重装时擦除），后者展开成持久数据目录（~/.x-code/plugins/data/<id>/，跨重装保留，第一次替换时 CLI 自动 mkdir -p）。expandCommandBody 完成替换。Hook 中有同名变量 ${pluginDir} / ${pluginDataDir}，功能相同。详见 Ch.39。

/plugin refresh

会话内热加载插件变更的单一入口。先重建 plugin 主 registry，再将变更合并到五个子 registry（skill / sub-agent / command / hook / MCP），其中 MCP 部分与 user + project MCP 合并后调 restartAll。重建后 system prompt cache 失效，下一条消息会 cache miss 一次。详见 Ch.39。

C.7 通用 LLM 概念

agentic

形容词，指 AI 能自主拆解任务、调用工具、读写文件、执行命令的能力维度。AI Coding 2023-2024 年开始从 inline completion 转向 agentic。详见 序章。

BPE

Byte-Pair Encoding，主流 LLM tokenizer 算法：从单字节开始把训练语料里最常一起出现的字节对合并成新 token、反复迭代。OpenAI 的 tiktoken 是常用实现，中英文 token 密度差异通常在 0-15% 量级。详见 Ch.30。

CoT（Chain-of-Thought）

思维链 prompting：让模型在输出最终答案前先写中间推理步骤，多步推理任务准确率显著提升。thinking mode 是 CoT 的工程化进化。详见 Ch.34。

doom-loop

LLM 在低 temperature 下反复尝试同一个失败操作的结构性失败模式（自回归推理强化重复 + 缺乏元认知 + 错误反馈不够明确），依赖模型自身无法跳出，必须由 loop guard 进行外部约束。详见 Ch.32。

function calling

OpenAI 2023 年提出的工具调用协议：模型按 JSON Schema 输出 tool_call，客户端执行后把 tool_result 喂回模型。MCP 是它的网络化扩展。详见 Ch.07。

KV cache

Transformer 推理标配优化：把每个 token 算注意力时产生的 K/V 张量缓存在 GPU 显存里，下一个 token 只算自己的 K/V，前面的直接复用，复杂度 O(n²)→O(n)。prompt caching 是它的服务端跨请求拓展。详见 Ch.33。

MCP（Model Context Protocol）

Anthropic 2024-11 提出的开放协议，把工具定义从单一应用拓展为跨应用标准；任何 MCP 工具服务器能被任何 MCP 客户端接入。当前是工具生态事实标准。详见 Ch.07。

prompt caching

KV cache 的服务端跨请求拓展：服务端发现同一前缀的 KV 张量被反复计算时跨请求保存，下次同前缀直接复用，因此前缀必须字节级一致才能命中。这是当前 token 优化的最大单点杠杆。详见 Ch.33。

prompt injection

恶意输入诱导模型偏离原意，比如让 webFetch 抓内网元数据地址泄露凭据。webFetch 私有 IP 黑名单必须包含 169.254.169.254 这条 link-local 元数据服务地址。详见 Ch.16。

RAG（Retrieval-Augmented Generation）

把事实存入向量数据库，每轮对话前先做向量检索拼入 prompt。优点是信息容量无限，缺点是召回质量依赖 embedding。X-Code CLI 不采用 RAG，而是采用「长上下文 + 工具按需读取」路径。详见 Ch.36。

ReAct

Yao et al. 2022 提出的 Reasoning + Acting 框架：模型在同一个生成中交替输出推理和行动，先描述意图与原因再调用工具，获取结果后再决定下一步。当前所有主流 agent CLI 的核心循环都是 ReAct 的工程化版本。详见 Ch.08。

slash command

用户在 ChatInput 里以 / 开头触发的本地命令，定义在 SLASH_COMMANDS：/help / /model / /thinking / /plan / /clear / /compact / /resume / /init / /review / /memory / /exit 等。详见 Ch.36。

temperature

采样温度参数，控制下一个 token 分布的尖锐度。agent 场景通常使用低 temperature（0-0.3）保证确定性，但低温度也意味着采样退化，一旦某个 token 概率最高就会持续被采样，这是 doom-loop 的成因之一。详见 Ch.32。

tool_call / tool_result

Tool Use 协议里成对出现的两个消息内容块：模型在 assistant message 里输出 tool_call（含 toolCallId / toolName / input）、客户端执行后用对应 toolCallId 在 user message 中回填 tool_result。少一边就是 orphan，下一轮请求会被供应商拒。详见 Ch.07。

VLM（Vision Language Model）

能直接接收图像 part 的多模态模型，DeepSeek 等纯文本供应商不支持。X-Code CLI 通过 vision-fallback 子 agent 借用任意一家 VLM 为图片生成 caption，再将文本注入纯文本供应商的对话。详见 Ch.35。
