# 第 12 章 工具系统总览：从注册表到可用工具集

读完第二部分，读者已经了解 Agent Loop 的核心循环：模型生成回复，CLI 执行其中的工具调用，再把结果合并回消息历史继续推理。但循环中「执行工具调用」这一步背后的全景尚未展开——模型实际能调用哪些工具？工具的定义是什么结构？为什么有的工具 AI SDK 自己执行、有的需要 CLI 接管？本章把工具系统的地图铺开，为后面十章的逐一拆解提供入口。全章按工具从定义到执行的路径展开，分为如下几个部分进行介绍。

- 12.1 节从一个 `readFile` 的具体定义出发，拆解工具的三段结构：description、inputSchema 和 execute。
- 12.2 节铺开工具全景图，列出 13 个静态工具与动态注入工具的分类。
- 12.3 节讨论 `buildTools` 如何把注册表装配为本轮可用工具集。
- 12.4 节解释为什么有的工具由 AI SDK 自动执行，有的需要 CLI 接管。
- 12.5 节从反面讨论哪些机制不做成工具以及背后的原因。
- 12.6 节介绍跨工具共享的统一机制。
- 12.7 节给出本章小结。

## 12.1 一个工具的三段定义

> 源码：`packages/core/src/tools/read-file.ts`

工具系统最直接的理解方式是看一个具体的定义。以 `readFile` 为例，以下是简化后的核心结构。

<!-- check:ignore=punctuation -->
```ts
export const readFile = tool({
  description: 'Read a file from the filesystem...',  // 模型通过这段文字决定是否调用
  inputSchema: z.object({                              // 参数校验规则
    filePath: z.string().describe('Absolute path to the file'),
    offset: z.number().optional(),
    limit: z.number().optional(),
  }),
  execute: async ({ filePath, offset, limit }) => {    // 实际执行逻辑
    const content = await fs.readFile(filePath, 'utf-8')
    return content.slice(offset ?? 0, ...)
  },
})
```

一个工具由三段组成：`description` 告诉模型这个工具能做什么，模型在系统提示词中读到这段文字后决定是否调用；`inputSchema` 用 Zod 定义参数的类型和校验规则，模型调用时按这个 schema 输出 JSON 参数；`execute` 是实际的执行函数，接收模型给出的参数，返回工具结果。三段分别对应 tool use 协议（Ch.07）中工具定义、工具调用和工具结果三个阶段。不过并非所有工具都有 `execute` 字段——部分工具需要访问完整的会话上下文（消息历史、权限模式、UI 回调等），而 `execute` 函数只能拿到模型给出的参数，拿不到这些上下文信息。这类工具的执行由 CLI 自己接管，12.4 节会详细讨论两种执行形态的区别。

## 12.2 工具全景图：13 个静态工具与动态注入

X-Code CLI 的工具分为两层：13 个每次启动都注册的静态工具，以及若干根据运行环境条件注入的动态工具。先看静态层——按用途分为六个类别。

| 类别 | 工具 | 后续章节 |
| --- | --- | --- |
| 文件 | `readFile` `writeFile` `edit` | Ch.13 |
| Shell | `shell` | Ch.14 |
| 代码库探索 | `glob` `grep` `listDir` | Ch.15 |
| 网络 | `webSearch` `webFetch` | Ch.16 |
| 控制类 | `askUser` `enterPlanMode` `exitPlanMode` | Ch.18 |
| 任务清单 | `todoWrite` | Ch.20 |

注册表在源码中是一个普通的对象，每个属性对应一个工具定义。

> 源码：`packages/core/src/tools/index.ts`

<!-- check:ignore=punctuation -->
```ts
export const toolRegistry = {
  readFile,
  writeFile,
  edit,
  shell,
  glob,
  grep,
  listDir,
  webSearch,
  webFetch,
  askUser,
  enterPlanMode,
  exitPlanMode,
  todoWrite,
}
```

13 个键对应 13 个静态工具。动态工具不在注册表中，而是由 `buildTools` 在运行时按条件注入。当前有三类动态工具：

（1）`task`——当子 agent 注册表存在时注入，用于委派子任务（详见 Ch.19）。

（2）`activateSkill`——当技能注册表（Skill Registry）中至少有一个技能时注入，用于激活技能指令（详见 Ch.38）。

（3）MCP 资源与桥接工具——当 MCP 注册表存在时注入 `listMcpResources` 和 `readMcpResource` 两个内置资源浏览工具，并为每个已连接的 MCP 服务器的工具创建桥接入口（详见 Ch.39）。

下一节展开这个装配过程。

## 12.3 从注册表到可用工具集：buildTools 的装配过程

> 源码：`packages/core/src/agent/loop.ts::buildTools`

模型并非天生知道这些工具的存在——每次发送 API 请求时，CLI 会把「当前可用工具列表」嵌入请求体中发给供应商。这个装配过程由 `buildTools` 函数完成。图 12-1 展示了装配的整体流程。


![image.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/7c47b625c42040a5a640430e624c93d0~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=715&h=629&s=43920&e=png&b=ffffff)

> 图 12-1 工具集装配流程——实线表示必有输入，虚线表示条件注入

以下是 `buildTools` 的简化结构。

<!-- check:ignore=punctuation -->
```ts
function buildTools(options: AgentOptions) {
  const tools = { ...toolRegistry } // 静态注册表全部引入

  // 条件注入：子 agent 委派
  if (options.subAgentRegistry) {
    tools.task = createTaskTool(options.subAgentRegistry)
  }

  // 条件注入：技能激活
  if (options.skillRegistry && options.skillRegistry.names().length > 0) {
    tools.activateSkill = createActivateSkillTool(options.skillRegistry)
  }

  // 条件注入：MCP 资源浏览 + 桥接工具
  if (options.mcpRegistry) {
    tools.listMcpResources = listMcpResources
    tools.readMcpResource = readMcpResource
    for (const entry of options.mcpRegistry.list()) {
      tools[entry.callableName] = bridgeMcpTool(entry)
    }
  }

  // 子 agent 场景下按白名单或黑名单过滤
  if (options.toolFilter) {
    // ...filter.allow / filter.deny
  }

  return tools
}
```

装配过程分五步。

（1）静态工具全部引入——13 个工具默认都在可用集合中。

（2）条件注入 `task` 工具——`task` 用于把任务委派给子 Agent（Sub-Agent），即一种专门化的小型 Agent，例如只读探索用的 `explore`、做代码审查的 `code-reviewer`。只有当子 Agent 注册表非空时 `buildTools` 才注入 `task`，同时将可用的子 Agent 名单嵌入工具描述中，让模型知道自己可以指派哪些子 Agent。子 Agent 的注册、发现机制与自定义方式详见 Ch.19。

（3）条件注入 `activateSkill`——技能（Skill）是一段预写好的 markdown 指令，模型判断当前任务匹配某个技能后调用 `activateSkill`，工具返回技能的完整文本，模型把它当作工具结果来遵循执行（详见 Ch.38）。

（4）条件注入 MCP 工具——MCP（Model Context Protocol，详见 Ch.39）允许外部服务向 CLI 注册自己的工具和资源。当 MCP 注册表存在时，`buildTools` 注入两个内置的资源浏览工具 `listMcpResources` 和 `readMcpResource`，并为每个 MCP 服务器暴露的工具创建一个桥接入口，桥接工具不带 `execute` 字段，由 CLI 接管执行并转发给对应的 MCP 服务器。

（5）按 `toolFilter` 过滤——子 agent 运行时拥有自己独立的 `agentLoop`（嵌套在主循环中），通过 `toolFilter` 限制可用工具。例如 `explore` 子 agent 只需要读类工具，不应修改文件，这种限制通过 `{allow: [...]}` 或 `{deny: [...]}` 实现。主 agent 不传 `toolFilter`，获得全部工具。

`buildTools` 在每次 `agentLoop` 调用之初执行一次（即用户每次提交消息时执行一次），同一次循环的后续轮次复用同一份结果。由于各注册表在启动阶段冻结，主 agent 不传 `toolFilter`，每次装配出的工具集在字节层面是稳定的。这一点直接影响 prompt cache（详见 Ch.33）能否命中：API 请求中的 `tools` 字段也是缓存前缀的一部分，跨轮次如果发生任何变化都会导致缓存失效。

## 12.4 为什么有的工具 SDK 自己执行，有的要 CLI 接管

工具定义的结构看起来大同小异（`description` + `inputSchema` + 可选的 `execute`），但实际执行时走两条不同的路径——区别在于工具是否提供了 `execute` 字段。图 12-2 展示了从模型发出 `tool-call` 到工具结果写回消息历史的完整分支。


![image.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/b5a1ef3be1cc4654ba89547658da76a8~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=632&h=915&s=50902&e=png&b=ffffff)

> 图 12-2 工具执行的两条路径与循环护栏分流

第一种形态是 AI SDK 自动执行。工具定义中包含 `execute` 函数，AI SDK 在流式响应中看到模型调用了这个工具后，直接调用 `execute` 获取结果，把 `tool-result` chunk 塞回流中，CLI 几乎不参与。这种形态适用于纯输入输出、不依赖会话状态的工具，包括 `readFile`、`glob`、`grep`、`listDir`、`webSearch`、`webFetch` 以及动态注入的 `activateSkill`——这 7 个工具的共同特征是执行过程只需要模型给出的参数，不需要权限审批，也不修改会话状态。

第二种形态是 CLI 接管执行。工具定义中没有 `execute` 字段，AI SDK 不知道如何执行这个工具，只把 `tool-call` chunk 送出来。CLI 在流结束后的 `processToolCalls` 阶段识别它，调用对应的处理函数（Dispatch Handler）完成执行。这种形态适用于需要权限审批、修改会话状态或触发 UI 副作用的工具：`writeFile`、`edit`、`shell` 在写入磁盘前需要弹出权限审批对话框；`task` 需要新开一个嵌套的 `agentLoop` 执行子任务；`askUser`、`enterPlanMode`、`exitPlanMode`、`todoWrite` 需要与 UI 通信或修改会话状态；MCP 桥接工具需要将调用转发给外部 MCP 服务器。

两种形态的本质区别在于 `execute` 函数的局限性：它只能拿到模型给出的参数，拿不到完整的会话上下文（消息历史、权限模式、回调函数等）。需要会话上下文才能完成工作的工具，只能走 CLI 接管的路径（详见 Ch.08「工具的两条执行路径」）。

CLI 接管的工具内部还有一层分流——是否经过循环护栏（Loop Guard，详见 Ch.32）。循环护栏的作用是检测模型对同一工具的重复调用，在达到阈值后拦截并提示模型更换思路，防止死循环（Doom Loop）式的无效重复。写入类工具（`writeFile`、`edit`、`shell`）和 MCP 桥接工具经过这道检测——用相同参数反复修改同一个文件确实可能是 doom-loop，应当拦截。但有 7 个工具的反复调用是完全合理的使用模式，被循环护栏拦截反而会导致功能异常。

| 工具 | 为什么反复调用是合理的 |
| --- | --- |
| `askUser` | 用户可能被连续询问几个不同的问题，每次问的内容不同 |
| `enterPlanMode` / `exitPlanMode` | 用户拒绝后模型可以修订方案再请求一次 |
| `todoWrite` | 模型每完成一项待办就调用一次，反复调用是设计意图 |
| `task` | 委派子任务，每次的 prompt 都不同，也是正常使用模式 |
| `listMcpResources` / `readMcpResource` | MCP 资源浏览天然是多次查询（详见 Ch.39） |

这 7 个工具走绕过循环护栏的专用路径，源码中的入口为 `BYPASS_LOOP_GUARD_HANDLERS`。以下是两种执行形态和循环护栏分流的完整对照。

| 工具 | 有 `execute` | 经过循环护栏 |
| --- | --- | --- |
| `readFile` `glob` `grep` `listDir` `webSearch` `webFetch` `activateSkill` | 有 | 不适用（AI SDK 自动执行，不走分发流程） |
| `writeFile` `edit` `shell` 及 MCP 桥接工具 | 没有 | 经过 |
| `askUser` `enterPlanMode` `exitPlanMode` `todoWrite` `task` `listMcpResources` `readMcpResource` | 没有 | 绕过 |

## 12.5 工具的边界：哪些机制不做成工具

读者可能会问：X-Code CLI 的自动记忆系统（Auto-Memory，详见 Ch.36）为什么不做成一个工具？用户和模型对话过程中，「用户偏好 PostgreSQL」「这个项目用 pnpm 不用 npm」这类信息会自动持久化为长期记忆，下次会话开始时自动加载到系统提示词中。但模型本身没有记忆写入工具——记忆的提取和写入完全由一个叫提炼器（Extractor）的后台组件独占。每轮主对话结束后，CLI 在后台自动运行提炼器，从刚才的对话片段中抽取值得长期保留的信息并持久化。整个过程发生在用户视野之外，对主对话中的模型透明。提炼器的调用时机、模型选择和输出格式详见 Ch.36。

不把记忆写入做成工具，背后有两个取舍。第一，如果记忆写入是一个工具，每次模型决定记录一条时都会在终端面板上出现一行工具调用记录——主对话结束、用户准备输入下一条消息时反而被这些调用打扰，界面不够干净。第二，把「提炼记忆」统一交给后台提炼器处理，写入路径只有一条，不需要额外的去重逻辑来处理模型和提炼器双写的冲突。

类似的边界还有系统提示词加载、AGENTS.md 加载、JSONL 会话日志写入——它们都由 CLI 在 `agentLoop` 周边自动处理，模型既不知道也调用不到。工具的定义边界可以归纳为三个条件且必须同时满足：（1）由模型主动决定是否调用；（2）参数由模型生成；（3）执行结果需要反馈给模型继续推理。自动记忆不满足第一条（不是模型决定写哪条记忆）和第三条（写入结果不需要反馈给模型），因此不适合做成工具。

## 12.7 小结

本章铺开了工具系统的全景地图。一个工具由三段定义组成：`description` 供模型决策、`inputSchema` 校验参数、`execute` 执行逻辑（或省略，由 CLI 接管）。X-Code CLI 的工具分为静态和动态两层：13 个静态工具始终在注册表中，`task`、`activateSkill` 和 MCP 相关工具则由 `buildTools` 在运行时按条件注入。`buildTools` 在每次循环启动时执行一次，输出的工具集在字节层面稳定，这是 prompt cache 能跨轮次命中的前提之一。工具的执行分为两种形态：带 `execute` 的工具由 AI SDK 在流内自动执行，不带 `execute` 的工具由 CLI 在流结束后通过 `processToolCalls` 手动分发——后者进一步按是否经过循环护栏分为两路，写入类工具经过检测，控制类和委派类工具绕过检测。不是所有与 Agent 相关的功能都适合做成工具，自动记忆、系统提示词加载、会话日志等机制由 CLI 在循环周边自动处理，不暴露给模型。

下一章（Ch.13）将进入第一组具体工具——文件操作三件套 `readFile`、`writeFile` 和 `edit`，讨论它们各自的 `description` 设计、参数校验和执行逻辑中的特殊考量。
