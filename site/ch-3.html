第 3 章 生产级 Agent 要防的 7 类失败

前两章分别从「最小 demo」和「三层工程」两个角度建立了全书的坐标系。本章换一个视角来看同一套工程：这些机制到底在防什么？从失败出发往回推，后续每一章的每个机制都对应着一类失败模式。把失败列清楚，每个机制为什么存在就不言自明了。

生产级产品与 demo 之间的差距，几乎全在异常路径。模型偶尔产生不合 Schema 的工具调用，工具偶尔被错误参数调用，网络偶尔抖动，长输出偶尔超出上下文（Context）容量，模型偶尔陷入重复，用户偶尔按 Esc。每一种「偶尔」在 demo 中都能容忍，进程崩溃后重启即可。但在生产环境中，每一种「偶尔」都可能损失用户数据、消耗大量 token、或者让用户对工具失去信任。生产级 Agent 与 demo 之间的差距，就是一整套对这些失败的防御。本章将这套防御按失败类型组织，读者可以对照后续章节理解每一章在防御什么、为什么必须防御。本章将分为如下几个部分进行介绍。

  • 3.1 节解释为什么要从失败模式出发，以及 7 类失败是如何归并出来的。
  • 3.2 至 3.8 节逐一展开 7 类失败：模型幻觉、工具误用、死循环、上下文溢出、供应商故障、用户中断、终端环境异常。每节先描述症状，再介绍 X-Code CLI 的防御方案，最后讨论设计原理。
  • 3.9 节给出「失败 × 章节」矩阵，将 7 类失败与后续各章交叉对照。
  • 3.10 节给出本章小结。

3.1 为什么要从失败模式出发

把后续各章看作「做了什么」是教程视角，把它们看作「防什么」是工程视角。后者更接近读者真正需要的信息——读完后不仅知道「应该怎么写」，还知道「忘了写会怎样」。

为什么是 7 类？这个数字不是先验设定的，而是反向归并的结果。将 X-Code CLI 实际运行中遇到的所有异常事件按发生位置进行聚类：发生在模型输出端的归为「模型幻觉」，发生在工具调用语义错位上的归为「工具误用」，发生在循环不收敛上的归为「死循环」，涉及上下文窗口容量的归为「上下文溢出」，涉及外部 API 协议层的归为「供应商故障」，涉及用户主动打断的归为「用户中断」，涉及终端环境差异的归为「终端环境异常」。聚类后的 7 类相互正交，合在一起覆盖了实际遇到过的所有事故场景。这个数字并非定理，未来新的失败类型出现时可能需要增加，但目前来看这 7 类已经稳定了一段时间。

3.2 模型幻觉（Hallucination）

症状包括：模型调用一个不存在的工具名；给工具的参数不合 Schema（漏字段、字段类型错）；编造文件路径或函数名（看起来合理但代码库中不存在）；声称「我已经执行了 X」但实际上没有发出任何工具调用。

X-Code CLI 的防御方案如下。当模型调用不存在的工具或参数格式不合法时，SDK 会直接拒绝这次调用并返回错误。但拒绝之后会产生一个新问题：模型发出了一个工具调用请求（tool_call），却没有对应的工具返回结果（tool_result），这种「有调用无返回」的不完整状态如果原样传给下一轮 API 请求，供应商会直接报错。因此需要一个配对修复机制（repairOrphanToolCalls，Ch.17）为这些落单的调用补上一条错误说明，使消息序列恢复完整。工具的 description 与 Zod Schema 形成双重约束——description 引导模型选择正确的工具，Schema 校验参数格式，出错时错误信息会回传给模型，引导它用合法参数重试。模型编造的文件路径会在 readFile 或 edit 实际访问时被文件系统报错阻止。至于「声称已做但实际未做」这一类，目前无法完全防御，只能在 system prompt 中反复要求每次写操作必须通过真实的工具调用来完成。

这套方案的核心思路是不试图阻止模型产生错误，而是确保每一个错误都能被立刻发现并反馈回来。在 prompt 中写「禁止产生幻觉」是无效的，幻觉源自模型的概率分布特性，无法通过指令消除。因此策略转为：让运行时对每一次工具调用都进行严格校验，一旦出错就将错误信息原样回传给模型，让模型在错误反馈的引导下自行修正。

3.3 工具误用

症状包括：模型试图用 Shell 执行 rm -rf 类危险命令；edit 修改了不该修改的文件；在尚未确认方案之前就先动手改代码；把 node_modules 误当成项目文件进行读写。

X-Code CLI 的防御方案围绕一个核心思路展开：在不同环节设置不同粒度的拦截点。三级权限模型（Ch.29）是最基础的一道拦截，将所有工具按风险等级划分为默认放行、普通确认、带危险警告确认三档。writeFile、edit、shell 默认需要确认，用户选择 always-allow 之后才记入规则表，后续同类操作不再询问。Shell 命令分级（Ch.14）在此基础上进一步细化，将复合命令拆解后按只读与破坏性两类分别走不同的审批策略。计划模式（Plan Mode，Ch.21）则从工作流层面拦截，强制执行「先出方案、用户审批、再执行」的流程，适用于重大修改场景。glob 与 grep 默认尊重 .gitignore，排除 node_modules 等噪声目录。

这套方案的核心取舍在于操作成本与误操作风险之间的平衡。每一次 edit 都弹出确认框会导致用户因厌烦而放弃使用，这是过严的代价；完全不询问则可能导致模型把 rm -rf node_modules 当作「清理依赖」直接执行，这是过松的代价。三档划分加上 always-allow 机制，将询问次数压缩到刚好足够：第一次遇到某类写操作时询问一次，用户授权后同类操作后续不再打断。

3.4 死循环（Doom-Loop）

症状包括：模型反复调用同一个失败命令、每次都报相同的错误（在 PowerShell 引号格式不熟悉的场景中尤为常见）；edit 的 oldString 不存在但模型反复用同样的值重试；生成的代码存在语法错误，反复 build 失败但每次「修复」都没有实质改动。

X-Code CLI 的防御方案如下。循环护栏（Loop Guard，Ch.32）持续监控每次工具调用，当检测到模型在短窗口内对同一工具发出语义相同的调用时，按两级策略逐步升级响应。第一级是软阻断：注入一条合成的工具返回结果，提示模型「这个调用已经连续失败多次，请更换思路」——多数死循环在这一步就能跳出，因为模型收到明确的失败反馈后通常会尝试不同的参数或工具。第二级是硬阻断：弹出对话框，由用户选择暂停或继续——只有当模型连「换思路」也无法做到时，才需要人工介入。--max-turns N 参数主要用于子 Agent 与非交互模式（--print），主交互模式下不启用该限制，依靠循环护栏加用户按 Esc 来拦截。

这套方案遵循「逐级升级」原则：能不打扰用户就不打扰，确实无法自行解决时才请求用户介入。设置两级而非单级的原因在于，绝大多数死循环属于模型「没意识到自己在重复」的轻度情况，一条提示就能解决；只有极少数属于模型确实陷入了无法跳出的思维定势，才需要用户帮助重新定义问题。如果只设单级硬阻断，每次死循环都会打断用户，频繁的打断会削弱用户对工具的信任。Ch.32 将带领读者从零实现这套循环护栏——从工具调用的语义指纹计算，到滑动窗口的重复检测，再到两级阻断的切换逻辑。

3.5 上下文溢出

模型的上下文窗口（Context Window）容量有限——即使是 200K token 的窗口，在多轮对话中也会被逐渐填满。症状包括：对话进行几十轮后，累积的消息历史超出窗口容量，API 请求直接失败；一次 grep 命中四千行代码或一次 readFile 读取一个八千行的大文件，单条工具返回结果就占据了大量空间，两三轮就会将窗口耗尽；系统提示词（System Prompt）在每轮请求中都需要重新发送，如果没有命中供应商的缓存机制，每轮都会产生额外的 token 计费。

X-Code CLI 通过多层防线来应对这一问题。第一层防线是工具结果截断（Ch.17）：每个工具返回的结果都有独立的大小限制，超出部分被截断并标记，从源头控制单条消息的体积。第二层防线是上下文压缩（Ch.31）：在每轮 API 调用前检查当前上下文大小，接近窗口容量上限时自动触发压缩——先尝试轻量裁剪，不够再调用模型将旧消息总结为摘要。如果主动检查的估算出现偏差，API 返回上下文超限错误时还有一条被动路径作为安全网，强制压缩后重试。第三层防线是提示词缓存（Prompt Caching，Ch.33）：系统提示词在整个会话期间保持字节级稳定，供应商可以缓存这部分内容，避免每轮都重新计算 token，显著降低费用和延迟。Token 经济学认知（Ch.30）是以上所有手段能够发挥作用的量化基础。

这套方案的核心设计思路是分层递进：能用轻量手段解决的就不动用重量手段。工具结果截断在数据进入消息数组之前就控制了体积；上下文压缩在窗口接近上限时主动腾出空间，用户不会察觉；被动路径只在极少数估算偏差过大时才触发。每一层都在尽量避免触发更重的下一层，从而将 API 调用失败和用户可感知的中断降到最低。Ch.17 和 Ch.31 将带领读者逐层实现这套防线——从工具结果的截断策略，到基于 token 估算的主动压缩触发，再到 API 报错后的被动压缩安全网。

3.6 供应商故障

Agent 依赖外部 API 来调用模型，而 API 会以各种方式出错。常见症状包括：请求过于频繁被限流（HTTP 429）；供应商服务器临时不可用（HTTP 503）；请求参数不合法被拒绝（HTTP 400）；模型的回复写到一半就因为达到输出长度上限而被截断；流式传输中途因网络波动而断开；模型发出了工具调用但因为格式问题没有收到返回结果，下一轮请求被供应商视为消息不完整而整轮拒绝。

X-Code CLI 的防御方案围绕三个核心问题展开：如何识别错误类型、如何选择应对策略、如何在错误后恢复到可继续的状态。

对于错误识别，错误分类器（Ch.11）将 API 错误按症状和可恢复性细分为多个类别——有些应该自动重试（如临时网络抖动），有些应该提示用户切换模型（如 API Key 无效），有些应该直接终止当前轮（如内容违规）。这些分类不是预先设计好的，而是在实际运行中逐步积累的结果，每一类都对应着真实日志中观察到的一种错误模式。

对于应对策略，每一轮工具调用结束后，runTurn 返回 4 种结果类型（TurnOutcome，Ch.08）：正常完成、出错、需要重试（例如上下文溢出经过压缩后重试）、被用户中断。其中一个特殊情况是模型的回复被截断（输出达到长度上限但内容没有写完）——此时不是报错，而是自动追加一条「请继续」的提示让模型接着输出（Ch.08），用户看到的是一段连贯的回复，中间只有短暂的停顿。

对于错误恢复，多供应商抽象（Ch.09）允许用户在某家供应商完全不可用时通过 /model 命令切换到其他供应商。前面 3.2 节提到的消息配对修复机制（Ch.17）同样在这里发挥作用——当工具调用和返回结果因为流中断而错位时，修复机制将消息序列补全为合法状态，使下一轮请求能够正常发出。上下文溢出错误（context too long）通过匹配多种错误信息模式来兼容不同供应商的差异写法，命中后触发压缩流水线的第三层进行紧急截断并重试。

这套方案的核心难点在于信号区分。同一个 HTTP 503 可能意味着临时抖动（应当重试）、供应商完全宕机（应当提示用户换模型）、或者发送请求时网络中断（应当立即重试）。分类数量偏多，但一个「更简洁的统一抽象」无法覆盖真实 API 错误的多样性。这是生产环境不得不承担的复杂度。Ch.11 将带领读者实现这套错误分类器——逐类拆解每种 API 错误的识别规则和对应的恢复策略，最终组装成一条完整的错误处理流水线。

3.7 用户中断

症状包括：用户按 Esc 想停止当前轮，但模型还在调用工具或 Shell 子进程还在运行；用户按 Ctrl+C 想退出 CLI，但进程留下了孤儿状态（半写的文件、残留的进程树）；用户中途改变主意，下次启动时希望从某个中间状态继续。

X-Code CLI 的防御方案如下。abortSignal 一路穿透——runTurn、streamText、工具 execute、execa 子进程都接受 options.abortSignal，Esc 一键即可打断整条调用链。中断时合成一条 [Tool execution interrupted by user] 占位 tool_result，以保持 messages 配对的合法性。Ctrl+C 采用双击退出机制，第一次按下时提示、第二次按下才真正退出，以防止误触。/resume 恢复机制（Ch.36）将会话状态记录在 JSONL 文件中，包含中断点信息，下次启动时可继续。abortSignal 在整条调用链中的穿透路径如图 3-3 所示。

图 3-3 abortSignal 穿透链——Esc 信号从用户一路传递到子进程

中断防御的关键不在于「能否中断」（任何程序都能响应 SIGINT），而在于中断之后能否保持状态可恢复。abortSignal 一路穿透是 Node.js 异步生态中的标准做法，但要正确实现它需要在每一个可能 await 的位置都接收 signal，否则信号会在该层被丢弃，下游无法收到中断通知。中断时合成占位 tool_result 并非出于美观考虑，而是因为不放置占位就会破坏 messages 的配对关系，导致下一轮 API 请求被供应商以 400 错误直接拒绝。这是「中断后能立刻继续」的硬约束。

3.8 终端环境异常

一个 CLI 工具在开发者的 macOS iTerm2 上运行完美，但同一份代码在用户的 Windows 老版 PowerShell 上可能出现乱码，在 SSH 远程连接中可能出现界面错位。症状对用户而言非常直观：输入框在打字时不断抖动；中文字符占位宽度计算错误，导致光标位置与实际文字不对齐；模型流式输出时屏幕频繁闪烁；某些特殊符号（如进度条中的 Unicode 图标）在老终端上显示为方块或问号。

这些问题的根本原因在于终端模拟器之间的差异。macOS Terminal、iTerm2、Windows Terminal、老版 PowerShell（ConHost）、cmd.exe、SSH 等不同终端对控制字符和 Unicode 的支持范围各不相同。在一个终端上能正常渲染的字符，在另一个终端上可能完全无法显示。此外，中日韩（CJK）字符在终端中占两个字符宽度，但许多布局引擎（如 Ink 使用的 Yoga）按单字符宽度计算，导致界面错位和抖动。

X-Code CLI 的防御策略是「先检测终端能力，再决定渲染方式」。具体措施包括以下几项。（1）启动时通过 IS_LEGACY_TERMINAL 检测当前终端是否为老版 ConHost，如果是，就将所有 Unicode 图标降级为 ASCII 字符（例如将 ✓ 替换为 +），确保在任何终端上都能正确显示（Ch.25）。（2）输入框组件（ChatInput）不依赖第三方布局引擎计算中文字符宽度，而是自行管理每个字符的屏幕位置，从根源上消除 CJK 字符导致的抖动问题（Ch.23、Ch.24）。（3）模型流式输出时，不是每收到一个 token 就刷新一次屏幕，而是按 150ms 窗口批量合并后再统一刷新，将刷新频率控制在人眼不会感知到闪烁的范围内（Ch.26）。（4）跨平台 Shell 抽象（Ch.14）通过 execa 适配各操作系统的进程管理差异，确保中断信号在 Windows 和 POSIX 系统上都能正确终止子进程。

这套策略的代价是每次启动都需要进行终端能力检测，并且渲染逻辑比直接调用第三方库更复杂。但不做检测的代价是部分用户会看到乱码或抖动的界面，而这种可见的体验退化对产品口碑的伤害远大于检测带来的微小启动延迟。

3.10 小结

本章从失败模式出发，将生产级 Agent 面对的异常路径归并为 7 类：模型幻觉、工具误用、死循环、上下文溢出、供应商故障、用户中断、终端环境异常。每一类失败不仅描述了症状和防御方案，还讨论了设计原理——三级权限如何在操作成本与误操作风险之间取得平衡、循环护栏为什么设置逐级升级的两层响应、上下文压缩为什么采用分层递进的策略、供应商错误为什么需要按症状细分而非统一处理。这些设计取舍才是工程经验的核心价值。

失败模式视角与第 2 章的三层工程视角是互补的两面。三层视角描述「工程师在哪里工作」，失败模式视角描述「在防御什么事故」。两个视角的交叉，能够完整解释后续各章每一节为什么存在、其设计原则是什么、可能的取舍点在哪里。带着这两张地图进入后续章节的具体实现，阅读体验会更为连贯。
