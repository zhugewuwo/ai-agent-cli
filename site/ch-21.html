第 21 章 Plan Mode：先计划再开工

上一章的 todoWrite 在模型动手实施时提供实时进度面板；本章的计划模式（Plan Mode）解决的是实施之前的问题——如何确保模型在跨多文件的复杂改动中不跑偏方向。复杂任务最常见的失败模式是模型收到用户的需求后就开始动手，改了一批文件之后发现方向错了，回滚成本远高于事先写一份计划并让用户过目、确认方向。Plan Mode 把这个「先规划后实施」的流程做成了会话级状态：进入 plan 状态后模型被约束为只读，必须先完成一份计划文档并经用户审批，才能切到实施阶段动手修改代码。

整个状态机只有三个状态。default 是会话启动后的初始状态，模型按正常权限做读写操作。用户通过 /plan 命令或模型通过 enterPlanMode 工具进入 plan 状态——此时系统提示词末尾追加一段约 80 行的覆盖段（Plan Mode Overlay），把模型每一轮的合法收尾方式锁定为 askUser（继续向用户提问）或 exitPlanMode（提交计划供审批）两个动作。用户在 exitPlanMode 的审批对话框里选择通过后，会话切到 acceptEdits 状态——文件写入工具（writeFile / edit）免审批自动通过，shell 命令仍走正常权限审批。用户拒绝进入时会话留在 default 状态；exitPlanMode 审批被拒时会话留在 plan 状态，等待模型修订后重新提交。下面围绕 Express → Fastify 迁移这个场景，展开状态机背后的设计选择，分为如下几个部分进行介绍。

21.1 一个完整的例子：Express → Fastify 迁移

假设用户输入「把项目从 Express 迁到 Fastify」。模型判断这是一个跨多文件、需要架构决策的大任务，主动调用 enterPlanMode 工具。CLI 弹出审批对话框「X-Code wants to enter plan mode」，用户选 Yes。进入 plan 状态的那一刻，handleEnterPlanMode 做了三件事：

（1）把 LoopState.permissionMode 设为 'plan'

（2）把 LoopState.systemPromptCache 清空——下一轮请求会重新拼装系统提示词，此时覆盖段会被追加到末尾

（3）在项目的 .x-code/plans/ 目录下生成一个新的 plan 文件路径（如 .x-code/plans/express-to-fastify-20260508-143022.md），存入 LoopState.currentPlanPath

// 源码：packages/core/src/agent/plan-tools.ts

state.permissionMode = 'plan'
state.systemPromptCache = null
// ...
if (!state.currentPlanPath) {
  const topic = (input.topic as string | undefined)?.trim()
  const fallbackText = lastUserMessageText(state.messages)
  // 优先用模型传入的 topic，其次用缓存的 taskSlug
  const explicitSlug = topic && topic.length > 0
    ? topic
    : state.taskSlug || undefined
  state.currentPlanPath = makePlanFilePath(fallbackText, { slug: explicitSlug })
}

下一轮请求发出时，系统提示词末尾已经追加了覆盖段。模型读完覆盖段后，按其中规定的「迭代式访谈」工作流推进：

第 1 轮：grep "express" 找所有引用 → 发现 18 个 endpoint + 4 个中间件
        writeFile 创建 plan 文件骨架（Context / Approach / Verification 三段）
        askUser："发现项目用了 express-rate-limit，迁移期间要保留这个能力，
                 偏好是 (a) @fastify/rate-limit 还是 (b) 自实现？"

用户答 a。

第 2 轮：webFetch fastify rate-limit 文档 → 在 plan 里补一节
        edit plan 列出 7 项主线任务
        askUser："测试是用 supertest 还是改成 fastify.inject？"

...

几轮迭代后 plan 写完了，模型再调用 exitPlanMode。CLI 再弹一次审批对话框，把 plan 文件内容展示给用户审核，用户选 Yes。这一刻 handleExitPlanMode 做了三件事：把 permissionMode 设为 'acceptEdits'（不是 'default'，21.6 节展开），再次清空 systemPromptCache，并在对话历史里追加一条 user message 告知模型已退出 plan mode、写工具已解锁：

// 源码：packages/core/src/agent/plan-tools.ts

if (approved) {
  state.permissionMode = 'acceptEdits' // 不是 'default'
  state.systemPromptCache = null
  // ...
  // 追加一条 user message 让模型知道模式已切换
  state.messages.push({
    role: 'user',
    content: [
      '## Exited Plan Mode',
      '',
      'You have exited plan mode. You can now make edits, run tools, and take actions.',
      'Write tools (writeFile, edit) are now auto-approved (acceptEdits mode); shell commands',
      'still go through normal permission classification.',
      persisted
        ? `The plan file is located at ${persisted} if you need to reference it.`
        : '',
    ].filter(Boolean).join('\n'),
  })
}

如果用户拒绝审批，模型收到一条标记为错误的工具结果——「Plan rejected by user. You are still in plan mode.」——要求模型根据用户反馈修订 plan、然后重新调用 exitPlanMode 提交。从这一轮开始，覆盖段已不再追加到系统提示词里，模型按 plan 文件内容逐步实施——writeFile / edit 免审批通过（acceptEdits 模式语义），shell 命令仍走正常审批。整轮交互展示了 plan mode 的核心流程：进入 plan 状态 → 在覆盖段约束下迭代探索与访谈 → 写 plan 文件 → 退出 plan 状态切到 acceptEdits 实施。下面六节详细说说相关的设计选择。

21.2 为什么约束靠提示词覆盖而非权限层拦截

读者可能预期 plan mode 的「模型只能读、不能写」一定在工具层或权限层强制拦截——writeFile / edit / shell 在 plan mode 下被工具白名单 deny，调用直接返回错误。实际并非如此。权限模块的注释明确写到：

'plan': pure prompt-based enforcement — no permission-layer change.
The system-prompt overlay tells the model not to write;
if it ignores that, the regular `ask` prompt still fires.

工具白名单在 plan mode 下保持不变，writeFile / edit / shell 仍然在主 Agent 的工具集里。权限判定函数 checkPermission 也没有「plan mode 下自动 deny 写工具」的特殊分支。唯一的约束来自系统提示词末尾追加的覆盖段——它告诉模型「现在不能写」。

这看起来约束很弱，但实测足够稳定，原因有三。其一，覆盖段的措辞极其强硬——开头第一句就是「you MUST NOT make any edits」，配合「This supercedes any other instructions you have received」，主流模型的遵守率非常高。其二，覆盖段把每轮的合法收尾方式锁定为两个——askUser 或 exitPlanMode——模型没有「做完就直接结束」的选项，行为路径被限制为固定的选项。其三，即使模型绕过覆盖段的约束调用了 writeFile 修改非 plan 文件，写入仍然会触发正常的 ask 权限对话框，用户看到对话框可以拒绝。最坏情况是被拒绝一次，不会出现在用户不知情下写入文件的后果。

那为什么不直接在工具层做硬约束，把 writeFile 从工具集里 deny 掉？原因有两个。

（1）维护成本不同。覆盖段是纯文本，调整约束规则只需编辑一段提示词字符串；而在权限层加硬约束，需要在 checkPermission 里新增 plan mode 分支、给工具白名单加条件逻辑、再补对应的单元测试。提示词的修改回路远短于代码的修改回路。

（2）交互体验不同。权限层硬拦截时，模型调用 writeFile 会收到一条工具错误（tool error），通常只能回复「抱歉，我无法执行这个操作」。而覆盖段下模型从一开始就知道「现在不该写代码」，遇到需要记录的内容会主动说「I'll add this to the plan file instead」，把信息写进 plan 文件而不是试图修改源码。前者是被动撞墙，后者是主动绕行，用户感受到的流畅度差异明显。

不过这条路径有一个前提：模型的系统提示词里确实包含覆盖段。子 Agent 的系统提示词是简化版、不包含覆盖段，因此子 Agent 必须在工具层补一道硬约束，详见 21.7 节。

21.3 覆盖段的四个关键段落

覆盖段在 system-prompt.ts 里整段定义为常量 PLAN_MODE_OVERLAY，约 80 行提示词。它不是简单告诉模型「只读」，而是一份完整的工作流规约——每一段都对应一个在实际使用中观察到的具体失败模式。以下拆解四个最关键的段落。

第一段是开场约束与 plan 文件路径。覆盖段的前几行同时完成两件事——明确禁止一切写操作，并告知模型唯一可写的 plan 文件路径：

Plan mode is active. The user indicated that they do not want you to execute yet
-- you MUST NOT make any edits (with the exception of the plan file mentioned below),
run any non-readonly tools (including changing configs or making commits),
or otherwise make any changes to the system. This supercedes any other instructions
you have received.

## Plan File Info
The plan file for this session lives at: {planFilePath}
This is the ONLY file you are allowed to edit.

{planFilePath} 是占位符——buildSystemPrompt 在拼装覆盖段时替换成实际路径（如 .x-code/plans/express-to-fastify-20260508-143022.md），让模型一进 plan mode 就确切知道哪个文件可写。这里 This supercedes any other instructions you have received 这句话的作用值得展开。覆盖段在系统提示词的最末尾追加，而前面的基础提示词里大量出现「主动帮用户写代码」「改完代码跑测试」这类鼓励动手的语句。如果不加 supercedes 这一句，模型会面临指令冲突——一边被告知「主动改代码」，一边又被告知「不能改」——它倾向于折中处理（如「只改一两个最关键的文件」），从而绕过 plan mode 的意图。supercedes 明确告诉模型遇到冲突时以覆盖段为准，前面的「主动写代码」暂时失效。

第二段是迭代式访谈循环。覆盖段把 plan mode 期间的工作模式定义为三步循环：

### The Loop

Repeat this cycle until the plan is complete:

1. Explore — Use readFile, glob, grep, listDir, webSearch, webFetch to read code...
2. Update the plan file — After each discovery, immediately capture what you learned...
3. Ask the user — When you hit an ambiguity..., use askUser. Then go back to step 1.

这段规定避免了两种常见偏差：模型无目标地反复探索代码但不产出任何 plan 内容，以及模型问了一两个问题就直接退出 plan mode。循环里的「After each discovery, immediately capture what you learned」强调边探索边写 plan，而不是把所有发现积攒到最后一次性倾倒——如果模型探索了十几个文件再一次性写 plan，中间任何一次上下文压缩都可能丢失关键发现。

第三段是 askUser 选项的两个隐藏 footer。plan mode 下 UI 会给每个 askUser 菜单自动追加两个额外选项：「Chat about this」（用户想聊一下，不想从菜单里选）和「Skip interview and plan immediately」（用户已经提供了足够信息，希望模型直接写 plan 并退出）。覆盖段告诉模型这两个选项的含义和应对方式——看到「Skip interview」就停止提问、把已有信息整理成 plan 并调用 exitPlanMode；看到「Chat about this」就用对话方式回应，不要立刻又弹一个 askUser 菜单。这两个选项由 UI 层自动注入，覆盖段明确要求模型不要自己在 options 数组里重复添加。

第四段是整个覆盖段最关键的一条硬规则——exitPlanMode 是退出 plan mode 的唯一方式：

### exitPlanMode is the ONLY way to leave plan mode (HARD RULE)

Plan mode is a state — calling askUser does NOT and CANNOT leave it.
Even if the user picks an option labelled "yes", "approve", ...
you are still in plan mode and writing files will still hit per-file permission prompts.

**Forbidden patterns** (do not do any of these):
- askUser({ question: "Approve this plan?", options: [...] })
- askUser({ question: "Should I proceed?", options: [...] })
...

这段针对的是模型最常见的错误用法——把「plan 写完了，要不要开始执行」做成 askUser 的选项。用户选了 Yes，模型以为获得了授权开始动手，但实际上 permissionMode 没有变——仍在 plan 状态，写文件仍然会触发审批对话框，导致整个流程卡住。覆盖段用大段文字加反例明确告诉模型：plan 审批必须通过 exitPlanMode 工具提交，askUser 无论用户怎么回答都不会改变会话状态。这个错误的根源在于模型把「用户表示同意」和「会话状态发生切换」混淆了——前者只是一个对话层面的回答，后者需要通过特定工具调用触发状态机转换。

整段覆盖段加起来约 700 tokens，每一段都对应一个在实际使用中被观察到的失败模式。这是 plan mode 设计的一条经验：模型在 plan mode 期间的行为完全由提示词控制，覆盖段写得越详细，模型的行为越稳定。

21.4 plan 文件为什么存在项目本地

每次进 plan mode，X-Code CLI 都新建一个 plan 文件。文件路径格式如下：

<repo>/.x-code/plans/express-to-fastify-20260508-143022.md

路径由两部分拼接而成：slug 和本地时间戳（YYYYMMDD-HHMMSS）。时间戳保证文件名唯一，slug 则让用户一眼看出这份 plan 对应哪个任务。slug 的生成分两种情况。如果用户输入包含英文单词（如「migrate Express to Fastify」），本地的 slugify 函数就能直接处理——小写化、空格转连字符、去除非字母数字字符、截断到 40 字符——得到 migrate-express-to-fastify，整个过程纯字符串操作，不消耗 token。但如果用户输入是纯中文（如「把项目从 Express 迁到 Fastify」），slugify 会把所有非 ASCII 字符清掉，剩下的有效字符不足 6 个，这时就回退到 LLM 生成路径：调一次模型，让它根据任务文本给出 2 到 4 个英文单词作为 slug。无论走哪条路径，slug 只在会话首轮生成一次并缓存，后续 plan mode 进出和 session 文件命名都复用同一个值。

// 源码：packages/core/src/agent/plan-storage.ts

export function slugify(text: string): string {
  return text
    .toLowerCase()
    .trim()
    .replace(/[^a-z0-9\s-]+/g, '') // 去除非 ASCII
    .replace(/\s+/g, '-')          // 空格转连字符
    .replace(/-+/g, '-')           // 合并连续连字符
    .replace(/^-+|-+$/g, '')       // 去除首尾连字符
    .slice(0, SLUG_MAX_LEN)        // SLUG_MAX_LEN = 40
    .replace(/-+$/g, '')           // 截断后再清一次尾部
}

文件存在项目本地（<repo>/.x-code/plans/）而非用户级目录（~/.x-code/），原因在于 plan 与仓库的代码状态绑定。通过查看 plan 文件，能立刻知道它对应的是哪个项目的哪段历史，不会出现「这份 plan 是给哪个项目写的」的混淆。每次进 plan mode 创建新文件而非覆盖固定文件，也避免了因模型写 plan 到一半被中断而导致文件损坏的风险。exitPlanMode 审批通过后 plan 文件留在原地不自动删除，读者想回顾历史可以直接查阅 .x-code/plans/ 目录。

21.5 两条触发路径与 UI 状态指示

进入 plan mode 有两条路径：用户主动和模型主动。用户主动是通过 /plan 斜杠命令，它接受三种用法：

（1）/plan 不带参数——在 plan 和 default 之间切换，交互式场景下最方便

（2）/plan on——幂等地设为 plan 状态

（3）/plan off——幂等地设为 default 状态

on / off 形式是为脚本化用例保留的——脚本不需要先查当前状态再决定切换还是设值，直接执行 /plan on 不会因为「已经是 plan mode」而出错或翻转。如果当前状态与目标状态相同，命令输出一行「Plan mode is already on / off — no change」，不做任何操作。如果参数无法解析（既不是 on/off 也不是 yes/no/true/false），命令返回用法提示。

// 源码：packages/cli/src/ui/components/App.tsx

function handlePlanToggle(commandText: string, arg: string) {
  const current = state.permissionMode === 'plan'
  const trimmed = arg.trim().toLowerCase()
  let next: boolean
  if (!trimmed) {
    next = !current // 无参数：切换
  } else {
    const parsed = parseBooleanArg(trimmed)
    if (parsed === null) {
      // 无法解析参数，提示用法
      addCommandMessage(commandText,
        `Unknown value: \`${arg}\`. Use \`/plan\`, \`/plan on\`, or \`/plan off\`.`)
      return
    }
    next = parsed
  }
  if (next === current) {
    // 已是目标状态，不做操作
    addCommandMessage(commandText,
      `Plan mode is already **${current ? 'on' : 'off'}** — no change.`)
    return
  }
  setPermissionMode(next ? 'plan' : 'default')
  addCommandMessage(commandText, next ? 'Enabled plan mode' : 'Disabled plan mode')
}

模型主动进入 plan mode 使用的是 enterPlanMode 工具（Ch.18 已介绍其基本形态）。与 /plan 命令不同的是，模型调用 enterPlanMode 必须经过用户审批对话框——这是为了防止模型在简单任务上启动 plan mode 拖慢执行节奏。如果模型已经在 plan mode 里再次调用 enterPlanMode，处理函数会短路返回「Already in plan mode. Continue the conversation; call exitPlanMode when the user has asked for an implementation and you have a plan ready.」，不重复弹审批。

进入 plan mode 后，终端输入框底部的状态栏左侧出现一行提示：

⏸ plan mode  ·  /plan to toggle

⏸（Unicode U+23F8）在传统 ConHost（老版 cmd.exe）下自动降级为 =，避免显示成方块（详见 Ch.25）。文字采用暗灰色样式（S_DIM），不抢占视觉重心但能让用户一眼确认当前处于 plan mode。Plan mode 当前不跨会话持久化——CLI 重启后默认回到 default 状态。

21.6 退出后为什么切到 acceptEdits 而不是 default

exitPlanMode 审批通过后，permissionMode 切到的不是 'default' 而是 'acceptEdits'：

// 源码：packages/core/src/agent/plan-tools.ts

if (approved) {
  state.permissionMode = 'acceptEdits' // 不是 'default'
  state.systemPromptCache = null
  // ...
}

acceptEdits 是 X-Code CLI 三档权限模式之一（详见 Ch.29），它的核心语义是：文件写入操作自动通过，不再弹审批对话框；shell 命令仍走正常审批。具体的路径分类规则（哪些路径即便在 acceptEdits 下也需要审批）详见 Ch.29。

为什么不回到 default？原因在于用户已经审批过整份 plan——plan 里写明了要改哪些文件、执行什么命令。后续模型按 plan 实施时每改一个文件再弹一次审批，价值不大——用户已经通过审批 plan 批量授权了这些写入操作。但 shell 命令仍走审批，因为 shell 的副作用不可逆（rm / git push 等），多一道确认更安全。这等于是一种一次性的批量授权：plan 审批那一刻把后续所有文件写入操作一并授权，shell 命令除外。

21.7 子 Agent 为什么用 toolFilter 而非 overlay

Plan mode 在主 Agent 路径上靠覆盖段软约束（21.2 节），但子 Agent 路径的约束机制不同——在工具层用 toolFilter 硬性禁止写工具：

// 源码：packages/core/src/agent/sub-agents/runner.ts

function buildToolFilter(agentDef, parentPermissionMode) {
  const deny = [...(agentDef.disallowedTools ?? []), 'task']

  // 主会话在 plan mode 时，general-purpose 子 Agent 额外禁止写工具
  if (parentPermissionMode === 'plan' && agentDef.name === 'general-purpose') {
    deny.push('writeFile', 'edit')
  }
  // ...
}

根本原因是子 Agent 的系统提示词是简化版（详见 Ch.19）——只包含角色定义、环境信息和输出契约，不包含 plan mode 覆盖段。子 Agent 完全不知道自己运行在 plan mode 的会话里，它看到的是一个普通的「通用 Agent」系统提示词。如果不加硬约束会出现这样的场景：主会话在 plan mode，模型调用 task({ subagent_type: 'general-purpose', prompt: '把 src/utils.ts 加个 formatDate 函数' })，子 Agent 收到 prompt 后看不出有只读约束——general-purpose Agent 的工具白名单本来就包含 writeFile / edit——子 Agent 会直接写入文件，主 Agent 的「plan mode 期间不能动代码」这一承诺被破坏。

X-Code CLI 只对 general-purpose 子 Agent 加这条约束，其他三个内置子 Agent（explore / plan / code-reviewer）不需要——因为它们的工具白名单本来就只包含读类工具，没有写工具可禁。这种「主 Agent 用提示词约束、子 Agent 用工具层约束」的不对称，是两套机制各自匹配各自的运行环境：主 Agent 有完整系统提示词、模型读得懂覆盖段，提示词约束更灵活也更容易维护；子 Agent 系统提示词简化、看不到覆盖段，必须在工具层硬性补上。理解了这个不对称就理解了 plan mode 的实现哲学——约束不在工具层、在提示词层；提示词管不到的地方（子 Agent）用工具层硬约束补。

21.8 小结

本章围绕 Express → Fastify 迁移的场景，完整走过了 Plan Mode 从进入到退出的全过程。Plan Mode 是一个三状态的会话状态机，核心约束不在权限层而在系统提示词末尾追加的覆盖段——覆盖段用 supercedes 句压住基础提示词的「动手」倾向，把模型每一轮的合法收尾锁定为 askUser 和 exitPlanMode 两条路径（21.2、21.3 节）。plan 文件存在项目本地、用 slug 加时间戳命名，slug 优先本地 slugify、太短则回退 LLM 生成一次后缓存（21.4 节）。两条触发路径——/plan 命令和 enterPlanMode 工具——分别面向用户主动和模型主动的场景（21.5 节）。退出后切到 acceptEdits 而非 default，等于 plan 审批是一次性批量授权，后续文件写入免审批、shell 仍走审批（21.6 节）。子 Agent 因为系统提示词不含覆盖段，在 plan mode 下用 toolFilter 硬性禁止写工具，与主 Agent 的提示词约束形成互补（21.7 节）。
