第 6 章 本地搭建与运行

上一章分析了 X-Code CLI 从 main() 入口到屏幕出现交互界面的完整启动流程，读者已经知道四步流水线的每一步做了什么。本章将从源码分析转入实际操作：把 X-Code CLI 的源码克隆到本地、安装依赖并构建、配置 API Key、启动验证。完成这四步之后，读者的终端上会出现一个可以正常对话的 CLI 实例，后续章节中所有「打开源码对照阅读」的操作都以这一步为前提。配套源码：github.com/woai3c/x-code-cli，本章及后续章节对应 v0.3.3 tag（详见序章「配套源码与版本对应」）。本章将分为如下几个部分进行介绍。

  • 6.1 节列出前置环境要求——Node.js、pnpm、Git 三项硬依赖及其版本约束的来由。
  • 6.2 节讲拉取代码与构建——从 clone 到 pnpm build 产出可执行的 bundle 文件。
  • 6.3 节讲配置 API Key——环境变量和 .env 两种方式的适用场景与注意事项。
  • 6.4 节讲启动验证——首次运行时的 Shell 侦测提示机制和通信链路确认。
  • 6.5 节说明后续章节的代码片段约定。
  • 6.6 节给出本章小结。

6.1 前置要求

在开始操作之前，读者需要确认本机已安装以下三项工具，如表 6-1 所示。

工具 版本 安装方式
Node.js ≥ 20.19.0 nodejs.org/download；推荐用 nvm（macOS / Linux）或 nvm-windows 多版本管理
pnpm ≥ 10（仓库 package.json 的 packageManager 字段固定到 pnpm@10.x） npm install -g pnpm 或 corepack enable（Corepack 会自动按 packageManager 字段激活对应版本）
Git 任意近版本 git-scm.com/downloads

表 6-1 前置环境要求

Node.js 版本下限为 20.19.0 的原因在 Ch.05 中已经讨论过：.env 文件加载依赖 Node 20.12 引入的内置 process.loadEnvFile 接口，20.19.0 以上的小版本在 ESM 模块解析等基础功能上更为稳定。pnpm 的版本约束来自仓库根 package.json 中的 packageManager: "pnpm@10.7.1" 字段，Corepack 会根据该字段自动下载并使用对应版本的 pnpm，确保所有开发者和 CI 环境使用同一版本的包管理器，避免因包管理器版本差异导致的 pnpm-lock.yaml 冲突。如果读者的系统中尚未安装 Node.js，推荐使用 nvm（macOS / Linux）或 nvm-windows（Windows）进行多版本管理，以便在不同项目之间切换 Node 版本而互不干扰。确认环境就绪后，在终端执行以下命令验证：

node -v    # v20.19.0+
pnpm -v    # 10+
git --version

6.2 拉取代码并构建

6.2.1 克隆仓库

git clone --branch v0.3.3 https://github.com/woai3c/x-code-cli.git
cd x-code-cli

--branch v0.3.3 将本地工作树固定到与本书正文严格对应的 commit。如果读者希望跟踪最新主干，可以省略 --branch 开关直接拉取默认分支，但需要注意最新代码可能已超出本书覆盖范围，部分文件路径或接口签名可能与正文描述不一致。建议首次跟读时使用指定 tag 的方式，等对整体架构有了充分理解之后，再切换到主干观察最新的演进。

6.2.2 安装依赖并构建

pnpm install
pnpm build

pnpm install 首次执行会下载约 500 个 npm 包（含传递依赖；直接依赖约 50 个，分布在 core 和 cli 两个工作区（Workspace）包中），耗时约 1–2 分钟，后续再执行时 pnpm 的全局内容寻址存储（Content-Addressable Store）会命中缓存，速度会快得多。pnpm build 内部按工作区拓扑顺序先后执行两步：先在 packages/core 中运行 tsc -b 将 TypeScript 编译为 JavaScript，再在 packages/cli 中运行 esbuild 将 cli 包打包成单文件 bundle（packages/cli/dist/cli.js），整个过程通常在数秒内完成。Ch.04 中已经讨论过选择 esbuild 而非 webpack 的原因：对于一个纯 Node.js CLI 应用，esbuild 的打包速度优势足以覆盖它在插件生态成熟度上的不足。构建工具链的完整配置细节详见附录一。

6.3 配置 API Key

X-Code CLI 至少需要一个供应商（Provider）的 API Key 才能启动。本书示例统一使用 DeepSeek 的 Key——在 platform.deepseek.com 注册后，进入「API Keys」页面创建即可。

6.3.1 环境变量方式

下表给出各 Shell 的「永久」与「临时」两种写法，读者按所在系统选择一行即可，如表 6-2 所示。

Shell / 系统 永久（用户级，新开终端生效） 临时（仅当前会话）
macOS / Linux bash echo 'export DEEPSEEK_API_KEY=sk-...' >> ~/.bashrc && source ~/.bashrc export DEEPSEEK_API_KEY=sk-...
macOS / Linux zsh echo 'export DEEPSEEK_API_KEY=sk-...' >> ~/.zshrc && source ~/.zshrc export DEEPSEEK_API_KEY=sk-...
fish set -Ux DEEPSEEK_API_KEY sk-... set -x DEEPSEEK_API_KEY sk-...
Windows PowerShell [Environment]::SetEnvironmentVariable('DEEPSEEK_API_KEY','sk-...','User') $env:DEEPSEEK_API_KEY = "sk-..."
Windows cmd setx DEEPSEEK_API_KEY "sk-..." set DEEPSEEK_API_KEY=sk-...

表 6-2 各 Shell 下 API Key 的配置方式

建议使用永久写法，新开终端即自动生效，不依赖特定的仓库目录。临时写法适合快速试用或在同一终端内切换不同的 Key。如果使用其他供应商，将 DEEPSEEK_API_KEY 替换为对应的变量名即可：ANTHROPIC_API_KEY、OPENAI_API_KEY、GOOGLE_GENERATIVE_AI_API_KEY、XAI_API_KEY、ALIBABA_API_KEY、ZHIPU_API_KEY、MOONSHOT_API_KEY。此外，OPENAI_COMPATIBLE_API_KEY 配合 OPENAI_COMPATIBLE_BASE_URL 可以接入任意 OpenAI 兼容端点（OpenAI Compatible Endpoint）。网页搜索工具（webSearch）需要额外配置 TAVILY_API_KEY 或 BRAVE_API_KEY（二选一即可，Tavily 优先），不配置则该工具无法返回搜索结果——模型仍然能看到并尝试调用它，但会收到一条包含注册地址和配置命令的错误提示，CLI 启动和其他 12 个内置工具均不受影响。以上模型供应商变量至少填写一项即可启动 CLI。

6.3.2 .env 文件方式

在仓库根目录新建 .env 文件，内容形如 DEEPSEEK_API_KEY=sk-...。CLI 启动时会从当前工作目录逐级向上搜索 .env 文件，找到第一个即加载，底层使用 Node 20.12+ 的内置 process.loadEnvFile 接口（详见 Ch.05 第 5.2.2 节）。.env 中定义的变量不会覆盖已存在的环境变量，因此通过 export 或系统级环境变量设置的值优先级更高。这个优先级顺序是合理的：用户在 Shell 配置文件中显式设置的值代表更明确的意图，不应被项目目录中的 .env 文件静默覆盖。

使用 .env 文件时有一个需要注意的安全细节。仓库自带的 .gitignore 已经包含 .env 和 .env.* 两条规则（仅排除 .env.example），因此 .env、.env.local、.env.dev 等常见变体都不会被 Git 跟踪。尽管如此，仍然建议读者养成在执行 git add 前先运行 git status 的习惯——如果将 Key 写入了 .gitignore 未覆盖的文件名（例如 keys.txt），或者在 fork 后修改了 .gitignore 规则，都有可能导致敏感信息被意外提交。日常开发仍建议以用户级环境变量为主，.env 仅作为项目内临时配置或多人协作时的补充手段。

6.4 启动验证

node packages/cli/dist/cli.js

执行上述命令后，终端应出现 X-Code CLI 的启动横幅（ASCII Logo、版本号、当前模型名称）和交互输入框。首次启动时，如果 CLI 未检测到任何已配置的 API Key，它会根据当前 Shell 类型自动输出对应的设置命令。Shell 侦测逻辑位于 packages/cli/src/shell.ts，覆盖 PowerShell、cmd、bash、zsh、fish、sh 共 6 种类型：在 Windows 上通过检测 PSModulePath 环境变量区分 PowerShell 与 cmd，在 Unix 系统上通过 SHELL 环境变量判断具体的 Shell 类型。这样设计的好处是用户不需要查文档就能获得与自己环境匹配的配置命令，按照终端输出的提示执行后重新启动即可。

启动成功后，读者可以输入一条简单的消息（如「帮我介绍一下这个项目」）来验证模型通信是否正常。如果收到模型的文本回复，说明从“代码拉取”到“ API 通信”的整条链路已经打通，本地开发环境的搭建就此完成。后续章节中所有「打开仓库对照阅读」的操作都以这一步为前提——读者在阅读某一章时，可以随时在本地仓库中打开对应的源码文件，结合运行中的 CLI 实例进行实验和验证。

6.5 后续章节的代码片段约定

后续章节正文中的代码片段都是关键摘录——为突出核心逻辑，会省略错误处理、类型注解、辅助分支和边界条件检查。完整可运行的版本以仓库内对应文件为准。每段代码上方会标注源文件路径，例如：

源码：packages/core/src/agent/loop.ts

按这个路径在仓库中打开即可查看完整上下文。当正文中的代码片段与仓库源码存在差异时，以仓库源码为准——正文为突出核心逻辑会进行适度简化，但不会改变代码的语义和执行顺序。

6.6 小结

本章完成了从源码到首次运行的全部操作。前置环境需要 Node.js 20.19.0 以上、pnpm 10 以上和 Git 三项工具，其中 pnpm 的版本通过仓库 package.json 的 packageManager 字段锁定，Corepack 据此自动激活对应版本。拉取代码时使用 --branch v0.3.3 将工作树固定到与本书正文对应的版本，首次跟读建议使用指定 tag 的方式。构建过程由 tsc -b 编译 core 和 esbuild 打包 cli 两步组成，耗时在数秒量级。API Key 的配置推荐使用用户级环境变量以获得跨终端的持久性，.env 文件作为项目级的补充手段，且不会覆盖已存在的环境变量。启动后若未检测到 Key，CLI 会针对当前 Shell 类型给出具体的配置命令，覆盖 PowerShell、cmd、bash、zsh、fish、sh 六种 Shell。完成本章的操作后，读者手中已经有了一份可运行的 X-Code CLI 源码实例，从下一章（Ch.07）开始，我们将进入第三部分「Agent Loop 引擎」，讨论 Tool Use 协议如何驱动 Agent 循环，每一个机制的讨论都可以在本地仓库中找到对应的源码对照阅读。
